## Purpose

Prove principle 2 with a wall clock: `down.ps1` (deletes the 4 demo RGs + Fabric
workspace items, pauses capacity) → Verifier confirms empty + idle cost profile →
`up.ps1` (replays L2–L10 pipelines + seed) → Verifier re-runs **every** layer audit
→ wall-clock report committed to `verification/reports/rebuild-proof.md`. The
<60-minute rebuild SLA applies to this standard path only; tenant objects persist
throughout (spec F6). The operational detail of the cycle lives in
`docs/runbooks/kill-rebuild.md`; this playbook is the *proof* procedure.

## Preconditions

- G0 complete + G1b granted; L2–L10 all hold Verifier PASS reports — you cannot
  prove a rebuild of an environment that never fully stood.
- Orchestrator unblock for L11.
- G2 consideration: `up.ps1` resumes the Fabric capacity for the reseed — the G2
  statement for the cycle's resume window is filed with the L11 run (trial phase:
  $0; paid F2: ~$0.36/hr × the window). This is the plan's ~$1–2/cycle.
- Credentials: `mls-github-deployer` for both workflows; `mls-verifier` for every
  audit. The Verifier must be able to run the **entire** audit suite
  (`verification/layer-01-audit.ps1` … `layer-10-audit.ps1`) — any single audit's
  credential gap surfaces here at the worst time, so check the suite ran green
  once in the preceding week.
- Timing: schedule the proof inside a window where the +75 min SQL auto-pause
  re-check (V6.4) and V6.3's async export do not block the wall-clock measurement
  — the <60 min clock covers `up.ps1` start → all synchronous audits green;
  explicitly-async criteria (V6.3, V6.4) re-attach on their own clocks [derived
  reading — the master plan pins the wall clock to the rebuild, and separately
  defines those criteria as async].

## Deploy procedure

1. **Down:**

   ```
   pwsh scripts/down.ps1
   ```

   Semantics (see `kill-rebuild.md` for full detail): parallel delete of
   `mls-rg-platform`, `mls-rg-apps`, `mls-rg-data`, `mls-rg-ops`; Fabric
   workspace-item delete inside `mls-operations` (workspace shell + roles persist
   [derived at L5]); capacity paused (trial: no-op); subscription-scope cost-export
   definition removed [derived at L6]. Tenant objects untouched.
2. **Down-state audit** (Verifier) — must PASS before `up.ps1` starts; this is the
   cycle's honesty checkpoint.
3. **Up, on the clock:**

   ```
   pwsh scripts/up.ps1
   ```

   Wraps `gh workflow run infra-up.yml` (full layer-ordered replay): L2–L4 replay
   as idempotent no-ops in seconds (tenant objects already present); L5 recreates
   lakehouse + seed (capacity resumed → seeded → re-paused); L6 Bicep platform;
   L7/L8 app CI deploys; L9 config re-verification; L10 re-arm is **not** in the
   timed path (re-seeding vulns is a demo-prep action, not an infrastructure
   layer) [derived]. The wall clock starts at `up.ps1` invocation and stops when
   the last synchronous layer audit goes green.
4. **Full re-audit:** Verifier runs every layer audit L1–L10 in order.
5. **Report:** wall-clock breakdown per phase committed to
   `verification/reports/rebuild-proof.md` (timed phases, audit results, cost
   observed for the cycle).

## F107 — the rebuild fails at L6, and only a real teardown could have found it

The first kill/reinstantiate cycle failed on the way back up, at L6, with both scheduled
query alert rules refusing to deploy:

```
l6-alert-kv   BadRequest: The workspace could not be found
l6-alert-sql  BadRequest: The workspace could not be found
```

The workspace was there. `az monitor log-analytics workspace list` returned
`mls-obs-demo-law`, `provisioningState: Succeeded`. What gives it away is the customer id:

```
customerId: faa5262a-f429-4202-8d5c-0ae649fd2e78   <- IDENTICAL to before the teardown
list-deleted-workspaces: mls-obs-demo-law          <- and still listed as soft-deleted
```

**Log Analytics workspaces soft-delete for 14 days.** Deleting `mls-rg-platform` did not
destroy the workspace; it soft-deleted it. Recreating a workspace with the same name in the
same resource group **recovers** the soft-deleted one rather than creating a new one - which
is why the customer id survived a teardown that was supposed to remove everything. ARM then
reports the recovered workspace as `Succeeded` while the scheduled-query-rule provider
cannot yet resolve it, so every dependent alert rule fails.

**Nothing short of a real teardown finds this.** Every previous L6 deployment ran against a
workspace that had existed for days. The failure needs a delete followed by a rebuild inside
the soft-delete window - which is the entire reason this layer exists, and the first thing
it did when finally run.

It also means the estate's rebuild story has a **second-rebuild-within-14-days** hole that
nobody would hit until a customer tried exactly what this layer advertises.

> ### CORRECTION, 2026-09-01 05:25Z — the diagnosis above was wrong
>
> I concluded from a 40-minute observation that the recovered workspace was permanently
> unreferenceable, and wrote that waiting it out "would have waited forever". **Both are
> false.** A retry of L6 about 105 minutes after the first failure **succeeded**: both alert
> rules now exist. And the workspace is STILL listed by `list-deleted-workspaces` — so the
> soft-delete listing was never the blocker, which means the tell I documented does not mean
> what I said it meant.
>
> What actually happens: a recovered workspace takes roughly **45 minutes** before dependent
> scheduled query rules can reference it. The workspace's own `modifiedDate` moved at
> 04:21Z, seven minutes after I measured and gave up. It is propagation — far slower than
> any retry window in this repository, which is why it presents as permanent.
>
> **Forty minutes of "no change" is not evidence of a stable state.** I asserted a negative
> from a sample shorter than the phenomenon, which is the same error as reading an empty
> API response as an empty resource (F105) — the thing this session kept finding in other
> people's checks.
>
> **The purge fix stays**, but for a corrected reason. It is no longer "the only thing that
> works"; it is that a rebuild which silently depends on a 45-minute propagation window is
> not a rebuild anyone can schedule or demo. Purging makes the next deploy deterministic
> instead of timing-dependent. That is a real argument — it is just not the argument
> originally written here.

**Candidate directions as originally written, kept because the reasoning is instructive
even where it was wrong:**

1. **Purge on teardown** - `az monitor log-analytics workspace delete --force` removes the
   workspace rather than soft-deleting it, so the rebuild creates a genuinely new one. The
   cleanest semantics for a demo whose claim is "kill it and bring it back", and it forfeits
   the 14-day recovery safety net that soft-delete exists to provide.
2. **Wait it out in the deploy** - treat recovery as propagation and retry the alert rules,
   stating the window and what it waits on, per CLAUDE.md. Unknown whether the provider ever
   catches up or whether recovery leaves the workspace permanently unreferenceable by new
   rules; that has to be measured, not assumed.
3. **Recover explicitly first** - have L6 detect the soft-deleted workspace and recover it as
   a named step before anything depends on it, so the ordering is stated rather than raced.

Direction 1 is the most honest about what teardown means and the easiest to reason about.
Direction 2 is the cheapest if the provider does catch up. Measure before choosing.

## What the 2026-09-01 cycle actually proved, and what it did not

The first kill/reinstantiate cycle ever executed. Recording the SCOPE rather than the
aspiration, because the two are not the same and a reader deserves the difference.

**Proved.** The four Azure resource groups were deleted and V11.1 passed: `az group list`
returned nothing matching the prefix. The estate then rebuilt from a cold workflow
dispatch, layer by layer, with the Verifier signing off each before the next began.

**Not proved, and deliberately so: Fabric.** The run passed `skip_fabric: true`, so the
workspace, the lakehouse and its ten seeded tables were never touched. The item
tombstone-and-recreate path remains **untested**. The reason was coordination, not caution
- a parallel session was mid-investigation against that lakehouse, and deleting it would
have destroyed both their work and the only verified-correct data in the estate. It is a
supported input for exactly this, but it means **V11.1's claim is "the Azure resource
groups", not "the estate"**, and nothing here should be quoted as the latter.

**Not proved, for want of a credential: V11.2.** "Tenant objects intact" is the SAFETY
criterion of the whole cycle - it is what proves a teardown did not cross the G3 line. It
recorded SKIP, honestly, because the tenant-object audits need `MLS_VERIFIER_CERT_BASE64`
and no CI credentials exist (P-12).

It was checked by hand instead: after the teardown, zero resource groups, **7 Entra groups
and 6 app registrations intact**. That is genuine evidence and it is not a sign-off. A
human looking at the tenant is exactly the thing the Verifier exists to replace, and the
cycle cannot be called complete until V11.2 passes on its own.

**Narrowed by F104: V11.3.** The up-phase audit re-executes the other layer audits, each
with its own retry windows, which is hours - and a CI login's federated assertion expires
after about five minutes, so the later child audits would fail on an expired credential
rather than on their subject. The run therefore selected a subset via
`l11_child_audit_layers`, and the report names which layers were re-run. A narrower V11.3
is a narrower claim, stated rather than implied.

The full-fidelity version of that claim was demonstrated separately the same night: a
complete `infra-up` took every layer from L2 to L7 green, including L7 at 5/5 - the layer
that had failed this workflow eight consecutive times.

## Validation cycle

Run by the Verifier as `mls-verifier` via `verification/layer-11-audit.ps1`. Report:
`verification/reports/L11-<date>.md` plus the committed
`verification/reports/rebuild-proof.md`.

### V11.1 — All RGs absent post-down

- **Criterion (master plan):** all RGs absent post-down.
- **Query:**

  ```
  az group list --query "[?starts_with(name,'mls-rg-')].name"
  ```

- **Expected:** empty array — none of `mls-rg-platform`, `mls-rg-apps`,
  `mls-rg-data`, `mls-rg-ops` present (nor any stray `mls-rg-*`). Supplementary:
  the Fabric item list for workspace `mls-operations` returns zero items.
- **Retry/propagation:** RG deletion is asynchronous — V11.1 declares
  `-RetryWindowMinutes 30` from the `down.ps1` completion signal, polled every 20 s
  (F59); a stuck delete beyond that is a failure (see failure mode 2).

### V11.2 — Tenant objects intact (L3/L4 audits still pass)

- **Criterion (master plan):** tenant objects intact (L3/L4 audits still pass).
- **Query:** re-execute, verbatim, in the down state:

  ```
  pwsh verification/layer-03-audit.ps1   # users/groups/CA/app registrations (V3.1–V3.4)
  pwsh verification/layer-04-audit.ps1   # labels + GUIDs (V4.1) — this is V4.2's L11 re-execution
  ```

- **Expected:** both audits PASS with the environment torn down — 5 users, 4
  groups, 3 app registrations, CA still `enabledForReportingButNotEnforced`,
  licences `Active` for every user the manifest flags `licensed` (see L03 V3.4 -
  unlicensed personas are by design, not a regression), 4 labels with unchanged
  GUIDs. Any regression here means
  `down.ps1` crossed the tenant-object line: stop, do not run `up.ps1`, escalate
  (this is simultaneously a G3-boundary violation and a G4 event).
- **Retry/propagation:** none beyond the underlying audits' own windows — these
  objects were not touched, so propagation is not in play.

### V11.3 — Post-up: all layer audits green

- **Criterion (master plan):** post-up: all layer audits green.
- **Query:**

  ```
  foreach ($n in 1..10) { pwsh verification/layer-$('{0:d2}' -f $n)-audit.ps1 }
  ```

- **Expected:** PASS for every layer audit L1–L10 against the rebuilt environment,
  including the exact-value checks (launches = 1,200; CA state
  `enabledForReportingButNotEnforced`; capacity `Paused` / trial-equivalent;
  minReplicas 0; label GUIDs unchanged). Async criteria V6.3/V6.4 re-attach on
  their own clocks and are recorded PENDING→PASS in the proof report [derived, per
  Preconditions].
- **Retry/propagation:** each audit keeps its own bounded retry windows; the
  rebuild path avoids tenant-object churn precisely so the long Entra/label
  propagation waits never appear here (spec F6).

### V11.4 — Wall-clock < 60 minutes

- **Criterion (master plan):** wall-clock < 60 min.
- **Query:** timestamps recorded by `up.ps1` (start) and the Verifier's audit
  runner (last synchronous audit green), cross-checked against workflow-run
  `created_at`/`updated_at` from
  `gh api repos/paulcfuqua/azure-devsecops-demo/actions/runs` — two independent clocks,
  the report cites both.
- **Expected:** elapsed < 60:00 minutes. The proof report breaks down the critical
  path (see `kill-rebuild.md` § clock budget) so a near-miss shows *where* the
  time went.
- **Retry/propagation:** none — the measurement is the measurement. A ≥ 60 min
  result is a criterion failure; re-run once after remediating the identified
  bottleneck (that re-run is attempt two — the G4 rule applies as everywhere).

### V11.5 — Run-rate returns to idle profile

- **Criterion (master plan):** run-rate returns to idle profile.
- **Query:**

  ```
  az consumption usage list --start-date <cycle+1d> --end-date <cycle+2d> \
    --query "[].{svc:instanceName, cost:pretaxCost}"
  az resource show --ids $env:FABRIC_CAPACITY_ID --query properties.state   # paid F2 phase
  az sql db show --ids <dbId> --query status                                # expect Paused
  ```

- **Expected:** daily cost consistent with the torn-down/parked envelope —
  **< $5/month idle** pro-rated (≈ < $0.17/day) once the post-cycle day's data is
  in; capacity `Paused` (trial: recorded equivalent); SQL `Paused`; no `mls`
  resource outside the plumbing set (OneLake storage, LAW retention, Key Vault,
  budget/export). The $75 budget's alerts (50/80/100%) are the continuous
  backstop.
- **Retry/propagation:** consumption data lags up to 24–48 h — this criterion
  closes asynchronously in the proof report, PENDING at cycle end, PASS on the
  first full post-cycle day's data. A cost anomaly here is a direct G4 trigger
  regardless of retry counts.

## Teardown

- **Teardown is the deliverable.** The standard cycle (`down.ps1`) is gate-free by
  design — RG-scoped demo resources + workspace items only. The G3-gated
  full-tenant teardown variant (Entra objects, labels, Fabric workspace shell,
  OIDC federation — with its honest 2–3 h rebuild SLA) is documented in
  `docs/runbooks/kill-rebuild.md` § G3 variant and is **not** part of L11's proof.

## Rollback

- **First validation failure:** identify which half broke.
  - Down-side failures (V11.1, V11.2): fix `down.ps1`/stuck resources; V11.2
    regressions halt everything (see above) — that path goes straight to
    escalation, not iteration.
  - Up-side failures (V11.3): the failing layer's own playbook rollback applies;
    L11 then re-runs **from `down.ps1`** — the proof must be a clean
    uninterrupted cycle, not a patched one.
  - Clock failure (V11.4): remediate the named bottleneck, full clean re-run.
- **Second consecutive failure of L11 → G4.** Additionally: any cost anomaly
  (V11.5) or credential failure during the cycle is G4 immediately, independent of
  the two-failure count.

## Failure modes

1. **Rebuild exceeds 60 minutes.** Detection: V11.4. Usual suspects: Fabric
   SQL-endpoint sync lag inflating L5's audit wait; container image rebuilds
   uncached; serialized workflow legs that should run parallel. Response: read the
   proof report's phase breakdown; fix the specific leg (cache, parallelism);
   clean re-run.
2. **RG delete stuck** (Key Vault soft-delete interplay, resource lock, or a
   nested resource in `Failed` state). Detection: V11.1 still lists an RG at
   +30 min; `az group show` shows `Deleting`. Response: `az group delete` again
   (idempotent); inspect blockers via
   `az resource list -g <rg>`; locks must be removed via the deploy identity —
   and their existence questioned, since nothing in this repo creates locks.
3. **Idempotent replay is not idempotent** (L2–L4 scripts attempt writes on
   existing tenant objects and error, stalling `infra-up.yml`). Detection: replay
   leg fails in minutes on a Graph/policy conflict error. Response: this is a
   defect in a create-if-absent guard — fix the script (Track C's Pester
   idempotency branches exist to prevent exactly this), re-run cycle.
4. **Orphan spend outside the four RGs** (V11.5 shows cost from a resource the
   cycle never deletes — e.g., a subscription-scope artifact created out-of-band).
   Detection: V11.5 consumption line items. Response: locate via
   `az resource list --query "[?starts_with(name,'mls')]"` at subscription scope;
   anything outside the four RGs + known plumbing violates principle 1 —
   delete via scripted path and root-cause which layer created it.
5. **Down-state audit passes but rebuild finds drift** (e.g., L5 workspace shell
   lost its `mls-verifier` Viewer role because someone deleted the workspace
   rather than its items). Detection: V11.3's L5 audit fails on access. Response:
   re-grant via the L5 script's role step (idempotent); root-cause the workspace
   deletion — workspace-shell deletion is G3 and should have left a trail.
