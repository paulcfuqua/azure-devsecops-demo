# L5 Playbook — Fabric Workspace, Lakehouse, Generators, Seeding

| | |
|---|---|
| **Layer** | L5 |
| **Lead** | Data & Copilot |

| **Teardown gate class** | Gate-free (workspace-item delete); labels/capacity persist |
| **Cost delta** | ~$0.36/hr only while resumed on paid F2 (~2 h for first seed ≈ $0.75/run); $0 during the Fabric trial |

## Purpose

Create workspace `mls-operations` on the Fabric capacity, the lakehouse
`mls_operations` with the 10 Delta tables (`launches`, `scrubs`, `vehicles`, `pads`,
`telemetry_summary`, `parts`, `suppliers`, `work_orders`, `cost_daily`,
`findings_history`), run the deterministic Python generators (seed `20260822`,
realistic messiness: scrub cascades, Saturday launch bias, supplier lead-time
outliers), load the seed, and leave the capacity paused. Because the seed is
deterministic, every downstream expectation — Verifier row counts, copilot golden
answers — is exact, not approximate.

## Preconditions

- G0 complete + G1b granted; L4 Verifier PASS.
- Orchestrator unblock for L5.
- **G2 approval for the capacity resume** — the master plan gates *each* resume.
  During the Fabric 60-day trial the stated cost delta is $0 (trial capacity bills
  nothing), which makes the G2 statement trivial but still recorded; once on paid
  F2 the statement is ~$0.36/hr × expected window. The Orchestrator files the G2
  with cost delta + duration before the workflow runs.
- **Fabric SP API toggle on** (G0 item C4) and `mls-github-deployer` admin on the
  capacity — `verify-g0.ps1` asserted this; L5 fails fast without it (risk register
  item 3).
- Credentials: `mls-github-deployer` for Fabric REST writes; `mls-verifier` needs
  workspace read + SQL endpoint query access for the audit. [derived] The workspace
  creation script grants `mls-verifier` the workspace **Viewer** role — the master
  plan requires the Verifier to query the SQL analytics endpoint (here and at L8)
  but does not name the access path; Viewer is the least privilege that allows it.
- Tracks A + C merged: generators pytest-green (determinism, row counts,
  distributions, referential integrity); `infra/fabric/*.ps1` REST wrappers
  Pester-green with mocked REST.

## Deploy procedure

1. Dispatch:

   ```
   gh workflow run layer-05-fabric.yml
   ```

   [derived] Workflow name per the `layer-<nn>-*.yml` pattern. Sequence inside the
   workflow (all via `infra/fabric/*.ps1` REST wrappers as `mls-github-deployer`):
   1. **Resume capacity** (G2 recorded — see Preconditions). On the trial capacity
      this is a no-op with $0 delta; on paid F2 it is a real ARM resume.
   2. Create workspace `mls-operations` bound to `$FABRIC_CAPACITY_ID`
      (create-if-absent); assign `mls-verifier` Viewer [derived, above].
   3. Create lakehouse `mls_operations` in the workspace (create-if-absent).
   4. Generate data: `python -m generators build` (Track A entry point) with seed
      `20260822` → `data/generated/` (gitignored, regenerated every run — the seed,
      not the artifacts, is the source of truth).
   5. Load: `data/seed/` loaders write the 10 Delta tables.
   6. **Pause capacity** — unconditionally, in a workflow `finally` step, so a
      failed seed can never leave a paid capacity running (trial: no-op).
2. Post run URL + expected-counts fixture (from Track A's pytest expectations) to
   the Verifier.

## Validation cycle

Run by the Verifier as `mls-verifier` via `verification/layer-05-audit.ps1`. Report:
`verification/reports/L05-<date>.md`.

### V5.1 — Workspace and lakehouse exist

- **Criterion (master plan):** Fabric REST: workspace + lakehouse exist.
- **Query:**

  ```powershell
  $ws = (Invoke-RestMethod -Uri "https://api.fabric.microsoft.com/v1/workspaces" -Headers $verifierAuth).value |
        Where-Object displayName -eq 'mls-operations'
  (Invoke-RestMethod -Uri "https://api.fabric.microsoft.com/v1/workspaces/$($ws.id)/lakehouses" -Headers $verifierAuth).value |
        Where-Object displayName -eq 'mls_operations'
  ```

- **Expected:** workspace `mls-operations` present and bound to the configured
  capacity ID; exactly one lakehouse `mls_operations` inside it.
- **Retry/propagation:** Fabric metadata is read-your-writes within minutes;
  standard 30-minute bounded retry covers API-side lag.

### V5.2 — Table list matches manifest

- **Criterion (master plan):** table list matches manifest.
- **Query:**

  ```powershell
  (Invoke-RestMethod -Uri "https://api.fabric.microsoft.com/v1/workspaces/$($ws.id)/lakehouses/$($lh.id)/tables" -Headers $verifierAuth).data.name
  ```

- **Expected:** exactly the 10 tables — `launches`, `scrubs`, `vehicles`, `pads`,
  `telemetry_summary`, `parts`, `suppliers`, `work_orders`, `cost_daily`,
  `findings_history`. Set equality: a missing table fails, and so does an extra one
  (drift).
- **Retry/propagation:** table registration after Delta writes can lag the load by
  several minutes; 30-minute bounded retry.

### V5.3 — SQL analytics endpoint returns expected row counts

- **Criterion (master plan):** SQL analytics endpoint returns expected row counts
  (e.g. `launches` = 1,200 ± 0 — seed is deterministic).
- **Query:** via the lakehouse SQL analytics endpoint connection string from V5.1's
  metadata, as `mls-verifier` (workspace Viewer):

  ```sql
  SELECT 'launches' AS t, COUNT(*) AS n FROM launches
  UNION ALL SELECT 'scrubs', COUNT(*) FROM scrubs
  -- ... one arm per table, all 10
  ```

- **Expected:** `launches` = **1,200 exactly (± 0)** — the plan pins this value; the
  other 9 tables must equal the counts in Track A's committed expected-counts
  fixture (`data/generators/tests/expected_counts.json` [derived path — Track A owns
  the fixture; the plan pins only the launches count]). Any deviation means
  non-determinism or a partial load — both hard failures, no tolerance band.
- **Retry/propagation:** the SQL analytics endpoint takes time to sync new Delta
  tables after first creation (commonly minutes, occasionally longer); 30-minute
  bounded retry, poll every 5 minutes. Note: if the capacity has already been
  paused per step 6, the audit resumes nothing — SQL-endpoint reads on a paused
  capacity fail, so the audit runs its SQL check **before** the layer-close pause
  is verified, or during the same resumed window as the seed. Sequence: V5.1 → V5.2
  → V5.3 while resumed, V5.4 after the pause step completes.

### V5.4 — Capacity paused at layer close

- **Criterion (master plan):** capacity state == `Paused` after layer completes.
- **Query:** for paid F2 (ARM resource):

  ```
  az resource show --ids $env:FABRIC_CAPACITY_ID --query "properties.state"
  ```

  During the Fabric trial: `GET https://api.fabric.microsoft.com/v1/capacities` and
  record the trial capacity's state.
- **Expected:** paid F2: `"Paused"` exactly. Trial phase [derived]: trial capacities
  expose no pause control and bill $0; the audit records
  `state=Active (trial, $0/hr)` as the accepted equivalent, and this criterion
  re-arms verbatim (`Paused` required) the moment G2 moves the workspace to paid
  F2. The cost-safety *intent* of the criterion (no idle spend) holds in both
  phases.
- **Retry/propagation:** pause is near-immediate; single check, one retry at
  +5 minutes.

## Teardown

- **Standard kill/rebuild cycle:** `infra/fabric/teardown-items.ps1` [derived name —
  master plan: "workspace-item delete script"] deletes the lakehouse (and any other
  workspace items) inside `mls-operations`; invoked by `down.ps1`. **Gate class:
  gate-free** — workspace items are demo resources. Labels (L4) and the capacity
  itself **persist**; the workspace shell persists too so role assignments
  (including `mls-verifier` Viewer) survive the cycle [derived — the plan deletes
  "workspace items", not the workspace].
- **Full teardown:** deleting the workspace `mls-operations` itself or the capacity
  is **G3** (tenant/capacity-level; the brief lists the Fabric workspace explicitly
  under G3).

## Rollback

- **First validation failure:** Verifier files specifics. Data & Copilot lead's
  standard remediation is **wipe-and-reseed**: run `teardown-items.ps1` (gate-free),
  then re-dispatch `layer-05-fabric.yml` — determinism guarantees the reseed
  converges to the identical expected state, so partial-load debris never has to be
  repaired in place.
- **Cost hygiene during rollback is non-negotiable:** every remediation run ends
  with the capacity pause step, failure or not. If any rollback iteration needs the
  capacity resumed on paid F2, that is a fresh G2 statement (cost delta + expected
  window).
- **Second consecutive failure of L5 → G4** — and the Verifier independently checks
  capacity state at every layer close (risk register item 4), so a rollback that
  leaves the capacity resumed trips its own alarm.

## Failure modes

1. **Fabric REST returns 401/403 for the SP.** Detection: first REST call fails.
   Cause: the G0 tenant toggle "Service principals can use Fabric APIs" is off, or
   `mls-github-deployer` lost capacity admin. Response: human re-checks G0 item C4
   (portal, ~2 min); credential failures recurring → G4.
2. **Capacity left resumed after a failed run (paid F2).** Detection: V5.4 fails;
   budget burn visible in Cost Management. Response: pause immediately via
   `infra/fabric/` wrapper (a pause is a spend *decrease* — no gate); root-cause why
   the `finally` pause step did not run; this is also a cost-anomaly G4 trigger if
   spend already deviated.
3. **Row counts off (V5.3 mismatch).** Detection: audit SQL counts differ from
   fixture. Causes seen: partial load (loader crashed mid-table), generator drift
   (dependency bump changed RNG behavior — pytest determinism test should have
   caught it pre-merge), or double-append from a re-run without wipe. Response:
   wipe-and-reseed (Rollback path); if generator drift, pin the dependency and
   re-baseline *nothing* — the seed contract (`launches` = 1,200, Saturday bias) is
   fixed and generators must be fixed to honor it.
4. **SQL analytics endpoint not yet synced** (tables exist, SQL queries 404/empty).
   Detection: V5.2 passes while V5.3 errors. Response: this is the propagation case
   the 30-minute retry exists for; if sync exceeds the window, fail the audit and
   investigate capacity health rather than extending the window ad hoc.
5. **Workspace name collision** (a stray `mls-operations` from a previous tenant
   experiment, bound to another capacity). Detection: V5.1 finds the workspace but
   capacity ID mismatches. Response: treat as drift — do not adopt the stray;
   G3-gated deletion of the impostor workspace or rename via sponsor decision, then
   re-run.

## Deferred validation

  pytest proves determinism (identical hash for seed `20260822` across runs), exact

  Saturday**), referential integrity across the 10 tables; `infra/fabric/*.ps1`
  Pester-tested against mocked REST (idempotency, error paths, the unconditional
  pause step); PSScriptAnalyzer clean; `actionlint` on `layer-05-fabric.yml`

  behavior and SP API access. Covered by `verification/layer-05-audit.ps1` at L5
