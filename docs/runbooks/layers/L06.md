## Purpose

Deploy the shared runtime platform via Bicep/AVM: the Container Apps environment,
workspace-based App Insights + Log Analytics, Azure SQL serverless per app DB
(auto-pause 60 min, min 0.5 vCore), storage for cost exports, the Cost Management
daily export → storage → consumption Function → lakehouse `cost_daily` pipeline, and
Key Vault. Everything is scale-to-zero/auto-pause so the built-but-parked profile
stays under $15/month.

**Changed 2026-08-24 (Copilot Studio amendment):** spec F4's `ANTHROPIC_API_KEY` is
void — no LLM key exists anywhere, and **no cloud** credential is stored in CI (that is
what OIDC is for). CI does still hold four long-lived credentials, and this vault holds
two more — see `SECURITY.md` for the complete list; the claim that CI "stores no secret
at all" was finding F28. Key Vault stays in
this layer, now holding the **Direct Line secret** for the L8 agent, which
`apps/directline-token` reads with its managed identity at runtime to mint per-session
chat tokens for the control tower's Ask tab. The human places that value at G0 item C7,
after L8 first publishes the agent; on a kill/rebuild the vault recovers from
soft-delete and the value is re-seeded from that same source.

## Preconditions

- G0 complete + G1b granted; L5 Verifier PASS (the cost-export Function writes to
  lakehouse `mls_operations` table `cost_daily`, which L5 created).
- Orchestrator unblock for L6.
- No G2 needed: every resource here is serverless/auto-pause/consumption by design —
  a deviation (e.g., provisioned SQL, minReplicas > 0) would *itself* be a
  spend-profile change requiring G2, and the audit treats it as a failure instead.
- Credentials: `mls-github-deployer` (Owner) via OIDC; `mls-verifier` (Reader) for
  the audit — Reader includes `*/read`, which covers ARM GET and Log Analytics
  query.
- Track E artifacts merged: `infra/bicep/` platform templates `bicep build` +
  `bicep lint` clean; names resolved exclusively through `infra/bicep/naming.bicep`
  (e.g. `mls-ops-demo-sql` per the CLAUDE.md convention).

## Deploy procedure

1. Dispatch:

   ```
   gh workflow run layer-06-platform.yml
   ```

   [derived] Workflow name per the `layer-<nn>-*.yml` pattern. The workflow:
   1. runs `az deployment sub what-if` on the platform templates and uploads the
      diff artifact;
   2. deploys via `az deployment sub create` → RG `mls-rg-platform` and the layer's
      resources with tags inherited by the L2 modify policy. Per-resource RG
      placement is authoritative in the Bicep templates (Track E), teardown scope
      per the master plan is `mls-rg-platform`;
   3. wires the Cost Management daily export (subscription scope → export storage),
      publishes the **Flex Consumption** Function (`apps/cost-ingest`) that ships export
      files to lakehouse `cost_daily`, and subscribes it to blob-created events on the
      `cost-exports` container. The Function App itself, its plan, its user-assigned
      identity, its runtime storage account, its container-scoped **Storage Blob Data
      Reader** grant and the Event Grid system topic are all resources of
      `infra/bicep/platform/main.bicep`; only the code publish and the event
      subscription are workflow steps, because the subscription's endpoint embeds a
      system key that does not exist until the site does. Both carry
      `continue-on-error`: the FinOps leg is not on the critical path and must not cost
      L6 its Verifier sign-off. **Until 2026-08-28 none of this existed** — this step
      described a deploy that was never written, which was finding F19. Its Fabric
      workspace **Contributor** grant (the least Fabric role that can write to OneLake)
      is issued from `layer-07-apps.yml`, because L5 and L6 run in parallel and only L7
      can assume both the workspace and the identity exist;
   4. creates the Key Vault holding `directline-secret` and grants the
      `apps/directline-token` Function's managed identity **Key Vault Secrets User** on
      it, wiring the Function's `DIRECTLINE_SECRET` app setting as a Key Vault
      reference. The *value* is placed by the human at G0 item C7 once L8 has published
      an agent — this workflow never sees it, and no GitHub Actions secret is involved
      anywhere in the chain;
   5. records deployment outputs (resource IDs, SQL server/DB names, LAW workspace
      ID) as the layer manifest artifact for the audit.
2. Post run URL + deployment name to the Verifier.

## Validation cycle

Run by the Verifier as `mls-verifier` via `verification/layer-06-audit.ps1`. Report:
`verification/reports/L06-<date>.md`. Expected values resolve from the Bicep-declared
manifest (deployment outputs), never from a teammate's message.

### V6.1 — ARM state matches manifest exactly

- **Criterion (master plan):** ARM GET on each resource:
  SKU/serverless/auto-pause/minReplicas values match manifest exactly.
- **Query:** for each resource ID in the deployment outputs
  (`az deployment sub show --name layer-06 --query properties.outputs` [derived
  deployment name]):

  ```
  az resource show --ids <id> --query "{sku:sku, props:properties}"
  # plus targeted asserts, e.g.:
  az sql db show --ids <dbId> --query "{sku:currentSku.name, autoPause:autoPauseDelay, minCap:minCapacity}"
  az containerapp env show --ids <envId> --query properties.provisioningState
  ```

- **Expected (concrete values the plan pins):** SQL: serverless SKU
  (`GP_S_Gen5`-class), `autoPauseDelay == 60` (minutes), `minCapacity == 0.5`;
  every container app added later gets `minReplicas == 0` (asserted for the
  environment's defaults now, per-app at L7); all other properties equal to the
  Bicep-declared values, field for field. Any mismatch — including a "better" SKU —
  is a FAIL (an un-gated spend increase).
- **Retry/propagation:** ARM GET is read-your-writes after deployment success;
  single pass, one retry at +5 minutes for provisioningState `Succeeded`.

### V6.2 — Log Analytics query succeeds as verifier

- **Criterion (master plan):** KQL query against LAW succeeds as verifier.
- **Query:**

  ```
  az monitor log-analytics query --workspace <lawCustomerId> \
    --analytics-query "Heartbeat | take 1; Usage | summarize count()" --timespan P1D
  ```

  (executed under the `mls-verifier` login — the point of the criterion is that the
  Reader credential can independently query the same workspace the control tower
  will use).
- **Expected:** HTTP 200 / a well-formed table result (row content may be empty this
  early — success of the query as the Reader identity is the criterion).
- **Retry/propagation:** workspace RBAC propagation up to ~15 min; standard
  30-minute bounded retry.

### V6.3 — First cost export file lands within 24 h

- **Criterion (master plan):** first cost export file lands within 24 h (async
  check L7 window).
- **Query:**

  ```
  az storage blob list --account-name <exportSA> --container-name cost-exports \
    --auth-mode login --query "[].{name:name, len:properties.contentLength}"
  ```

  and, once the Function has run, the lakehouse side:
  `SELECT COUNT(*) FROM cost_daily` via the SQL analytics endpoint (capacity resumed
  window required — piggyback on the next scheduled resume rather than forcing one).
- **Expected:** ≥ 1 export blob with `len > 0` within 24 h of L6 completion; a
  `cost_daily` row count > 0 after the Function's first ingestion.
- **Retry/propagation:** **explicitly asynchronous — the L6 audit report records
  this criterion as PENDING and the audit re-runs it during the L7 window** (the
  master plan's "async check L7 window"). L6 sign-off may proceed with V6.3 PENDING;
  it must be closed PASS before L7's own sign-off. Cost Management's first export
  can take up to 24 h and is outside our control — do not G4 on a first-day miss;
  one full re-check at +24 h, then it counts as a failure.

### V6.4 — SQL auto-pauses after idle

- **Criterion (master plan):** SQL auto-pauses (checked after 75 min idle).
- **Query (scheduled 75 minutes after the last deployment touch of the DB):**

  ```
  az sql db show --ids <dbId> --query "status"
  ```

- **Expected:** `"Paused"`. The 75-minute mark = 60-minute auto-pause delay + 15
  minutes of margin.
- **Retry/propagation:** if `Online` at +75 min, check
  `az sql db list-usages`/recent connections for a chatty client (a monitoring probe
  keeping the DB awake is the classic cause), then one re-check at +120 min. Still
  `Online` → FAIL (idle-cost model broken).

### V6.5 — SQL backup posture matches the template-pinned values

- **Criterion:** NOT a master-plan criterion — it is not in the 43-row
  traceability table in `docs/runbooks/layers/README.md`, which that file's own
  header states is scoped exactly to master-plan criteria. Added by
  compliance/findings/2026-08-26-prepublication-review.md#f16 (Task 18 — CP-9):
  `infra/bicep/platform/main.bicep`'s `databases` array set no
  `shortTermRetentionPolicy`/`backupShortTermRetentionPolicy` or
  `requestedBackupStorageRedundancy`, so both resolved to whatever the Azure
  platform default was on a given deployment day — a decision this template never
  made, documented, or verified. Same shape as every other SQL property V6.1
  already pins field-for-field; backup posture was the one nobody looked at.
- **Query:**

  ```
  az sql db show --ids <dbId> --query requestedBackupStorageRedundancy
  az resource show --ids <dbId>/backupShortTermRetentionPolicies/default --query properties.retentionDays
  ```

  (`requestedBackupStorageRedundancy` is a top-level database property;
  `retentionDays` lives on the child `backupShortTermRetentionPolicies/default`
  resource, which a plain `az resource show` reaches without the dedicated
  `az sql db str-policy show` command's separate `--resource-group`/`--server`/
  `--database` argument shape.)
- **Expected:** `requestedBackupStorageRedundancy == Local`; short-term
  `retentionDays == 7`. Both are template parameters
  (`sqlBackupStorageRedundancy`, `sqlBackupRetentionDays`) restated explicitly in
  `demo.bicepparam`; any mismatch — including a "better" tier — is a FAIL, same
  as V6.1's treatment of a "better" SKU, since backup storage redundancy has its
  own cost and residency implications (Geo/GeoZone would replicate backup data
  cross-region, widening the boundary the `allowedLocations` policy otherwise
  pins). No `backupLongTermRetentionPolicy` is asserted — the template does not
  set one, deliberately: the database holds seeded synthetic data with a
  deterministic regenerator (`data/seed/`), not data an LTR vault needs to
  protect.
- **Retry/propagation:** ARM GET is read-your-writes after deployment success;
  single pass, one retry at +5 minutes — same shape as V6.1.

## Teardown

- **Standard kill/rebuild cycle:** `az group delete --name mls-rg-platform --yes`
  (invoked by `down.ps1`, which deletes all four demo RGs — `mls-rg-platform`,
  `mls-rg-apps`, `mls-rg-data`, `mls-rg-ops`). **Gate class: gate-free** — RG-scoped
  teardown of demo resources requires no approval by design.
- The Cost Management export definition at subscription scope is deleted by
  `down.ps1`'s cleanup step and recreated by replay [derived — the export object
  lives at subscription scope, not in an RG; leaving it pointed at a deleted
  storage account would generate failure noise].
- Nothing here is G3: no tenant objects in this layer.

## Rollback

- **First validation failure:** Verifier files specifics. Platform lead has the
  cheapest rollback in the system: fix the Bicep in the worktree, PR, re-dispatch —
  Bicep deployments are idempotent and converge in place. For structural mistakes
  (wrong SKU family, mis-provisioned ACA env), full reset is gate-free:
  `az group delete --name mls-rg-platform --yes`, then redeploy.
- **Key Vault caveat on delete-and-redeploy:** soft-delete means a same-name vault
  can block recreation; the Bicep uses recover-if-soft-deleted
  (`createMode: 'recover'` when a soft-deleted vault with the target name exists)
  [derived — required for the kill/rebuild loop to be repeatable; the plan is
  silent on soft-delete handling].
- **Second consecutive failure of L6 → G4.**

## Failure modes

1. **SQL never auto-pauses** (V6.4 `Online` persistently). Detection: V6.4;
   long-term, budget burn. Cause: a keep-alive connection (App Insights
   availability test, misconfigured health probe). Response: locate the client via
   SQL audit/connection telemetry, fix the probe interval or exclude the DB;
   auto-pause config itself is asserted by V6.1 so config drift is already excluded.
2. **Key Vault name collision with a soft-deleted vault.** Detection: deployment
   fails `ConflictError: Exist soft deleted vault with the same name`. Response:
   the recover-mode template path (see Rollback) — never `purge` reflexively; purge
   is irreversible and unnecessary once recover-mode is in place.
3. **Cost export never produces a file** (V6.3 still empty at +24 h). Detection:
   V6.3 re-check. Causes: export identity lacks storage Blob Data Contributor;
   export created disabled; storage firewall blocks the service. Response: check
   `az costmanagement export show` state + last-run status; fix in Bicep/script and
   re-run; re-arm the 24 h clock once at most before failing the criterion.
4. **ACA environment region capacity/quota rejection.** Detection: deployment error
   `InsufficientCapacity`/quota exceeded. Response: quota increase is a human/portal
   support path — escalate via Orchestrator; do not silently change
   `$AZURE_LOCATION` (allowed-locations policy from L2 constrains it, and a region
   move is a sponsor-visible decision).
5. **Function → lakehouse ingestion fails while the export side works.** Detection:
   blobs exist, `cost_daily` stays empty. Causes: capacity paused at Function run
   time (SQL endpoint write path unavailable), or schema drift in the export CSV.
   Response: the Function must queue/retry until the next resumed window [derived
   design note — ingestion must tolerate a paused capacity by design]; schema drift
   is fixed in the Function via PR.
