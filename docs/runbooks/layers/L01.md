## Purpose

Establish the control plane everything else deploys through: the public monorepo
`paulcfuqua/azure-devsecops` with naming module and tag taxonomy, the `infra-up.yml` /
`infra-down.yml` workflow skeletons with a working OIDC login job, the GitHub `demo`
environment holding tenant/subscription IDs as variables (never committed), secret
scanning + push protection, branch protection with required checks, and gitleaks in CI.
After L1, GitHub Actions can authenticate to the demo subscription as
`mls-github-deployer` with zero stored cloud secrets.

- Phase P Track G has already created the repo, branch protection, and GHAS settings;
  L1 confirms them and adds the Azure-facing pieces (environment variables, OIDC job).

## Deploy procedure

1. Populate the GitHub environment `demo` with variables (values from G0 outputs —
   these are variables, not secrets, per spec F5):

   ```
   gh api -X PUT repos/paulcfuqua/azure-devsecops/environments/demo
   gh variable set AZURE_TENANT_ID       --env demo --body <tenant GUID>
   gh variable set AZURE_SUBSCRIPTION_ID --env demo --body <subscription GUID>
   gh variable set AZURE_CLIENT_ID       --env demo --body <mls-github-deployer app ID>
   gh variable set FABRIC_CAPACITY_ID    --env demo --body <trial capacity ID>
   ```

   [derived] Variable names follow the `azure/login` OIDC convention
   (`AZURE_TENANT_ID`/`AZURE_CLIENT_ID`/`AZURE_SUBSCRIPTION_ID`); the master plan
   names only "tenant/sub IDs as variables".

2. Confirm GHAS toggles (set in Phase P Track G; re-assert idempotently):

   ```
   gh api -X PATCH repos/paulcfuqua/azure-devsecops \
     -f security_and_analysis[secret_scanning][status]=enabled \
     -f security_and_analysis[secret_scanning_push_protection][status]=enabled
   ```

3. Merge the L1 PR carrying `infra/bicep/naming.bicep` (company prefix `mls` set once),
   the tag taxonomy constants, `.github/workflows/infra-up.yml` and
   `infra-down.yml` skeletons (OIDC login job + layer-dispatch scaffolding), and the
   gitleaks CI job.

4. Exercise the OIDC path end to end:

   ```
   gh workflow run infra-up.yml --field layers=none --field mode=oidc-smoke
   ```

   [derived] `mode=oidc-smoke` input runs only the login job (`azure/login` with
   `client-id: ${{ vars.AZURE_CLIENT_ID }}` against environment `demo`, then
   `az account show`) and asserts the returned subscription ID equals
   `${{ vars.AZURE_SUBSCRIPTION_ID }}`. The master plan requires the assertion; the
   dispatch input name is a derivation.

5. Hand off to the Verifier: post the run URL and the L1 manifest (naming module +
   environment variable list) on the task list.

## Validation cycle

Run by the Verifier as `mls-verifier` via `verification/layer-01-audit.ps1`; report
committed to `verification/reports/L01-<date>.md`. The GitHub checks use the
Verifier's dedicated GitHub read token (spec F8), never the deployer's context.

### V1.1 — OIDC round-trip succeeds and lands in the demo subscription

- **Criterion (master plan):** Actions run using OIDC succeeds (`az account show`
  inside the runner matches the demo sub).
- **Query:**

  ```
  gh run list --workflow infra-up.yml --limit 1 --json databaseId,conclusion
  gh api repos/paulcfuqua/azure-devsecops/actions/runs/<databaseId>/jobs \
    --jq '.jobs[] | select(.name=="oidc-login") | .conclusion'
  ```

  The login job's "Assert subscription" step fails the run if `az account show
  --query id -o tsv` differs from `vars.AZURE_SUBSCRIPTION_ID`, so run conclusion is
  the independent signal.
- **Expected:** run `conclusion == "success"`, job `oidc-login` `conclusion ==
  "success"`.
- **Retry/propagation:** federated-credential propagation can lag a few minutes after
  G0; on `AADSTS70021`/`AADSTS700213` re-dispatch once after 10 min, within the
  standard 30-minute bounded retry window.

### V1.2 — Secret scanning + push protection enabled

- **Criterion (master plan):** `gh api repos/{repo}` shows secret scanning + push
  protection enabled.
- **Query:**

  ```
  gh api repos/paulcfuqua/azure-devsecops \
    --jq '.security_and_analysis | {ss: .secret_scanning.status, pp: .secret_scanning_push_protection.status}'
  ```

- **Expected:** `{"ss":"enabled","pp":"enabled"}`.
- **Retry/propagation:** none — settings are read-your-writes; a single query.

### V1.3 — No committed IDs (grep audit)

- **Criterion (master plan):** no committed IDs (grep audit).
- **Query:** against a fresh clone of `main`:

  ```
  git grep -iE "$env:AZURE_TENANT_ID|$env:AZURE_SUBSCRIPTION_ID|$env:FABRIC_CAPACITY_ID"
  git grep -iE '[0-9a-f]{8}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{12}' -- ':!docs' ':!*.lock'
  ```

  (first command: the three real GUIDs, values injected from the Verifier's own
  environment context, never from the repo; second: generic GUID sweep with a
  reviewed allowlist for library-internal GUIDs).
- **Expected:** first command: zero matches (exit code 1). Second: matches only on
  the committed allowlist (e.g. label GUIDs recorded by L4, which are not secrets and
  are required audit evidence).
- **Retry/propagation:** none.

### V1.4 — Federated credential subject matches the repo

- **Criterion (master plan):** federated credential subject matches
  `repo:<owner>/<repo>`.
- **Query (Graph, read-only via `Directory.Read.All`):**

  ```powershell
  $app = Get-MgApplication -Filter "displayName eq 'mls-github-deployer'"
  Get-MgApplicationFederatedIdentityCredential -ApplicationId $app.Id |
    Select-Object Name, Issuer, Subject
  ```

- **Expected:** `Issuer == https://token.actions.githubusercontent.com`; `Subject ==
  repo:paulcfuqua/azure-devsecops:environment:demo`. [derived] The environment-scoped
  subject is the most conservative binding satisfying the plan's
  `repo:<owner>/<repo>` requirement — it additionally pins deploys to the `demo`
  environment's protection rules.
- **Retry/propagation:** Graph reads of the app registration may lag its creation by
  up to 30 minutes; standard bounded retry, poll every 5 minutes.

## Teardown

- **Standard cycle:** none. The repo persists — it IS the product (master plan L1).
  `down.ps1` does not touch GitHub.
- **Gate class:** the only destructive operation touching L1 artifacts is removal of
  the OIDC federation on `mls-github-deployer`, which is **G3** (tenant-level,
  per-occurrence approval) and lives with the G3 full-tenant teardown variant in
  `docs/runbooks/kill-rebuild.md`.

## Rollback

- **First validation failure:** Verifier commits the FAIL report with criterion,
  exact query, observed vs expected. Platform lead fixes in its worktree (all L1
  operations are idempotent: environment PUT, variable set, GHAS PATCH, workflow
  re-dispatch) and requests re-audit. Nothing needs deleting; there is no partial
  cloud state at L1.
- **If the OIDC assertion failed** because the federated credential is wrong, the fix
  is a G0-adjacent action: the human re-runs `scripts/bootstrap/01-root-oidc.ps1`
  (idempotent) under their own login — agents never modify the root federation.
- **Second consecutive failure of L1 → G4:** Orchestrator escalates to the human with
  both FAIL reports. Do not iterate a third time without human input.

## Failure modes

1. **AADSTS700213 / subject mismatch on `azure/login`.** Detection: login job fails
   with an AADSTS error naming the presented subject claim. Response: compare the
   claim in the error against the federated credential subject (V1.4 query); correct
   via re-run of `01-root-oidc.ps1` (human). Do not "fix" by widening the subject to
   branch-wildcards — keep the environment binding.
2. **Environment variables missing or stale.** Detection: login job fails fast on the
   pre-flight step that asserts all four `demo` variables are non-empty. Response:
   re-run deploy step 1; values come from G0 outputs, never from memory.
3. **Push protection blocks a legitimate push** (false-positive pattern in test
   fixtures). Detection: push rejected with a secret-scanning block URL. Response:
   rewrite the fixture so it does not pattern-match a credential (never use the
   bypass flow for convenience — bypass is reserved for documented false positives
   and is itself audit-visible).
4. **gitleaks flags a historical commit.** Detection: gitleaks CI job fails on a
   commit already on `main`. Response: treat as a real incident — rotate whatever
   leaked (only possible candidate is `ANTHROPIC_API_KEY`; nothing else is secret),
   then scrub via history rewrite only with sponsor sign-off since the repo is
   public and shared.
5. **Branch protection drift** (required checks removed, force-push enabled).
   Detection: V-adjacent check in the audit script:
   `gh api repos/paulcfuqua/azure-devsecops/branches/main/protection`. Response:
   re-apply protection from the settings-as-code script in the L1 PR; investigate
   who/what changed it (audit log) before proceeding.
