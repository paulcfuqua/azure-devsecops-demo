## Purpose

Create the four-level sensitivity taxonomy — **Public / Internal / Confidential /
Export-Controlled** — via Security & Compliance PowerShell, and document the
auto-label policy for the lakehouse workspace `mls-operations` (applied where
licensing allows: auto-labeling is an E5/AIP-P2 feature, in scope during the trial
window). Labels are tenant-level objects that persist across every standard
kill/rebuild cycle; their GUIDs become fixed audit evidence recorded at first
creation.

## Preconditions

- G0 complete + G1b granted; L3 Verifier PASS.
- Orchestrator unblock for L4.
- **M365 E5 trial active** (g0-bootstrap § B): label creation via S&C PowerShell
  requires the Exchange-backed compliance portal — this is precisely why the dual
  trials are activated the same day the tenant switches on. The M365 E5 trial's
  30-day window means L4 should run early in the tenant's life; the labels persist
  after the trial lapses.
- Credentials: the S&C endpoint accepts app-only auth only for apps granted
  `Exchange.ManageAsApp` plus a compliance admin role. [derived]
  `01-root-oidc.ps1` grants `mls-github-deployer` `Exchange.ManageAsApp` with the
  Compliance Administrator role, and `mls-verifier` `Exchange.ManageAsApp` with the
  **View-Only Configuration** (read-only) role so `Get-Label` works for the audit;
  the master plan is silent on S&C auth plumbing, so this is the minimal-privilege
  derivation.
- Track C artifact merged: `infra/purview/labels.ps1` Pester-green,
  PSScriptAnalyzer-clean.

## Deploy procedure

1. Dispatch:

   ```
   gh workflow run layer-04-purview.yml
   ```

   [derived] Workflow name per the `layer-<nn>-*.yml` pattern. The workflow runs
   `infra/purview/labels.ps1` (ExchangeOnlineManagement /
   `Connect-IPPSSession`), which:
   - creates each of the 4 labels **if absent** (`Get-Label` first — existing labels
     are never recreated, preserving their GUIDs);
   - publishes the label policy scoping the labels to the demo users' groups;
   - records the resulting label GUIDs to
     `verification/reports/label-guids.json` via PR (first run only — thereafter the
     file is the fixed expectation the audit compares against).
2. The auto-label policy for `mls-operations` is **documented** in
   `infra/purview/auto-label-design.md` and applied by the same script where the
   AIP-P2 entitlement is present (checked at runtime); absence of the entitlement
   downgrades to documented-only with an explicit workflow warning, per spec F1's
   agreed degrade path.
3. Post run URL to the Verifier.

## Validation cycle

Run by the Verifier as `mls-verifier` via `verification/layer-04-audit.ps1`
(read-only S&C session). Report: `verification/reports/L04-<date>.md`.

### V4.1 — Four labels exist with expected GUIDs

- **Criterion (master plan):** `Get-Label` returns the 4 labels with expected GUIDs
  recorded to `verification/reports/`.
- **Query:**

  ```powershell
  Connect-IPPSSession -AppId $env:MLS_VERIFIER_APP_ID -Organization $env:TENANT_DOMAIN -CertificateThumbprint $env:MLS_VERIFIER_CERT
  Get-Label | Select-Object DisplayName, Guid |
    Where-Object DisplayName -in 'Public','Internal','Confidential','Export-Controlled'
  ```

- **Expected:** exactly 4 labels — `Public`, `Internal`, `Confidential`,
  `Export-Controlled`. **First L4 run:** GUIDs are captured and committed to
  `verification/reports/label-guids.json` (the "recorded to `verification/reports/`"
  half of the criterion). **Every subsequent run:** returned GUIDs must equal the
  recorded ones exactly — a changed GUID means a label was deleted and recreated,
  which only a G3 action could legitimately do.
- **Retry/propagation:** label replication across S&C endpoints can lag; standard
  30-minute bounded retry, poll every 5 minutes. (Downstream *client* replication
  can take up to 24 h but is not this criterion's scope.)

### V4.2 — Labels survive a kill/rebuild cycle

- **Criterion (master plan):** labels survive a kill/rebuild cycle (checked again at
  L11).
- **Query:** identical to V4.1, executed in two contexts: (a) at L4 sign-off to
  establish the baseline, and (b) re-executed by the L11 audit immediately after
  `down.ps1` and again after `up.ps1` — L11's "tenant objects intact" criterion
  (V11.2) invokes this check by reference; this playbook owns the criterion, L11
  owns the re-execution schedule.
- **Expected:** same 4 labels, same GUIDs as `label-guids.json`, at every
  checkpoint. Any delta post-`down.ps1` means the teardown path touched tenant
  objects — a critical defect in `down.ps1`, stop-the-line.
- **Retry/propagation:** none beyond V4.1's window — persistence is binary.

## Teardown

- **Standard kill/rebuild cycle:** **labels persist — the cycle must not touch
  them** (brief principle 2 and spec F6). `infra/purview/labels.ps1` replayed by
  `up.ps1` no-ops via its create-if-absent guard.
- **Full teardown:** G3-gated script `infra/purview/teardown.ps1` [derived name —
  master plan says "G3-gated script" without a path; placed beside the apply script
  per repo convention] removes the label policy then the labels. **Gate class: G3.**
  Note the honest consequence: recreated labels get new GUIDs;
  `label-guids.json` must be re-baselined in the same PR that records the G3
  approval.

## Rollback

- **First validation failure:** Verifier files specifics. Lead fixes
  `infra/purview/labels.ps1` or the label policy via PR and re-dispatches; the
  create-if-absent design means re-runs converge without deleting anything.
  **Never delete a label to fix it** — deletion is G3 and orphans the recorded
  GUIDs; label properties (tooltip, policy scope) are all modifiable in place.
- **If V4.1 fails on GUID mismatch:** do not "fix" by re-baselining the JSON — a
  GUID change without a recorded G3 approval is an incident. Escalate to the
  Orchestrator with the S&C audit log (`Search-UnifiedAuditLog -Operations
  DeleteLabel`) before any remediation.
- **Second consecutive failure of L4 → G4.**

## Failure modes

1. **S&C session fails to establish** (`Connect-IPPSSession` errors — tenant not
   Exchange-backed, trial not active, or role missing). Detection: workflow fails at
   connect. Response: verify M365 E5 trial state (human, admin center); verify the
   `Exchange.ManageAsApp` grant + role assignment from G0. This is the spec F1
   licensing risk landing — degrade path (documented-design-only) requires sponsor
   sign-off, never a silent skip.
2. **Label GUID drift between rebuilds.** Detection: V4.1 GUID mismatch. Response:
   treat as incident (see Rollback); root causes seen in the wild: someone ran a G3
   teardown without re-baselining, or a portal-side manual deletion (violates
   principle 1 — zero manual portal actions after G0).
3. **M365 E5 trial lapse (day 30) before first L4 run.** Detection:
   `New-Label` rejected for licensing. Response: labels already created persist and
   remain manageable; if L4 never ran, sponsor decision — re-trial path/paid, or the
   spec F1 descope. Schedule L4 in the first week of tenant life to avoid this.
4. **Auto-label policy application fails (AIP P2 entitlement absent).** Detection:
   runtime entitlement check in `labels.ps1` logs the downgrade warning. Response:
   accepted degrade per spec F1 — auto-labeling stays documented-only; the L4 audit
   does not fail on this (it is not a master-plan criterion), but the workflow
   warning is copied into the audit report for the record.
5. **Label policy scoping error** (labels published to no one, invisible in client
   apps). Detection: not caught by V4.1 (labels exist regardless); caught by the
   audit's supplementary policy check `Get-LabelPolicy | Select -Expand
   ExchangeLocation`. Response: fix policy scope in `labels.ps1`, re-apply.
