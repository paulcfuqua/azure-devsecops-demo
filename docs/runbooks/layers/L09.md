# L9 Playbook — DevSecOps Chain

| | |
|---|---|
| **Layer** | L9 |
| **Lead** | DevSecOps |
| **Master plan** | `docs/superpowers/plans/2026-08-22-g1-master-plan.md` § L9 |
| **Teardown gate class** | Gate-free — config-as-code; Defender left `Off`; nothing billable persists |
| **Cost delta** | $0 idle; Defender ~$0.29/day only while toggled on (**G2 each enable**) |

## Purpose

Activate the full security chain: CodeQL (JS/TS + Python), Dependabot configuration,
secret scanning confirmation, SPDX SBOMs (Syft) attached to releases, a Trivy gate
that fails CI on CRITICAL, ZAP baseline scans against the reachable public surface, Defender
`Containers` plan toggle scripts (G2 on each enable), and the control-tower Dev/Sec
feeds wired to the GitHub Security and Defender APIs. After L9, the pipeline the
self-healing showpiece rides on is fully armed.

## Preconditions

> **Do not run L9 while an L7 audit is in flight.** L9's ZAP baseline scans the
> launch-ops app - since F144 it reads that host from the LIVE ingress rather than the
> stored `vars.STAGING_URL` - and L7's **V7.5 waits for that same app
> to scale back to zero**. Sustained ZAP traffic keeps a replica warm, so V7.5 spends its
> full 30-minute deadline watching a scale-in that cannot happen and then fails - an hour
> lost to two correct workflows disagreeing about whether the app should be idle. Run them
> in sequence, or point `zap_target_url` at an app no L7 criterion measures.


- G0 complete + G1b granted; L7 Verifier PASS (a staging URL must exist for ZAP;
  control-tower must be deployed to receive feeds). L8 PASS per strict layer order.
- Orchestrator unblock for L9.
- **G2 approval for the Defender toggle test** — V9.5 requires an enable→disable
  round-trip; the enable raises the run-rate (~$0.29/day prorated, duration:
  minutes for the test). Filed by the Orchestrator before the workflow runs.
- Credentials: `mls-github-deployer` for `az security pricing` writes and release
  uploads; `mls-verifier` GitHub read token for GHAS/API checks, Reader for
  Defender state.
- Track G artifacts live since Phase P: `codeql.yml`, Dependabot config, secret
  scanning already enabled on the repo; Track C-standard local validation done for
  `scripts/defender/toggle-containers-plan.ps1` [derived — the defender scripts sit

## Deploy procedure

1. Merge the L9 PR carrying/confirming:
   - `.github/workflows/codeql.yml` (matrix: `javascript-typescript`, `python`);
   - `.github/dependabot.yml` (npm, pip, github-actions ecosystems);
   - `.github/workflows/sbom.yml` — Syft generates SPDX JSON per app, attached to
     the release created on tagged builds;
   - Trivy gate already present in per-app CI (L7) — L9 adds the **negative test**
     fixture: a workflow job that builds a deliberately CRITICAL-pinned image and
     asserts CI fails, then rebuilds with the pin fixed and asserts pass;
   - `.github/workflows/zap.yml` — ZAP baseline against the `launch-ops` staging
     FQDN, report uploaded as artifact;
   - `scripts/defender/toggle-containers-plan.ps1` (`-Enable` / `-Disable`).
2. Execute the layer sequence:

   ```
   gh workflow run layer-09-devsecops.yml
   ```

   [derived] Workflow name per the `layer-<nn>-*.yml` pattern. **It exists**
   (`.github/workflows/layer-09-devsecops.yml`, 2026-08-24) and orchestrates: the GHAS
   state report (read-only `gh api`), the Trivy negative test as the two jobs
   `trivy-negative-fail` / `trivy-negative-pass` — those names are contract, V9.2 selects
   on them — an SBOM release build (it creates the release, then **calls** `sbom.yml` so
   the SPDX documents land as release *assets*, which is what V9.3 reads), a ZAP baseline
   run (`zap.yml`, also **called**, so its artifact belongs to this run id), and the
   Defender toggle round-trip (`-Enable`, state assert, `-Disable`) under the filed G2,
   with the disable in an `always()` step.

   It also **produces the three audit inputs that used to be hand-set demo variables**:
   `-LayerRunId` and `-ZapRunId` are its own `github.run_id` (a reusable workflow called
   with `uses:` runs inside the caller's run), and `-ReleaseTag` is the tag its `release`
   job created. `MLS_L9_RUN_ID` / `MLS_L9_RELEASE_TAG` / `MLS_L9_ZAP_RUN_ID` survive only
   as overrides for re-verifying an older run.

   Dispatch inputs: `release_tag` (empty ⇒ `l9-<run number>` as a prerelease),
   `zap_target_url` (empty ⇒ the launch-ops ingress FQDN read from Azure; F144 -
   `vars.STAGING_URL` is now only a last resort for a checkout with no Azure credentials,
   and a stored value that disagrees with the live one is reported as stale),
   `defender_toggle` (default `true`; turning it off leaves V9.5 unprovable - it asserts a
   paired Standard-then-Free write in the run's own window, so an end state of `Free`
   without the round-trip is a FAIL, not a pass) and `dry_run`.

   **The Defender round-trip restores what it found (F31).** The job reads the plan's
   incoming `pricingTier` first and **refuses to run** if it is anything but `Free`:
   it will not disable a Defender for Containers plan this estate did not enable.
   Re-run with `defender_toggle: false` on a subscription that already has the plan
   on. This is also why the demo belongs in a dedicated, empty subscription --- see
   `README.md` and `docs/runbooks/g0-bootstrap.md`.
3. Wire control-tower Dev/Sec feeds: config PR pointing the tabs at the GitHub
   Security API (Dependabot/CodeQL alert counts) and Defender secure-score API —
   consumed via the existing app deploy path.
4. Post run URLs + artifacts to the Verifier.

## Validation cycle

Run by the Verifier as `mls-verifier` via `verification/layer-09-audit.ps1`. Report:
`verification/reports/L09-<date>.md`.

### V9.1 — All GHAS features enabled

> **The Verifier cannot fully observe this criterion, and that is recorded rather than
> papered over (F103).** `security_and_analysis` on the repository object and
> `GET /repos/{owner}/{repo}/vulnerability-alerts` are both **admin-only**. The Verifier's
> token is read-only by contract, so GitHub omits the block and refuses the endpoint.
>
> V9.1 used to read that absence as *disabled* and announce that secret scanning, push
> protection and Dependabot alerts were **off** on a repository where all three were
> enabled. Unobservable is now its own reported state: the criterion still FAILS, because
> "nobody could check" is not a sign-off, but it never again claims a control is missing
> when it simply could not look.
>
> **Resolved 2026-09-01 without granting admin, and the reasoning is the point.**
>
> Granting `MLS_VERIFIER_GH_TOKEN` repository admin was the obvious fix and the wrong one.
> The Verifier's independence is not a feature of this demo, it is the product: a reader
> who sees the auditor holding admin on the repository it audits is right to discount every
> criterion after it. And "both calls are GET, so it stays read-only" is a promise about our
> behaviour, not a property of the credential - GitHub's `admin` could change branch
> protection or disable scanning outright. That substitution is exactly what CLAUDE.md
> warns against: assert the capability, not the artefact.
>
> What the endpoints actually allow decided it:
>
> | Control | Requirement | Read-only auditor? |
> |---|---|---|
> | CodeQL analyses | unprivileged | yes |
> | Dependabot alerts | `security_events`, or `public_repo` on a public repo | **yes, no admin** |
> | `security_and_analysis` | admin | no |
> | Secret scanning alerts | admin, **and 404s on public repos regardless** | no, by GitHub's design |
>
> So **Dependabot is recovered in a stronger form**: rather than reading a status field,
> V9.1 lists the alerts. A `200` proves the feature is live, because a repository with
> Dependabot alerts disabled cannot serve them. That is capability evidence, not
> configuration evidence, and it is better than what it replaces.
>
> **Secret scanning and push protection are NOT CLAIMED here**, and the report says so in
> those words. They are admin-only, unobservable to any read-only caller on a public
> repository, enabled by default on public repositories, and not something this estate
> configures - V9.1 was taking credit for a platform default it neither set nor could see.
> They are evidenced at G0 by a human who genuinely holds admin.
>
> The criterion's title and Expected changed with it. A check that quietly narrows what it
> tests while keeping its old name is a slower version of the same lie.


- **Criterion (master plan):** GitHub API shows all GHAS features enabled.
- **Query:**

  ```
  gh api repos/paulcfuqua/azure-devsecops-demo \
    --jq '.security_and_analysis'
  gh api repos/paulcfuqua/azure-devsecops-demo/vulnerability-alerts -i   # Dependabot alerts: expect 204
  gh api repos/paulcfuqua/azure-devsecops-demo/code-scanning/analyses --jq '.[0].tool.name'
  ```

- **Expected:** `secret_scanning.status == "enabled"`,
  `secret_scanning_push_protection.status == "enabled"`; vulnerability-alerts
  endpoint returns 204 (Dependabot alerts on); at least one completed CodeQL
  analysis with `tool.name == "CodeQL"` for each of the two language matrices.
- **Retry/propagation:** first CodeQL analysis must finish — allow one workflow
  runtime (~10–20 min) inside the standard 30-minute window.

### V9.2 — Seeded CRITICAL image fails CI, passes after pin

- **Criterion (master plan):** a seeded CRITICAL image fails CI (negative test)
  then passes after pin.
- **Query:**

  ```
  gh api repos/paulcfuqua/azure-devsecops-demo/actions/runs/<layer09-runId>/jobs \
    --jq '.jobs[] | select(.name | startswith("trivy-negative")) | {name, conclusion}'
  ```

- **Expected:** job `trivy-negative-fail` concludes `success` **because** its inner
  Trivy step exited non-zero on the seeded CRITICAL (the job asserts the failure);
  job `trivy-negative-pass` concludes `success` scanning the pinned rebuild. Both
  halves present — a gate that never fails is untested.
- **Retry/propagation:** none — the negative test is self-contained; a new
  overnight CVE can only add findings, not remove the seeded one.

### V9.3 — SBOM artifact present and SPDX-valid

- **Criterion (master plan):** SBOM artifact present + SPDX-valid.
- **Query:**

  ```
  gh release view <tag> --json assets --jq '.assets[].name'
  gh release download <tag> -p '*.spdx.json' -D $env:TEMP/sbom
  # validate with the pinned SPDX tooling from the sbom workflow:
  pyspdxtools -i $env:TEMP/sbom/<file>.spdx.json
  ```

- **Expected:** one `*.spdx.json` per app attached to the release; validator exits
  0 (well-formed SPDX with document namespace, creation info, and package list
  non-empty).
- **Retry/propagation:** none — artifacts are immutable once attached.

### V9.4 — ZAP report exists with 0 High

- **Criterion (master plan):** ZAP report artifact exists with 0 High.
- **Query:**

  ```
  gh run download <zap-runId> -n zap-baseline-report -D $env:TEMP/zap
  # parse the JSON report:
  (Get-Content $env:TEMP/zap/report.json | ConvertFrom-Json).site.alerts |
    Where-Object riskdesc -like 'High*'
  ```

- **Expected:** report artifact present for the staging URL; zero alerts at risk
  level High. (Medium/Low/Informational findings are recorded in the report and
  triaged as normal backlog — only High fails the criterion.)
- **Retry/propagation:** if ZAP could not reach staging (cold-start timeout), one
  re-run; an unreachable target produces an empty report, which is a FAIL, not a
  pass.

### V9.5 — Defender plan toggles on→off leaving state `Off`

- **Criterion (master plan):** Defender plan toggles on→off leaving state `Off`.
- **Query:**

  ```
  az security pricing show --name Containers --query "{tier:pricingTier}"
  az monitor activity-log list --offset 6h \
    --query "[?contains(operationName.value,'Microsoft.Security/pricings')].{op:operationName.value, status:status.value, time:eventTimestamp}"
  ```

- **Expected:** current `pricingTier == "Free"` (the ARM representation of the
  plan's `Off` state), **and** the Activity Log shows the paired write events from
  the toggle round-trip (Standard then Free) within the layer window — proving the
  toggle exercised, not merely never-enabled. Foundational CSPM stays on (free,
  spec F10) — that plan is out of scope for this check.
- **Retry/propagation:** pricing state is immediate; single check, one retry at
  +5 minutes for Activity Log lag.

## Teardown

- **Standard kill/rebuild cycle:** nothing to tear down — the chain is
  config-as-code in the repo (persists by design), Defender is left `Off`
  (verified by V9.5), and nothing billable persists. `down.ps1` does not touch
  GitHub settings. **Gate class: gate-free / not applicable.**
- Defender must read `Free` at every cycle close; any enable is a fresh G2, and
  disabling is always allowed without a gate (spend decrease).

## Rollback

- **First validation failure:** Verifier files specifics. DevSecOps lead fixes
  config via PR and re-runs the relevant workflow — all L9 state is either repo
  config or a subscription toggle, both idempotent.
- **If V9.5 finds `pricingTier == "Standard"`** (Defender left on): disable
  immediately via `toggle-containers-plan.ps1 -Disable` — no gate for a spend
  decrease — then root-cause why the layer's disable step failed. If spend already
  deviated from the envelope, that is a cost-anomaly G4 independent of the retry
  count.
- ZAP High findings roll back nothing: fix the finding in the app (or its config)
  via the normal PR path — the criterion exists to catch real issues, not to be
  waived.
- **Second consecutive failure of L9 → G4.**

## Failure modes

1. **CodeQL default-setup conflict** (org/repo default setup blocks the advanced
   `codeql.yml` workflow: "CodeQL analyses from advanced configurations cannot be
   processed"). Detection: codeql.yml run fails with the conflict error. Response:
   disable default setup via
   `gh api -X PATCH repos/.../code-scanning/default-setup -f state=not-configured`
   (settings-as-code), re-run.
2. **Defender left enabled** (cost leak). Detection: V9.5; budget alert at 50% if
   missed. Response: immediate disable (see Rollback); Verifier's every-layer-close
   capacity/cost check is the backstop.
3. **ZAP flags High on a framework false positive** (e.g., missing header on a
   platform-served route). Detection: V9.4 parse. Response: fix genuinely where
   possible (headers are real hardening); only rule-tune via committed
   `zap.conf` with justification in the PR — never by editing the report or
   criterion.
4. **SBOM validator breaks on tool upgrade** (Syft output schema shifts against the
   pinned validator). Detection: V9.3 validation error with unchanged app code.
   Response: pin both Syft and validator versions in `sbom.yml`; upgrade both
   deliberately in one PR.
5. **Dependabot config valid but silent** (no alerts ever raised — wrong directory
   globs, ecosystem typo). Detection: V9.1 passes (feature on) but L10
   preconditions later find zero alerts on known-vulnerable pins. Response: fix
   `.github/dependabot.yml` paths to cover `apps/vuln-lab/`; this failure mode is
   the reason L10 pre-checks alert presence before its own chain run.
