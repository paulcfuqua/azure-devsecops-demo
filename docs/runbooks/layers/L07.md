| | |
|---|---|
| **Layer** | L7 |

| **Master plan** | `docs/superpowers/plans/2026-08-22-g1-master-plan.md` § L7 |

## Purpose

Ship the user-facing surface: the `apps/shared/spec-renderer` library (JSON schema +
8–10 Fluent UI v9 components + Storybook + unit tests), the `launch-ops` app
(SQL-backed CRUD + lakehouse-backed analytics views), the `control-tower` app
(Dev/Sec/Ops tabs on live APIs), OpenTelemetry wiring into App Insights, and
path-filtered CI per app (build → test → Trivy image scan → deploy to ACA via OIDC).
After L7 the demo has two browsable apps scaling 0→N→0 on the L6 platform.

**Both of them require an Entra sign-in (F25, 2026-08-28).** `launch-ops` and
`control-tower` are behind Container Apps Easy Auth, exactly like the compliance board.
The reason is their own nginx: both blind-proxy `location /api/` to `data-api`, whose
identity holds **Security Reader at subscription scope**, so an open dashboard was an
open read of the adopter's live Defender for Cloud posture — F1 had made `data-api`
internal and recorded "both frontends already proxy `/api/` server-side" as the reason
that sufficed, which was the bypass rather than the fix. `/healthz` is the single path
excluded from authentication, so V7.1 below still works unchanged.

**Easy Auth configures itself; there is nothing to set up first (F36, 2026-08-28).**
This workflow used to refuse to run until `MLS_LAUNCH_OPS_CLIENT_ID`,
`MLS_CONTROL_TOWER_CLIENT_ID` and `MLS_COMPLIANCE_CLIENT_ID` were all hand-set, which
made a secure estate an undeployable one. Two steps replace that refusal:

1. **Before the deployment** — "Resolve the Easy Auth client IDs from their Entra app
   registrations": for each dashboard it honours the matching variable if you set one,
   and otherwise looks the registration up by the display name
   `infra/entra/manifest.json` declares for that `appKey` (L3 created it, as this same
   identity, which holds `Application.ReadWrite.OwnedBy`). A registration it cannot find
   is **not** an error — that app deploys with **internal ingress and no `authConfig`**,
   because `main.bicep` makes `ingressExternal` the same expression as "is Easy Auth
   configured", and the run emits a `::warning` plus a step-summary table naming each app,
   its state, and the one command that fixes it (`gh workflow run layer-03-entra.yml`).
   An `az` failure, or two registrations with the same display name, **is** an error and
   stops the deploy.
2. **After the deployment** — "Register each dashboard's Easy Auth redirect URI now that
   its FQDN exists": adds `https://<that app's ingress FQDN>/.auth/login/aad/callback` to
   each registration, **merged** into the URIs already there (`--web-redirect-uris`
   replaces the whole list, so overwriting would silently drop a working one). It is
   idempotent, and carries `continue-on-error` in the same position as the F20 and F24
   remediation steps — after the V7.1 manifest is written and uploaded — for the same
   reason: idempotent remediation must never cost a working deployment its Verifier
   sign-off. A failure is reported to the run summary rather than swallowed.

The three variables therefore survive only as **overrides**, for an adopter who wants to
bring their own app registrations.

**A fifth container app deploys from this template and is not L7's to validate.** The
compliance board (`mls-compliance-demo-ca`) is provisioned by the same
`infra/bicep/apps/main.bicep` and the same `layer-07-apps.yml` as the four above, but it
belongs to **L12** — see [`L12.md`](L12.md). It is deliberately excluded from this
template's `containerAppNames` output. None of L7's five criteria cover it, and none
should.

Since the 2026-08-24 amendment the control tower also carries a fourth tab, **Ask**,
which is showpiece #1's surface: a Direct Line embed of the L8 Copilot Studio agent. It
ships here **dark** — the tab and its backend token route are built and tested at L7,
but `ASK_TAB_ENABLED` is off and the Direct Line secret reference is empty until L8
publishes an agent. There is no separate copilot app any more: `copilot-svc` is retired,
and what replaces it on the compute side is `apps/mcp-tools`, deployed at L8, not here.
None of L7's five Verify criteria change — the Ask tab is deliberately not part of any
of them, so a dark tab cannot fail this layer.

## Deploy procedure

1. Merge the L7 PR(s); path-filtered CI does the deploys — there is no separate
   layer workflow for apps:

   ```
   .github/workflows/app-launch-ops-ci.yml      # paths: apps/launch-ops/**, apps/shared/**
   .github/workflows/app-control-tower-ci.yml   # paths: apps/control-tower/**, apps/shared/**
   ```

   Each runs build → unit tests → container build → Trivy scan (fail on CRITICAL)
   → `azure/login` (OIDC, environment `demo`) → `az containerapp update` with the
   image and `minReplicas 0`.
2. For a full-environment replay (`infra-up.yml`), the same two workflows are
   invoked via `workflow_call` after L6 completes [derived — the master plan names
   per-app CI as the deploy path; the call wiring is the derivation].
3. The deploy step stamps the container image's content hash into a response header
   / `/healthz` marker [derived mechanism] so V7.1 can bind "endpoint is up" to
   "endpoint serves the audited build".
4. Confirm the Ask tab deployed **dark**: `ASK_TAB_ENABLED` unset/false in the container
   app's configuration, and the tab either hidden or rendering its "not yet available"
   state. L8 step 5 flips this flag; nothing about it is a redeploy. [derived flag name —
   the master plan does not name the control tower's configuration keys.]
5. Open the **canary PR** for V7.4: a trivial whitespace-level change under each
   app's path, opened by the lead (the Verifier never writes to the repo), left for
   the audit to observe, then closed without merge.
6. Post run URLs + image digests to the Verifier.

## Validation cycle

Run by the Verifier as `mls-verifier` via `verification/layer-07-audit.ps1`. Report:
`verification/reports/L07-<date>.md`.

### V7.1 — Public endpoints return 200 with correct content hash markers

- **Criterion (master plan):** public endpoints return 200 with correct content
  hash markers.
- **What "public" means since F25:** the apps are externally reachable but
  Easy-Auth gated, and `/healthz` — the only path this criterion touches — is the
  only path in `globalValidation.excludedPaths`. An unauthenticated GET of `/` or of
  anything under `/api/` now redirects to a login page, which is the point. If this
  criterion ever starts failing with a 302, check that `easyAuthExcludedPaths` in
  `infra/bicep/apps/main.bicep` still contains `/healthz` — and do not "fix" it by
  adding `/api/`.
- **Query:**

  ```powershell
  foreach ($app in 'launch-ops','control-tower') {
    $fqdn = az containerapp show -g mls-rg-apps -n (naming $app) --query properties.configuration.ingress.fqdn -o tsv
    Invoke-WebRequest "https://$fqdn/healthz" -MaximumRetryCount 3
  }
  ```

- **Expected:** HTTP 200 from both apps; the health payload's content-hash marker
  equals the image digest recorded in the deploy run (binding endpoint to build).
  First request may cold-start from 0 replicas — allow up to 60 s response time
  before retry counts as failure.
- **Retry/propagation:** ingress DNS + cold start; retry 3× over 5 minutes, within
  the standard 30-minute window.

### V7.2 — Renderer schema validation passes on golden specs

- **Criterion (master plan):** renderer schema validation passes on golden specs.
- **Query:**

  ```
  npm --prefix apps/shared/spec-renderer run validate:golden
  ```

  (ajv validation of every fixture under
  `apps/shared/spec-renderer/golden/` against the component-spec JSON Schema —
  local execution; the Verifier runs it from the audited commit, trusting the repo
  state, not a teammate's claim.)
- **Expected:** exit 0; every golden spec valid; the fixture set covers all ~9
  component types (bar/line/area chart, stat card, KPI row, data table, timeline,
  donut, markdown block).
- **Retry/propagation:** none — deterministic local check.

### V7.3 — OTel spans visible in App Insights

- **Criterion (master plan):** OTel spans from a synthetic request visible in App
  Insights via KQL.
- **Query:** issue one **authenticated** synthetic request per app, each carrying its
  own W3C trace id, then look those trace ids up in App Insights:

  ```
  az account get-access-token --resource <easy-auth-client-id>          # per app
  GET https://<fqdn>/api/tables/launches \
      -H 'Authorization: Bearer <token>' \
      -H 'traceparent: 00-<traceId>-<spanId>-01'

  az monitor log-analytics query --workspace <lawCustomerId> --analytics-query \
    "AppRequests | where OperationId in ('<traceId>', ...) | project TimeGenerated, AppRoleName, OperationId, ResultCode, Name" \
    --timespan PT1H
  ```

- **Expected:** ≥ 1 `AppRequests` row per app whose `OperationId` is that app's probe
  trace id. `AppRoleName` on those rows is **`data-api`**, not the frontend: the
  dashboards are nginx serving a static bundle and emit nothing server-side, so the
  instrumented app in the chain is the one that produces the span. Per-frontend
  attribution comes from the trace id, never from `AppRoleName`.
- **Three earlier shapes of this criterion were wrong, each for its own reason** — an
  anonymous probe (F89), `/healthz` as the probe path (F89), and a marker in the URL
  matched against `Url` (F97). The section below records what each cost and why.
- **Retry/propagation:** App Insights ingestion latency is typically 2–10 minutes, so
  V7.3 declares `-RetryWindowMinutes 15`, polled every 20 s. V7.1 declares 10 and V7.4
  declares 15 for the canary PR's CI run (F59).

### V7.4 — Per-app CI green on a canary PR

- **Criterion (master plan):** per-app CI green on a canary PR.
- **Query:**

  ```
  gh pr checks <canary-pr-number> --json name,state
  gh api repos/paulcfuqua/azure-devsecops-demo/commits/<canary-sha>/check-runs \
    --jq '.check_runs[] | {name, conclusion}'
  ```

- **Expected:** every required check on the canary PR concludes `success` — for
  both app pipelines when the canary touches `apps/shared/**`, and **only** the
  matching app's pipeline when it touches a single app path (path-filter working is
  part of the criterion's intent). Canary PR is then closed unmerged by the lead.
- **Retry/propagation:** none beyond CI runtime; a flaky-check rerun is allowed
  once, recorded in the report.

### V7.5 — Replicas scale 0→N→0

- **Criterion (master plan):** replicas scale 0→N→0.
- **Query:** three-phase observation per app:

  ```
  az containerapp replica list -g mls-rg-apps -n <app> --query "length(@)"   # phase 1: expect 0
  # phase 2: drive load — 20 concurrent GETs for 60 s, then:
  az containerapp replica list ... # expect >= 1
  # phase 3: after idle (scale-in window + margin):
  az containerapp replica list ... # expect 0
  ```

- **Expected:** 0 before load; ≥ 1 under load; back to 0 after the idle window.
  [derived] Phase-3 wait: ACA scales in within ~5 minutes of idle plus the
  configured cooldown — the audit waits 15 minutes before the phase-3 read; a
  nonzero count at +30 minutes is a FAIL (idle-cost model broken).
- **Retry/propagation:** phase-3 only, as above; phases 1–2 are immediate.

## Teardown

- **Standard kill/rebuild cycle:** `az group delete --name mls-rg-apps --yes` via
  `down.ps1`. **Gate class: gate-free** (RG-scoped demo resources). Container
  images live in the registry inside the demo RGs and are rebuilt by CI on replay —
  nothing app-side survives the cycle except the repo itself.
- Nothing G3 in this layer: app registrations used by the apps were created at L3
  and persist there (their teardown is L3's G3 concern, not L7's). The one Entra
  **write** this layer makes is the F36 redirect-URI merge, which only ever ADDS a
  reply URL to a registration L3 already owns — it creates and deletes nothing, so a
  kill/rebuild simply adds the new FQDN's callback alongside the old one. Stale
  callbacks pointing at deleted container apps are inert (they authenticate nothing);
  pruning them is an L3 concern, done by hand.

## Rollback

- **First validation failure:** Verifier files specifics. The joint leads fix in
  worktrees and let path-filtered CI redeploy — every deploy is
  image-replacement, inherently idempotent. For a corrupted environment-level state
  the gate-free reset is `az group delete --name mls-rg-apps` + replay of both CI
  workflows.
- Failures in V7.2 (golden specs) roll back **in the repo only** — no cloud state
  involved; fix the schema/fixtures via PR, re-run the audit.
- **Second consecutive failure of L7 → G4.**

## Failure modes

1. **Cold-start timeout read as downtime** (V7.1 fails on first-ever request).
   Detection: 200 arrives on manual retry after ~30–60 s. Response: none needed —
   the audit's retry policy absorbs it; if cold start exceeds 60 s consistently,
   investigate image size/startup path (that latency will also poison the demo's
   feel).
2. **Trivy gate blocks deploy on a CVE published overnight** (unrelated to the
   change). Detection: CI fails at the scan step naming a base-image CVE. Response:
   bump/pin the base image via PR (the DevSecOps chain exists to make this loud);
   never suppress the gate to ship a layer.
3. **OTel spans missing** (V7.3 empty). Causes: connection string not injected
   (Bicep app config), sampling set to 0, or ingestion lag. Detection: V7.3
   timeout after 30 minutes. Response: check app env vars against the L6 manifest;
   fix wiring via PR; ingestion lag alone is covered by the retry window.
4. **Path filters misfire** (canary touching one app triggers both pipelines, or
   neither). Detection: V7.4's filter assertion. Response: fix `paths:` globs in
   the CI workflows; this is exactly the drift that turns "per-app CI" into
   "monolithic CI" silently.
5. **Replicas never return to 0** (V7.5 phase 3 fails). Causes: health probe
   traffic keeping the app warm, scale rule floor set to 1 by a template change.
   Detection: V7.5; long-term, idle cost creep. Response: check scale rules against
   the manifest (minReplicas must be 0), fix probe frequency; an intentional floor
   change would be a G2 question — as an unrequested drift it is simply a defect.

### Failure mode: the MCP container app will not provision

```
ContainerAppOperationError: Failed to provision revision for container app 'mls-mcp-demo-ca'.
Field 'configuration.secrets' is invalid: 'mcp-auth-token':
Unable to get value using Managed identity .../mls-mcp-demo-id
```

**The other five apps deploy fine; only this one fails.** `mls-mcp-demo-ca` is the single app
that resolves a secret from Key Vault at runtime - `infra/bicep/apps/main.bicep` declares
`mcp-auth-token` as a `keyVaultUrl` reference rather than a value, so the token never becomes
a deploy parameter, an env value, or anything in ARM history (hard rule 5). That design costs
one prerequisite: **the secret has to exist before L7 runs.** It is created by hand at
`docs/runbooks/g0-bootstrap.md` item 11, and item 11 cannot run until L6 has created the vault.

The error message is the same whether the identity lacks permission or the secret is absent,
which makes it slow to diagnose from the workflow log alone. **Ask the vault** - L6 wires Key
Vault diagnostics into Log Analytics, so the answer is one query away:

```kusto
AzureDiagnostics
| where ResourceProvider == "MICROSOFT.KEYVAULT"
| where OperationName has "Secret"
| project TimeGenerated, OperationName, httpStatusCode_d, identity_claim_oid_g, requestUri_s
| order by TimeGenerated desc
```

- **404** - authenticated and authorised, and the secret is not there. Run item 11.
- **403** - the identity cannot read it. Check it holds Key Vault Secrets User on the vault
  (`infra/bicep/apps/main.bicep` module `mcpKvGrant`), and allow for RBAC propagation.

That distinction settled this in one query on 2026-08-31 when neither the operator nor the
agent could read the vault directly (F87).

### Failure mode: the layer deploys, and serves none of the demo

Every container app reports `Succeeded`, every endpoint answers HTTP 200, and the payload
is the **Azure Container Apps "Welcome" page**:

```
$ curl https://mls-launch-ops-demo-ca.<region>.azurecontainerapps.io/healthz
<!DOCTYPE html> ... <title>Azure Container Apps - Welcome</title>
$ az containerapp show -g mls-rg-apps -n mls-launch-ops-demo-ca \
    --query "properties.template.containers[0].image" -o tsv
mcr.microsoft.com/azuredocs/containerapps-helloworld:latest
```

**The deploy took the placeholder path.** `image_tag` used to default to the empty string,
which `demo.bicepparam` reads as "keep the `containerapps-helloworld` placeholder", and the
five target ports defaulted independently to **80** — the placeholder's port, not the
**8080** every real app Dockerfile EXPOSEs. Two knobs that must agree, defaulting apart.

This is worth recognising by its signature rather than its cause, because the estate looks
healthy from every angle a deploy checks: provisioning state, replica count, ingress,
HTTP status. Only the *content* of the response gives it away — which is precisely why
V7.1 binds the endpoint to the image digest instead of passing on liveness. **Three
criteria failed on one fact:** V7.1 (no digest in the payload), V7.3 (no telemetry, because
a hello-world container emits none) and V7.5 (the scale profile of the wrong workload).
Read together they say "wrong image", not "three problems" (F88).

Fixed since 2026-08-31: `image_tag` defaults to `latest`, and the *same step* that resolves
the image derives the port from that decision, so the two cannot disagree. The placeholder
is still reachable — pass an empty `image_tag` deliberately — and now emits a `::warning`
saying the estate will serve none of the demo. This closes open item **P-1**.

**If you see the Welcome page**, do not debug ingress. Check the image first:

```bash
az containerapp list -g mls-rg-apps \
  --query "[].{app:name,image:properties.template.containers[0].image}" -o table
```

### Failure mode: V7.3 finds no telemetry, and App Insights is wired correctly

Symptom: `launch-ops rows=0; control-tower rows=0`, while `az containerapp show` proves the
connection string is present on every container and points at the one App Insights
component in the subscription. Querying it directly returns **zero rows in every table** -
`requests`, `pageViews`, `traces`, `dependencies` - over 24 hours.

**Do not extend the retry window; nothing is in flight.** Before 2026-08-31 there was no
request the Verifier was permitted to make that could produce a span:

- The three dashboards are **nginx serving a static bundle**. Easy Auth's only excluded
  path is `/healthz`, which nginx answers from its own config, so no application code runs.
- Every other path returns **401 at Easy Auth**, so it never reaches `data-api` - the one
  app in the chain that emits `AppRequests`.
- The probe is `curl`, so the browser SDK in `src/telemetry/browser.ts` never executes.

The fix was **not** to open an unauthenticated path: adding anonymous surface to the app
tier of a compliance demo to satisfy a check is backwards. Easy Auth already publishes the
way in - its `WWW-Authenticate` names the `resource_id` to request a token for - and the
Verifier already federates as `mls-verifier`. What was missing was that the dashboards'
**app registrations had no service principal**, so no client-credentials token could be
issued for them at all (F89). L3 now creates a principal for every registration and grants
`mls-verifier` a `Telemetry.Probe` role that confers no application capability.

**Reading the observed line:**

| Observed | Means |
|---|---|
| `could not obtain a token` | the app registration has no service principal, or the probe role is unassigned. Re-run L3 |
| `http=401` | Easy Auth rejected the token. Check the audience matches the app's `registration.clientId` |
| `http=403 rows=0` | the probe got in; this is an **emission** problem - connection string or sampling |
| `http=403 rows>=1` | PASS. A 403 is expected: the probe role grants no data access, and the claim is that the request reached the app |

### Failure mode: V7.5 reports `1->1->0` for one app and `0->1->0` for another

Not an app difference - a **race with V7.1**, which curls every endpoint earlier in the same
audit and leaves them warm. Whichever app happened to scale back down first passed. V7.5 now
waits for the app to settle at zero before starting, because "starts at 0" was never the
claim; "goes 0 → N → 0" is. An app that will not settle is reported as exactly that (F89).

### V7.3: the four fixes, and the criterion that was looking in an empty column (F97)

By the end of 2026-08-31 the hard part worked. App Insights went from **zero rows in 24
hours** to **70 `requests` spans**, `cloud_RoleName=data-api`. The observability pipeline
demonstrably carries application telemetry, which is what this layer exists to show.

Getting there took four fixes, each hiding the next:

| Fix | What it unblocked |
|---|---|
| F88 | real images instead of `containerapps-helloworld` |
| F89 | service principals, so the Verifier could obtain a token at all |
| F93 | tokenised-manifest resolution, so ingress stopped failing closed to internal |
| F95 | SNI + upstream `Host`, so nginx could reach data-api |

Run 33446777368 (2026-08-31 22:33Z) then came back `V7.1 PASS, V7.2 PASS, **V7.3 FAIL**,
V7.4 PASS, V7.5 PASS` - 4 of 5, with the deploy job green end to end for the first time.
V7.3's observed line was:

```
launch-ops http=404 rows=0; control-tower http=404 rows=0
  | no AppRequests row carrying probe=verifier-20260831223658-launch-ops
  | no AppRequests row carrying probe=verifier-20260831223658-control-tower
```

**Neither failure was in the estate. Both were in the criterion (F97).**

**1. The probe path returned 404 on every request.** `nginx.conf.template`'s
`proxy_pass ${DATA_API_ORIGIN}/` has a trailing slash, which **strips the `/api` prefix** -
the comment directly above it says so. The audit's default `-ProbePath /api/launches`
therefore arrived at data-api as `/launches`, while the real route is `/tables/launches`,
reached via `/api/tables/launches`. All 70 spans were `resultCode=404`, `Name = "GET /*"`.

A 404 does still prove the request traversed Easy Auth and reached application code, which
is V7.3's actual claim - so the criterion was *satisfiable*. It was just only ever going to
exercise a route the product does not have, which is not a demonstration anyone wants to
give. The default is now `/api/tables/launches`, and a test asserts the segment after
`/api` is one of data-api's allowlisted tables.

**2. The criterion matched a field the application deliberately never sets.** It looked for
`probe=<run>-<app>` inside the span's `Url`. Querying the workspace directly settles it:

```
Name        : GET /*
OperationId : f5896115aeba2211b1de27d5cc9525a7
ResultCode  : 404
Url         :                       <- empty. on every row. always.
```

`Url` is empty **by design**. data-api builds its spans from an attribute allowlist
(`apps/data-api/src/telemetry/attributes.ts`) whose header says what is deliberately not
there: *the raw request path or query string (caller-controlled free text), any request or
response header, SQL text, upstream URLs.* The route template `GET /tables/:table` is
emitted instead, precisely so caller text never reaches telemetry.

So the criterion was not merely reading the wrong column. **It was quietly asking the
application to start recording caller-supplied text so that an audit could pass** - in a
demo whose stated design is that it never does. A check may not ask the system to weaken
itself in order to go green. That is the reusable half of this finding, and it is now a
test: `failure-classes.Tests.ps1` forbids any verification KQL from filtering an `App*`
table on `Url`, and asserts the allowlist stays free of URL, query-string, header and
client-address attributes.

**The carrier the application already implements is W3C trace context.** The request
middleware calls `propagation.extract(context.active(), req.headers)` - the comment beside
it says both frontends send trace context on their API calls so a slow tab can be followed
from click to SQL round trip. A probe that sends `traceparent: 00-<traceId>-<spanId>-01`
therefore produces an `AppRequests` row whose `OperationId` **is** that trace id. One trace
id per frontend gives exact per-app attribution with no application change, and it
strengthens the claim: V7.3 now evidences end-to-end trace correlation - the feature the
demo advertises - rather than the bare existence of a span.

The trace ids are minted **once per run**, not per attempt, so a retry re-probes under the
same ids and spans accumulate against one query instead of each attempt restarting the
evidence.

**What this cost, and the cheaper path built because of it.** Five L7 audits at ~55 minutes
each, four and a half hours of wall clock, almost entirely to answer one question about one
criterion - while V7.5's two 15-minute scale-in waits ran every time for no reason. That is
CLAUDE.md's *"a run is an expensive, rate-limited observation"* pointing at the estate's own
tooling. `-OnlyCriterion` (P-10) now exists for exactly this: `only_criterion: V7.3` on the
workflow verifies one criterion, reports the rest as SKIP, and exits **3** so a filtered run
can never be mistaken for a sign-off.

**And the diagnosis that should have come first.** Two `az monitor log-analytics query`
calls - one for the row shape, one for the allowlist - answered in seconds what three
40-minute runs did not. When a check reports zero rows, ask what the row actually looks
like before changing the check.

### F98: the layer was green for two days over an estate serving no data

V7.3's fix left one number in its evidence line unexplained: `http=503`. Chasing it found
something larger than a criterion bug.

`data-api` was running with `MLS_DATA_BACKENDS=local`. LOCAL mode reads
`data/generated/*.json`, which is **gitignored** (CLAUDE.md: never commit generated data)
and therefore **empty in the image by design** - the Dockerfile says so in a comment. So
every `/api/tables/*` route answered 503, and both dashboards rendered empty.

The workflow already knew. It emitted this warning on every run:

> *LOCAL mode reads data/generated, which is not in the image, so every /api/tables route
> will answer 503 and both dashboards will render empty. Set `MLS_SQL_ENDPOINT` ... and
> re-run.*

`MLS_SQL_ENDPOINT` was never set on the `demo` environment, and **nothing failed**. L7's
five criteria test health, golden specs, telemetry, CI and scaling; not one of them reads
a row. The layer could go 5/5 over a product that served nothing.

**Two rules from CLAUDE.md were being broken at once.** *Every value has one source* - the
endpoint's source is the L5 lakehouse metadata, not a GitHub variable somebody remembers to
fill in. And *a constant that names something in another system is verified against that
system, not written from memory* - this one was left to memory, and memory did not.

The fix applies the pattern L7 **already uses** for the Easy Auth client IDs (F36): resolve
it from the system that owns it, in the deploy path, so it fails in seconds rather than
inside a 503. Precedence:

1. `vars.MLS_SQL_ENDPOINT` - an explicit override always wins, so a broken resolver can
   never overrule a human who knows better.
2. The Fabric REST API, read with the deploy job's own identity: the same
   `GET /v1/workspaces` -> `/lakehouses` -> `properties.sqlEndpointProperties
   .connectionString` walk `verification/layer-05-audit.ps1` already performs.
3. Nothing - and then **the run fails**, unless `allow_local_backend=true`.

Step 3 is the F88 shape: an estate that provisions cleanly and serves none of the demo must
be something somebody asked for, never a default. L7-before-L5 is a real state, so it stays
reachable - by asking for it.

**The criterion gap is worth stating separately, because the fix above does not close it.**
No L7 criterion asserts that the API returns data. V7.1 checks `/healthz`, which nginx
answers from its own config. That is a deliberate scope choice - L7 is the app tier and L5
owns the data - but it is why this survived five runs, and it is why the 503 was found by
reading an unrelated evidence line rather than by a test.

### F101: data-api cannot log in to the lakehouse, and no role change will fix it

With F98 resolving the endpoint, `data-api` came up in **cloud mode** and the 503 became a
**502**:

```
upstream_unavailable (502) detail=ConnectionError: Login failed for user '<token-identified principal>'
```

Everything that usually explains this was checked and eliminated:

| Suspected | Actual |
|---|---|
| Lakehouse not seeded | All 10 tables present, `launches = 1,200` |
| Role never granted | `data-api identity already holds workspace role 'Viewer'` |
| Wrong identity wired | `mls-data-api-demo-id` clientId/principalId match the container app and the grant exactly |
| Fabric SP tenant settings off | `ServicePrincipalAccessGlobalAPIs` and `...PermissionAPIs` both **on, org-wide, no group scoping** |
| Endpoint itself broken | **V5.3 PASSES as `mls-verifier`** - `launches = 1,200 +/- 0` over the same TDS endpoint |

So the endpoint works, the data is there, the grant exists, and one principal can read while
another cannot. The difference is what KIND of principal each one is, and Microsoft's
documentation settles it:

> *Fabric natively supports authentication and authorization for Microsoft Entra **users and
> service principal names (SPN)** in SQL connections to warehouse and SQL analytics endpoint
> items. ... **SPNs represent application objects** within a tenant.*

`mls-verifier` is an **app registration** - an application object, so an SPN. `data-api`
authenticates as a **user-assigned managed identity**, which is a service principal without
an application object behind it. Fabric's REST APIs accept managed identities (which is
exactly why the workspace role grant succeeded and reported success), but the **TDS endpoint
does not**. The grant is real; it just never applies to a login that Fabric's SQL layer
cannot resolve.

**This is a platform constraint, not a misconfiguration**, and it is worth being precise
about because the estate looks correct at every layer.

**The experiment this reading prevented.** The obvious next move was to bump `data-api` from
Viewer to Contributor and see whether the login succeeded. The same page rules it out
without spending the cycle:

> *Any workspace role (Admin, Member, Contributor, or Viewer) is sufficient to connect to
> warehouse or lakehouse items with a SQL connection string.*

Viewer was never the constraint. That is CLAUDE.md's *"a constant that names something in
another system is verified against that system"* earning its keep twice in one hour - the
first time was the `ManagedIdentity` principal-type value, which does not exist in the
Fabric enum at all (`User | ServicePrincipal | Group | ServicePrincipalProfile |
EntireTenant`), so the fix that looked obvious would have been a no-op at best.

**What it costs the demo.** No L7 criterion asserts that the API returns rows, so this fails
nothing - the dashboards render empty while the layer signs off. That gap is the subject of
F98's closing note and it is the reason this was found by reading an evidence line rather
than by a test.

**Options, none yet chosen:**

- give `data-api` an **app registration** for its Fabric reads (L3 already creates
  registrations from the manifest) - the only option that keeps the TDS path;
- read the lakehouse through the **Fabric REST/OneLake APIs**, which do accept managed
  identities, instead of TDS;
- grant the workspace role to a **security group** containing the identity and test whether
  Fabric's SQL layer resolves group membership - cheap to try, uncertain, and it should be
  tried before either of the above because both are large.
