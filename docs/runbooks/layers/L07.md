## Purpose

Ship the user-facing surface: the `apps/shared/spec-renderer` library (JSON schema +
8–10 Fluent UI v9 components + Storybook + unit tests), the `launch-ops` app
(SQL-backed CRUD + lakehouse-backed analytics views), the `control-tower` app
(Dev/Sec/Ops tabs on live APIs), OpenTelemetry wiring into App Insights, and
path-filtered CI per app (build → test → Trivy image scan → deploy to ACA via OIDC).
After L7 the demo has two browsable apps scaling 0→N→0 on the L6 platform.

**A fifth container app deploys from this template and is not L7's to validate.** The
compliance board (`mls-compliance-demo-ca`) is provisioned by the same
`infra/bicep/apps/main.bicep` and the same `layer-07-apps.yml` as the four above, but it
belongs to **L12** — see [`L12.md`](L12.md). It is deliberately excluded from this
template's `containerAppNames` output because V7.1's sweep is an *unauthenticated* GET
expecting 200, which is exactly the request its Easy Auth gate exists to refuse. None of
L7's five criteria cover it, and none should.

Since the 2026-08-24 amendment the control tower also carries a fourth tab, **Ask**,
which is showpiece #1's surface: a Direct Line embed of the L8 Copilot Studio agent. It
ships here **dark** — the tab and its backend token route are built and tested at L7,
but `ASK_TAB_ENABLED` is off and the Direct Line secret reference is empty until L8
publishes an agent. There is no separate copilot app any more: `copilot-svc` is retired,
and what replaces it on the compute side is `apps/mcp-tools`, deployed at L8, not here.
None of L7's five Verify criteria change — the Ask tab is deliberately not part of any
of them, so a dark tab cannot fail this layer.

## Deploy procedure

1. Merge the L7 PR(s); path-filtered CI does the deploys — there is no separate
   layer workflow for apps:

   ```
   .github/workflows/app-launch-ops-ci.yml      # paths: apps/launch-ops/**, apps/shared/**
   .github/workflows/app-control-tower-ci.yml   # paths: apps/control-tower/**, apps/shared/**
   ```

   Each runs build → unit tests → container build → Trivy scan (fail on CRITICAL)
   → `azure/login` (OIDC, environment `demo`) → `az containerapp update` with the
   image and `minReplicas 0`.
2. For a full-environment replay (`infra-up.yml`), the same two workflows are
   invoked via `workflow_call` after L6 completes [derived — the master plan names
   per-app CI as the deploy path; the call wiring is the derivation].
3. The deploy step stamps the container image's content hash into a response header
   / `/healthz` marker [derived mechanism] so V7.1 can bind "endpoint is up" to
   "endpoint serves the audited build".
4. Confirm the Ask tab deployed **dark**: `ASK_TAB_ENABLED` unset/false in the container
   app's configuration, and the tab either hidden or rendering its "not yet available"
   state. L8 step 5 flips this flag; nothing about it is a redeploy. [derived flag name —
   the master plan does not name the control tower's configuration keys.]
5. Open the **canary PR** for V7.4: a trivial whitespace-level change under each
   app's path, opened by the lead (the Verifier never writes to the repo), left for
   the audit to observe, then closed without merge.
6. Post run URLs + image digests to the Verifier.

## Validation cycle

Run by the Verifier as `mls-verifier` via `verification/layer-07-audit.ps1`. Report:
`verification/reports/L07-<date>.md`.

### V7.1 — Public endpoints return 200 with correct content hash markers

- **Criterion (master plan):** public endpoints return 200 with correct content
  hash markers.
- **Query:**

  ```powershell
  foreach ($app in 'launch-ops','control-tower') {
    $fqdn = az containerapp show -g mls-rg-apps -n (naming $app) --query properties.configuration.ingress.fqdn -o tsv
    Invoke-WebRequest "https://$fqdn/healthz" -MaximumRetryCount 3
  }
  ```

- **Expected:** HTTP 200 from both apps; the health payload's content-hash marker
  equals the image digest recorded in the deploy run (binding endpoint to build).
  First request may cold-start from 0 replicas — allow up to 60 s response time
  before retry counts as failure.
- **Retry/propagation:** ingress DNS + cold start; retry 3× over 5 minutes, within
  the standard 30-minute window.

### V7.2 — Renderer schema validation passes on golden specs

- **Criterion (master plan):** renderer schema validation passes on golden specs.
- **Query:**

  ```
  npm --prefix apps/shared/spec-renderer run validate:golden
  ```

  (ajv validation of every fixture under
  `apps/shared/spec-renderer/golden/` against the component-spec JSON Schema —
  local execution; the Verifier runs it from the audited commit, trusting the repo
  state, not a teammate's claim.)
- **Expected:** exit 0; every golden spec valid; the fixture set covers all ~9
  component types (bar/line/area chart, stat card, KPI row, data table, timeline,
  donut, markdown block).
- **Retry/propagation:** none — deterministic local check.

### V7.3 — OTel spans visible in App Insights

- **Criterion (master plan):** OTel spans from a synthetic request visible in App
  Insights via KQL.
- **Query:** issue one tagged synthetic request per app
  (`GET /healthz?probe=verifier-<runId>` — a read, permitted to the Verifier), then:

  ```
  az monitor log-analytics query --workspace <lawCustomerId> --analytics-query \
    "AppRequests | where Url has 'probe=verifier-<runId>' | project TimeGenerated, AppRoleName, OperationId" \
    --timespan PT1H
  ```

- **Expected:** ≥ 1 `AppRequests` row per app carrying the probe marker, with
  `AppRoleName` matching the app name from `naming.bicep`.
- **Retry/propagation:** App Insights ingestion latency is typically 2–10 minutes;
  poll every 5 minutes within the standard 30-minute window.

### V7.4 — Per-app CI green on a canary PR

- **Criterion (master plan):** per-app CI green on a canary PR.
- **Query:**

  ```
  gh pr checks <canary-pr-number> --json name,state
  gh api repos/paulcfuqua/azure-devsecops-demo/commits/<canary-sha>/check-runs \
    --jq '.check_runs[] | {name, conclusion}'
  ```

- **Expected:** every required check on the canary PR concludes `success` — for
  both app pipelines when the canary touches `apps/shared/**`, and **only** the
  matching app's pipeline when it touches a single app path (path-filter working is
  part of the criterion's intent). Canary PR is then closed unmerged by the lead.
- **Retry/propagation:** none beyond CI runtime; a flaky-check rerun is allowed
  once, recorded in the report.

### V7.5 — Replicas scale 0→N→0

- **Criterion (master plan):** replicas scale 0→N→0.
- **Query:** three-phase observation per app:

  ```
  az containerapp replica list -g mls-rg-apps -n <app> --query "length(@)"   # phase 1: expect 0
  # phase 2: drive load — 20 concurrent GETs for 60 s, then:
  az containerapp replica list ... # expect >= 1
  # phase 3: after idle (scale-in window + margin):
  az containerapp replica list ... # expect 0
  ```

- **Expected:** 0 before load; ≥ 1 under load; back to 0 after the idle window.
  [derived] Phase-3 wait: ACA scales in within ~5 minutes of idle plus the
  configured cooldown — the audit waits 15 minutes before the phase-3 read; a
  nonzero count at +30 minutes is a FAIL (idle-cost model broken).
- **Retry/propagation:** phase-3 only, as above; phases 1–2 are immediate.

## Teardown

- **Standard kill/rebuild cycle:** `az group delete --name mls-rg-apps --yes` via
  `down.ps1`. **Gate class: gate-free** (RG-scoped demo resources). Container
  images live in the registry inside the demo RGs and are rebuilt by CI on replay —
  nothing app-side survives the cycle except the repo itself.
- Nothing G3 in this layer: app registrations used by the apps were created at L3
  and persist there (their teardown is L3's G3 concern, not L7's).

## Rollback

- **First validation failure:** Verifier files specifics. The joint leads fix in
  worktrees and let path-filtered CI redeploy — every deploy is
  image-replacement, inherently idempotent. For a corrupted environment-level state
  the gate-free reset is `az group delete --name mls-rg-apps` + replay of both CI
  workflows.
- Failures in V7.2 (golden specs) roll back **in the repo only** — no cloud state
  involved; fix the schema/fixtures via PR, re-run the audit.
- **Second consecutive failure of L7 → G4.**

## Failure modes

1. **Cold-start timeout read as downtime** (V7.1 fails on first-ever request).
   Detection: 200 arrives on manual retry after ~30–60 s. Response: none needed —
   the audit's retry policy absorbs it; if cold start exceeds 60 s consistently,
   investigate image size/startup path (that latency will also poison the demo's
   feel).
2. **Trivy gate blocks deploy on a CVE published overnight** (unrelated to the
   change). Detection: CI fails at the scan step naming a base-image CVE. Response:
   bump/pin the base image via PR (the DevSecOps chain exists to make this loud);
   never suppress the gate to ship a layer.
3. **OTel spans missing** (V7.3 empty). Causes: connection string not injected
   (Bicep app config), sampling set to 0, or ingestion lag. Detection: V7.3
   timeout after 30 minutes. Response: check app env vars against the L6 manifest;
   fix wiring via PR; ingestion lag alone is covered by the retry window.
4. **Path filters misfire** (canary touching one app triggers both pipelines, or
   neither). Detection: V7.4's filter assertion. Response: fix `paths:` globs in
   the CI workflows; this is exactly the drift that turns "per-app CI" into
   "monolithic CI" silently.
5. **Replicas never return to 0** (V7.5 phase 3 fails). Causes: health probe
   traffic keeping the app warm, scale rule floor set to 1 by a template change.
   Detection: V7.5; long-term, idle cost creep. Response: check scale rules against
   the manifest (minReplicas must be 0), fix probe frequency; an intentional floor
   change would be a G2 question — as an unrequested drift it is simply a defect.
