## Purpose

Prove showpiece #3 with GitHub's own AI doing the fixing. No authored triage script
exists any more: `.github/scripts/self-heal-triage.mjs` is retired, and the explanation
the audience reads on the PR is Copilot Autofix's own.

Two tracks, because GitHub heals the two finding types by two different mechanisms and
[Copilot Autofix covers CodeQL alerts, not Dependabot dependency alerts](https://docs.github.com/en/code-security/code-scanning/managing-code-scanning-alerts/responsible-use-autofix-code-scanning):

| Track | Finding | Who writes the fix | Trail the audience sees |
|---|---|---|---|
| **Code** | 1 seeded CodeQL-detectable JS/TS flaw in `apps/vuln-lab` | **Copilot Autofix** (LLM + CodeQL, driven by `self-heal.yml` through the Autofix REST API) | alert → Autofix suggestion + explanation → PR → gauntlet → auto-merge → deploy → alert `fixed` |
| **Dependency** | 3 seeded vulnerable pins (real CVEs, patch available) | **Dependabot security updates**, which [automatically open PRs for every open alert with an available patch](https://docs.github.com/en/code-security/dependabot/dependabot-security-updates/about-dependabot-security-updates) | alert → Dependabot patch PR → gauntlet → auto-merge → deploy → alert closes on merge |

Both tracks then ride the identical L9 gauntlet (CodeQL, tests, Trivy, ZAP) →
auto-merge on green → deploy → alert closed. Auto-merge on green inside the demo
environment is intentionally allowed (brief: that IS the showpiece); the human sees the
PR trail, not an approval prompt.

**Accepted trade, recorded:** the triage narrative is now GitHub's, not ours. We lose the
ability to shape the explanation text with a custom prompt. Autofix suggestions are also
[non-deterministic and may be incomplete or wrong](https://docs.github.com/en/code-security/code-scanning/managing-code-scanning-alerts/responsible-use-autofix-code-scanning)
— which is precisely why the gauntlet, not the model, is the gate.

## Preconditions

- G0 complete + G1b granted; L9 Verifier PASS (the gauntlet the heal PR must survive is
  exactly L9's chain — it must already be proven).
- Orchestrator unblock for L10.
- **No LLM credential of any kind.** This layer stores no secret: Autofix is a GitHub
  platform feature, invoked with the workflow's own `GITHUB_TOKEN`.
- **Autofix available and allowed.** The repo is public, so
  [Copilot Autofix for CodeQL alerts is GA and free, with no Copilot subscription](https://github.blog/changelog/2024-09-17-now-available-for-free-on-all-public-repositories-copilot-autofix-for-codeql-code-scanning-alerts/),
  and it is enabled by default for any repository using CodeQL — enabling code scanning
  is sufficient, there is no second switch. Confirm nobody disabled it at repo level.
- **CodeQL running on the seeded language.** Autofix covers a subset of the default and
  security-extended CodeQL suites; the seeded flaw must be one CodeQL actually reports in
  JS/TS on the default setup, or the code track never starts. Pre-check:

  ```
  gh api repos/paulcfuqua/azure-devsecops-demo/code-scanning/alerts --jq '[.[]|select(.state=="open")]|length'
  ```

  ≥ 1 open code-scanning alert on `apps/vuln-lab/`.
- **Alert presence pre-check for the dependency track:** confirm Dependabot has raised
  alerts for the 3 seeded pins
  (`gh api repos/paulcfuqua/azure-devsecops-demo/dependabot/alerts --jq 'length'` ≥ 3 open,
  filtered to `apps/vuln-lab/`) — this catches L9 failure mode 5 before it burns the
  layer's audit attempts.
- **Dependabot security updates enabled** on the repo (they are what opens the dependency
  PRs; alerts alone do not).
- Repo settings allow auto-merge, and branch protection's required checks equal the
  gauntlet's check names exactly (a mismatch silently blocks auto-merge).
- Workflow permissions: `self-heal.yml` needs `security-events: write` (create and read
  an autofix), `contents: write` (commit the autofix onto a branch) and
  `pull-requests: write` (open the PR). The Autofix REST endpoints require the
  `security_events` scope, or `public_repo` on a public repo, and the commit endpoint
  requires `repo`/`public_repo`
  ([REST reference](https://docs.github.com/en/rest/code-scanning/code-scanning)).
- Track F artifact merged: `apps/vuln-lab` with its 3 CVE pins **and** the seeded
  CodeQL-detectable flaw, plus a README stating their purpose (spec F5 — vulnerable
  *dependencies* and a deliberately unsafe code path, not exploit code).

## Deploy procedure

1. Merge the L10 PR carrying `.github/workflows/self-heal.yml`. (It historically also
   carried the re-seed script `apps/vuln-lab/reseed.ps1`; that script is retired — see
   the banner — and is kept only until the migration deletes it.)
2. ~~Arm the lab.~~ **RETIRED — do not run `reseed.ps1`.** Arming the lab by pull request
   is F190: the PR reintroduces a critical alert and cannot merge past code scanning
   protection without an administrator override. The chain now runs on whatever real
   findings the estate produces; there is nothing to arm and nothing to restore.
3. Let the chain run. Neither track is manually dispatched on the happy path — the
   triggers firing on alert creation are part of what is being proven.

   **Code track.** `self-heal.yml` triggers on `code_scanning_alert` [derived trigger
   detail] and, per open alert:

   ```
   POST /repos/{owner}/{repo}/code-scanning/alerts/{n}/autofix          # 202 accepted (200 if one exists)
   GET  /repos/{owner}/{repo}/code-scanning/alerts/{n}/autofix          # poll until status == success
   POST /repos/{owner}/{repo}/code-scanning/alerts/{n}/autofix/commits  # target_ref = heal branch, message = ...
   ```

   then opens the PR from that branch with Autofix's `description` quoted in the body,
   and enables auto-merge. [derived] Poll budget: every 15 s for 5 minutes, then fail the
   run and let the next trigger retry — generation is asynchronous and the API documents
   no SLA. A status of `error` or `outdated` is a real result, not a flake: `outdated`
   means the alert moved under the fix and the branch must be regenerated from the
   current head.

   **Dependency track.** Nothing to invoke. Dependabot opens the patch PRs itself;
   `self-heal.yml` only labels them for auto-merge so both tracks converge on the same
   gauntlet [derived — the master plan requires auto-merge on green for the healed PRs
   and Dependabot PRs are not auto-merge-flagged by default].
4. Nothing to do for the deploy stage either: merging a heal touches `apps/vuln-lab/**`,
   which triggers `.github/workflows/vuln-lab-witness.yml`. That workflow stamps the merge
   commit onto `mls-vuln-lab-demo-ca` and rolls the revision V10.1 stage 6 / V10.2 stage 5
   read. It no-ops with a NOTICE when the estate is torn down, so a heal merged between
   demos does not fail a push to `main` — but the audit will then correctly report that
   heal as never shipped. See *The deployment witness* below.
5. Post the alert numbers and PR numbers to the Verifier as they appear.

## The deployment witness (`mls-vuln-lab-demo-ca`)

Both trails end in a deploy stage, and the estate resource they read is
`mls-vuln-lab-demo-ca` — provisioned by `infra/bicep/apps/main.bicep` (module
`vulnLabWitnessApp`, name owned by `naming.bicep`'s `appKeys.vulnLab`) and rolled by
`.github/workflows/vuln-lab-witness.yml` on every push to `main` touching
`apps/vuln-lab/**`.

**It is a witness, not a fifth serving app, and `apps/vuln-lab` is never containerised.**
Recorded here because it is the obvious thing to "fix" later:

1. The lab pins three known-vulnerable packages, one CRITICAL (`minimist@1.2.5`,
   CVE-2021-44906). An image built from it fails the L9 Trivy CRITICAL gate — the same
   gauntlet stage 4 requires every heal PR to pass. The Autofix track never touches the
   pins, so **its heal PR would go red every time**. The only escapes are suppressing the
   gate (failure mode 3 forbids it: "Never suppress a check to make a heal pass") or
   shipping known-vulnerable containers into an estate with Defender for Containers
   toggled on at L9, where they raise real findings.
2. The two code seeds are HTTP server factories for a path traversal and a command
   injection. `apps/vuln-lab/README.md`'s safety argument is that *no server is ever
   started*. Deploying them would trade that away for nothing.
3. The repo-root `package.json` excludes the lab from `workspaces` so its pins cannot
   resolve to patched versions, and the README guarantees it is "not in any Dockerfile".

So the witness runs a pinned public placeholder image, holds no lab code and no lab
dependency, and carries the heal's identity as configuration: `MLS_HEAL_COMMIT`, plus the
lab's advisory count at that commit. Ingress is disabled and `minReplicas` is 0, so it
runs zero replicas and costs **$0**.

**What the stage therefore proves, exactly:** that the merged commit reached Azure through
the pipeline, hands-off, under the estate's deployer identity — and the audit will not
accept "some revision appeared after the merge", which any unrelated redeploy satisfies.
It requires the revision to carry *this* heal's merge commit, which nothing satisfies by
accident. What it does **not** prove is that the healed code runs somewhere; nothing can
prove that about a package deliberately never deployed, and the report says so rather than
implying otherwise.

## Validation cycle

Run by the Verifier as `mls-verifier` (GitHub read token + Reader) via
`verification/layer-10-audit.ps1`. Report: `verification/reports/L10-<date>.md`.

### V10.1 — the backlog drains

- **Criterion:** no **healable** finding remains open past the SLO its severity declares.
  Reported **per lane and per severity**, never averaged — a blended figure hides the slice
  that is not moving, which is the failure the compliance platform was built to avoid.
- **Command:**

  ```
  gh api repos/<repo>/dependabot/alerts?state=all
  gh api repos/<repo>/code-scanning/alerts?state=all
  cat .github/self-heal-policy.json
  ```

- **Expected:** every open finding that has an upstream fix is inside its declared SLO.
  The service levels are **declared** in `.github/self-heal-policy.json`, not defaulted:
  critical/high 7 days, medium/low 30 days. A missing or malformed policy makes this
  criterion **SKIP** rather than invent a pass line.
- **Not counted:** a finding with no upstream fix does not consume its SLO — it is
  `pending-solution`, which holds and ages legitimately, and **V10.4** is what stops that
  state becoming a place a backlog goes to die quietly. `apps/vuln-lab` is excluded by
  `excludedPaths` in the policy; the audit **reports how many findings it excluded**, so an
  empty backlog cannot be manufactured by editing that list unnoticed.
- **Unobservable ≠ empty:** an alert surface that could not be read reports SKIP. An
  identity that cannot look must never be able to report the queue drained (F103/F105).

### V10.2 — every closure is traceable

- **Criterion:** for each finding closed inside the declared window, either a self-heal
  pull request explains it with a complete trail, **or** it is explicitly recorded as
  closed some other way. An unexplained closure fails.
- **The seven stages live here.** They did not die with the seeded model; they moved, and
  they now apply **per healed finding** instead of to three pins somebody planted:
  1. a merged pull request that explains the closure — Dependabot names the package in its
     title, an Autofix heal names the alert number in its body;
  2. the gauntlet green — `skipped` and `neutral` are not failures (every heal PR carries
     five skipped `deploy to Container Apps` jobs), and a run where **nothing** executed is
     not a pass either;
  3. the merge **pre-authorised** by an auto-merge request armed *before* it and credited
     to the identity that armed it. F191: the question is *when* the decision was made, not
     who is credited with it — a hand-merge produces an identical `mergedBy`;
  4. the healed code actually running.
- **The deploy stage changed shape.** Old: *did the vuln-lab witness roll?* New: **did the
  application this heal actually changed receive a revision carrying the merge commit?**

  ```
  PR changed files → apps/<name>/** → naming.bicep appKeys → <prefix>-<key>-<env>-ca → revision
  ```

  The binding is the image tag and needs no cooperation from the applications: every app CI
  computes `tag="sha-${GITHUB_SHA:0:7}"`, and on a push to `main` `GITHUB_SHA` **is** the
  merge commit — so a revision whose image ends `:sha-<first 7>` is the estate's own record,
  read with Reader, that this heal shipped.
- **Reported, not failed:** a heal touching no deployed application (`verification/`,
  `docs/`) — no deploy assertion is possible and saying so is honest where failing is a lie
  about what was observed; and an application that is not deployed at all, which is a
  different fact from a heal that did not ship.
- **Closed another way:** GitHub's own dismissal record, not a file this repository invents.
  A dismissal carrying a reason is explained; a dismissal with **no** reason recorded is
  not. A `fixed` alert with no heal PR behind it is the case this criterion exists to catch
  — something closed it and the estate cannot say what.

### V10.3 — the alert surface was readable

- **Criterion:** the self-heal chain could actually READ the alert surface. A denial is
  never recorded as "no alerts to heal" (F123).
- **More load-bearing than before.** With no planted alert guaranteeing the queue is
  non-empty, **"no findings" is the expected steady state** — so a denial that read as an
  empty queue would look exactly like success, every run, forever.
- **No retry window.** A 403 is settled the instant it is returned.

### V10.4 — `pending-solution` is not a dumping ground

- **Criterion:** for every finding held as `pending-solution`, verify that **no upstream fix
  actually exists** — re-read per held finding rather than trusting the list projection.
- **Why it exists:** this state legitimately does not count as a failure, which makes it the
  obvious place for a backlog to go and die quietly. An unverified "no fix available" is the
  artefact-instead-of-capability trap this repository keeps paying for, one level up.
- **Expected:** every held finding has no `first_patched_version` in its advisory. One that
  names a patched version fails — bump it, or record why that version is not adoptable.

## Teardown

- **Standard kill/rebuild cycle:** ~~re-arming~~ **RETIRED.** Teardown here used to mean
  *re-arming* rather than deleting, via `apps/vuln-lab/reseed.ps1`. Do not run it. There
  is nothing to restore between cycles: the chain heals real findings as they arrive.
  **Gate class: gate-free** (repo PR + RG-scoped app state only). The vuln-lab
  deployment witness dies with `mls-rg-apps` in `down.ps1` and is recreated by
  `layer-07-apps.yml` on the next build. Its revision history does not survive a rebuild,
  which is why each cycle's heal stamps its own merge commit rather than relying on a
  cumulative trail.
- Nothing G3 in this layer. Nothing to rotate or revoke either — the layer holds no
  credential.

## Rollback

- **First validation failure:** Verifier files which stage broke, for which track and
  which finding. DevSecOps lead fixes the specific stage (trigger config, the Autofix API
  call sequence, auto-merge settings, gauntlet check names) via PR and lets the chain
  re-run against the next real finding. **Do not re-seed to manufacture one.** Still
  never hand-close alerts, hand-write a fix, or hand-merge PRs to "complete" a run. A
  hand-assisted chain is a failed chain: V10.1 stage 3 checks that the head commit came
  from the Autofix API and stage 5 checks the merger identity.
- If a heal PR broke something post-merge (a bad Autofix suggestion merged on green),
  revert via a normal revert PR through the same gauntlet — the pipeline's own safety
  story, demonstrated rather than bypassed. This is a legitimate outcome to show, not an
  embarrassment: Autofix is documented as fallible, and the gauntlet is why that is safe.
- **Second consecutive failure of L10 → G4.**

## Failure modes

1. **Autofix never generates** (`status` stays `pending`, or returns `error`).
   Detection: V10.1 stage 2. Causes: the alert's rule is outside the subset of CodeQL
   queries Autofix supports; the file is too large so context is truncated and Autofix
   declines; a multi-file data-flow fix beyond its reach. Response: re-choose the seeded
   flaw for one that Autofix demonstrably handles — verify once, off-demo, before relying
   on it. This is the code track's equivalent of "real CVEs, patch available".
2. **403 from the Autofix API.** Detection: the workflow's first `POST …/autofix` fails.
   Causes: the repo is archived, or Advanced Security features are not enabled on it.
   Response: confirm the repo is public and code scanning is on — on a public repo those
   features are free and enabled; a 403 here means the repo state changed, not that the
   feature is unavailable.
3. **Autofix's fix fails the gauntlet.** Detection: V10.1 stage 4 shows non-success
   conclusions. Response: this is the pipeline honestly refusing a bad heal and it is a
   *valid* demo beat, but not a passing audit. Fix by choosing a seeded flaw whose fix
   lands green, not by weakening the gauntlet. Never suppress a check to make a heal pass.
4. **Alert latency stalls a chain at stage 1.** Detection: re-seed merged, zero alerts
   after several hours. Response: for the dependency track verify `.github/dependabot.yml`
   covers `apps/vuln-lab/` (L9 FM5) and force a manifest re-scan by pushing a trivial
   change to the lab's manifest; for the code track confirm the CodeQL workflow actually
   ran on the merge commit and scans the lab's paths. The 24 h audit window absorbs
   ordinary latency.
5. **Auto-merge silently blocked** (branch protection requires a check name the gauntlet
   does not produce, or auto-merge disabled at repo level). Detection: stage 4/5 — PR
   green but unmerged with `autoMergeRequest == null` or a pending required check.
   Response: align required-check names with the gauntlet's job names in
   settings-as-code; re-run. Note that Dependabot PRs must be explicitly flagged for
   auto-merge; a PR sitting green and unmerged usually means that step did not run.
6. **`outdated` autofix.** Detection: stage 2 returns `outdated`. Cause: the default
   branch moved after the suggestion was generated, so the patch no longer applies.
   Response: regenerate against the current head — the workflow should treat `outdated`
   as "recreate", not as an error to report.
7. **The heal merged but the witness never rolled.** Detection: V10.1 stage 6 / V10.2
   stage 5 report either "no new container app revision timestamped after the merge" or
   "revision(s) exist after the merge but none carries `MLS_HEAL_COMMIT=<sha>`". Causes:
   the estate was torn down when the heal merged (`vuln-lab-witness.yml` no-ops with a
   NOTICE); L7 has not run, so the witness does not exist; or the merge did not touch
   `apps/vuln-lab/**` and so did not fire the trigger. Response: deploy the estate, then
   `gh workflow run vuln-lab-witness.yml -f commit=<merge sha>` to stamp that specific
   commit, and re-run the audit. Never relax the criterion to "any revision": a revision
   that is not this heal's does not prove this heal shipped.
8. **Only one track completes.** Detection: V10.1 or V10.2 fails while the other passes.
   Response: they are independent criteria and both must pass; treat each incomplete
   chain as its own stage-level defect (modes 1–6), fix, and let the chain re-run against
   the next real finding. **Do not re-seed to produce one.** Partial credit does not
   accumulate across runs — a pass requires the trails to complete within one window.
