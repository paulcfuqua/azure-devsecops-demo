## Purpose

Prove showpiece #3: `apps/vuln-lab` seeded with 3 known-vulnerable dependency pins
(real CVEs, patch available), and `self-heal.yml` driving the full loop —
Dependabot/CodeQL alert → Claude triage (explanation comment) → patch PR → CI
gauntlet (CodeQL, tests, Trivy, ZAP) → auto-merge on green → deploy → alert closed.
Auto-merge on green inside the demo environment is intentionally allowed (brief:
that IS the showpiece); the human sees the PR trail, not an approval prompt.

## Preconditions

- G0 complete + G1b granted; L9 Verifier PASS (the gauntlet the heal PR must
  survive is exactly L9's chain — it must already be proven).
- Orchestrator unblock for L10.
- `ANTHROPIC_API_KEY` valid (triage runs on the Claude API; ~$0.50/heal).
- **Alert presence pre-check:** before running the chain, confirm Dependabot has
  actually raised alerts for the 3 seeded pins
  (`gh api repos/paulcfuqua/azure-devsecops/dependabot/alerts --jq 'length'` ≥ 3
  open, filtered to `apps/vuln-lab/`) — this catches L9 failure mode 5 before it
  burns the layer's audit attempts.
- Repo settings allow auto-merge, and branch protection's required checks equal the
  gauntlet's check names exactly (a mismatch silently blocks auto-merge).
- Track F artifact merged: `apps/vuln-lab` with its 3 CVE pins + README stating
  their purpose (spec F5 — vulnerable *dependencies*, not exploit code).

## Deploy procedure

1. Merge the L10 PR carrying `.github/workflows/self-heal.yml` and the vuln-lab
   re-seed script `apps/vuln-lab/reseed.ps1` [derived path — master plan names "a
   re-seed script" without location; co-located with the lab per repo convention].
2. Arm the lab (first run: the pins are already present from Track F; subsequent
   demos: re-seed):

   ```
   pwsh apps/vuln-lab/reseed.ps1
   ```

   The script restores the 3 vulnerable pins via PR (never direct push —
   CLAUDE.md), which merges through normal CI and re-raises the alerts.
3. Let the chain run. `self-heal.yml` triggers on `dependabot_alert`/
   `code_scanning_alert` events [derived trigger detail]: for each open alert it
   invokes the Claude triage step (posts the explanation comment), opens the patch
   PR flagged for auto-merge, and the L9 gauntlet takes it from there. No manual
   dispatch is part of the happy path — the trigger firing on alert creation is
   part of what is being proven.
4. Post the alert numbers + PR numbers to the Verifier as they appear.

## Validation cycle

Run by the Verifier as `mls-verifier` (GitHub read token + Reader) via
`verification/layer-10-audit.ps1`. Report: `verification/reports/L10-<date>.md`.

### V10.1 — Full chain observed via API trail for ≥ 2 of 3 seeded vulns

- **Criterion (master plan):** full chain observed via API trail for at least 2 of
  3 seeded vulns: alert created → PR with triage comment → checks green → merged by
  automation → new ACA revision → alert state `fixed`. Human sees the PR trail only
  (per brief).
- **Query — six chain stages, each read independently from APIs, per vuln:**

  ```powershell
  # 1. alert created
  gh api repos/paulcfuqua/azure-devsecops/dependabot/alerts/<n> --jq '{state, created_at, dep:.dependency.package.name}'
  # 2. PR exists with triage comment
  gh pr view <pr> --json comments --jq '.comments[] | select(.body | contains("self-heal triage"))'
  # 3. checks green
  gh api repos/paulcfuqua/azure-devsecops/commits/<head-sha>/check-runs --jq '[.check_runs[].conclusion] | unique'
  # 4. merged by automation
  gh pr view <pr> --json mergedBy,autoMergeRequest --jq '{by:.mergedBy.login, auto:(.autoMergeRequest != null)}'
  # 5. new ACA revision after merge
  az containerapp revision list -g mls-rg-apps -n <vuln-lab-app> --query "[].{name:name, created:properties.createdTime}"
  # 6. alert closed
  gh api repos/paulcfuqua/azure-devsecops/dependabot/alerts/<n> --jq '.state'
  ```

- **Expected:** for **at least 2 of the 3** seeded vulns, all six stages hold:
  (1) alert `state` was `open` with `created_at` after the re-seed merge;
  (2) the patch PR carries the triage explanation comment authored by the
  self-heal workflow; (3) check-run conclusions are exclusively `success` across
  the gauntlet (CodeQL, tests, Trivy, ZAP); (4) `mergedBy.login` is the automation
  identity (`github-actions[bot]`) with an auto-merge request present — no human
  merger anywhere in the trail; (5) a new revision timestamped after the merge;
  (6) alert `state == "fixed"`. Timestamps must be monotonic across stages 1→6.
  The third vuln's outcome is recorded either way; 3/3 is the target, 2/3 is the
  pass line.
- **Retry/propagation:** the chain is asynchronous end to end — Dependabot alert
  latency after re-seed is minutes-to-hours; the audit polls stage-by-stage with an
  overall window of **24 h from re-seed merge** [derived — the master plan sets no
  chain deadline; 24 h bounds Dependabot's un-SLA'd alert latency while keeping the
  layer demoable day-to-day]. Within a demo context the observed norm is well under
  an hour; the 24 h bound is the audit deadline, not the expectation.

## Teardown

- **Standard kill/rebuild cycle:** `apps/vuln-lab/reseed.ps1` restores the
  vulnerable pins for the next demo — teardown here means *re-arming*, not
  deleting. **Gate class: gate-free** (repo PR + RG-scoped app state only). The
  vuln-lab container itself dies with `mls-rg-apps` in `down.ps1`.
- Nothing G3 in this layer.

## Rollback

- **First validation failure:** Verifier files which stage broke for which vuln.
  DevSecOps lead fixes the specific stage (trigger config, triage step, auto-merge
  settings, gauntlet check names) via PR, then re-arms with `reseed.ps1` and lets
  the chain re-run. Re-seeding is cheap and idempotent by design — never hand-close
  alerts or hand-merge PRs to "complete" a run; a hand-assisted chain is a failed
  chain (stage 4 explicitly checks the merger identity).
- If a heal PR broke something post-merge (bad patch merged on green), revert via a
  normal revert PR through the same gauntlet — the pipeline's own safety story,
  demonstrated rather than bypassed.
- **Second consecutive failure of L10 → G4.**

## Failure modes

1. **Dependabot alert latency stalls the chain at stage 1.** Detection: re-seed
   merged, zero alerts after several hours (pre-check query). Response: verify
   `.github/dependabot.yml` covers `apps/vuln-lab/` (L9 FM5); force a manifest
   re-scan by pushing a trivial change to the lab's manifest file; the 24 h audit
   window absorbs ordinary latency.
2. **Auto-merge silently blocked** (branch protection requires a check name the
   gauntlet does not produce, or auto-merge disabled at repo level). Detection:
   stage 4 — PR green but unmerged with `autoMergeRequest == null` or pending
   required check. Response: align required-check names with the gauntlet's job
   names in settings-as-code; re-run.
3. **Triage step produces no comment** (Claude API failure, token exhaustion, or
   the workflow's comment step lacking `pull-requests: write` permission).
   Detection: stage 2 empty. Response: check `self-heal.yml` run logs and workflow
   `permissions:` block; API-side failures follow the credential-failure path (G4
   on recurrence).
4. **Patch PR fails the gauntlet** (upgrade breaks vuln-lab tests, or the pinned
   fix pulls a new CRITICAL). Detection: stage 3 shows non-success conclusions.
   Response: this is the pipeline honestly refusing a bad heal — fix the lab's
   compatibility range or choose a different seeded CVE whose patch path is clean;
   seeded vulns must be selected so a patch exists *and* lands green (that is what
   "real CVEs, patch available" means operationally).
5. **Only 1 of 3 chains completes.** Detection: V10.1 tally below the pass line.
   Response: treat each incomplete chain as its own stage-level defect (modes 1–4);
   fix, re-seed, re-run — partial credit does not accumulate across runs; a pass
   requires ≥ 2 complete chains within one armed cycle.
