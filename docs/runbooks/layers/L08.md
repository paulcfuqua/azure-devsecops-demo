## Purpose

Deploy `copilot-svc` — the LLM tool-use loop (Anthropic API, decision locked at G1)
over exactly five tools: `query_lakehouse_sql`, `query_log_analytics`,
`get_github_security`, `get_defender_posture`, `get_cost_series`. Output is a JSON
component spec validated against the shared renderer schema **before** return —
never runtime-generated UI code. The golden-question eval suite (≥ 10 questions
whose answers derive exactly from the deterministic seed `20260822`, e.g. "which day
of the week has the most launches" → **Saturday**) is the layer's functional
contract. This is showpiece #1.

## Preconditions

- G0 complete + G1b granted; L7 Verifier PASS (renderer schema published; ACA env
  proven); L5 PASS (lakehouse SQL endpoint holds the seeded truth the evals assert).
- Orchestrator unblock for L8.
- `ANTHROPIC_API_KEY` present as the GitHub Actions secret and mirrored to Key
  Vault by L6 (spec F4: the system's only stored secret).
- **Capacity resumed for the eval window** — eval questions execute real lakehouse
  SQL. G2 statement filed for the resume (trial phase: $0 delta, still recorded;
  paid F2: ~$0.36/hr × window). Capacity re-paused at layer close (V5.4's standing
  rule; the Verifier re-checks capacity state at every layer close).
- `mls-verifier` holds workspace Viewer (granted at L5 [derived there]) so it can
  re-execute the copilot's SQL independently.
- Track F artifacts merged: 5-tool interface with mocked tool tests green; eval
  harness runs in mock mode; live-LLM smoke already done in Phase P if the key was
  provided early.

## Deploy procedure

1. Merge the L8 PR; path-filtered CI deploys it:

   ```
   .github/workflows/app-copilot-svc-ci.yml   # paths: apps/copilot-svc/**, apps/shared/**
   ```

   Build → unit tests (tool mocks, schema-validation guard) → container build →
   Trivy → OIDC deploy to ACA (`minReplicas: 0`), with `ANTHROPIC_API_KEY` injected
   as a Key Vault reference — the key never appears in Bicep, YAML, or logs.
2. Run the eval suite against the deployed service:

   ```
   gh workflow run copilot-eval.yml
   ```

   [derived] Dedicated eval workflow name — the master plan mandates the suite but
   not its workflow file. It resumes the capacity (G2 per Preconditions), runs the
   ≥ 10 golden questions against the live service, uploads
   `eval-results.json` (per-question: answer, spec, SQL executed, latency,
   tool-call trace), and re-pauses the capacity in a `finally` step.
3. Post eval run URL + results artifact to the Verifier.

## Validation cycle

Run by the Verifier as `mls-verifier` via `verification/layer-08-audit.ps1`. Report:
`verification/reports/L08-<date>.md`. The Verifier consumes the eval artifact as
*claims* and re-derives the facts itself.

### V8.1 — Eval suite ≥ 9/10 with valid schema output and Verifier-re-executed SQL

- **Criterion (master plan):** eval suite passes ≥ 9/10 with valid schema output
  and SQL that the Verifier re-executes against the lakehouse to confirm the
  numbers.
- **Query:** three independent re-checks over `eval-results.json`:

  ```powershell
  # (a) answers match golden expectations
  $r = gh run download <runId> -n eval-results | ConvertFrom-Json
  # (b) every returned component spec validates against the renderer schema
  npm --prefix apps/shared/spec-renderer run validate -- --stdin  # per spec
  # (c) re-execute each recorded SQL statement on the lakehouse SQL analytics
  #     endpoint as mls-verifier and compare result sets to the copilot's numbers
  ```

  For the canonical question the re-executed SQL must reproduce: "which day of the
  week has the most launches" → weekday argmax of `launches` = **Saturday** (the
  generator's built-in bias, pinned by Track A's distribution test).
- **Expected:** ≥ 9 of the ≥ 10 questions pass all three checks — correct answer,
  schema-valid spec, and SQL whose independent re-execution yields the numbers the
  copilot returned. A question failing any one check fails whole.
- **Retry/propagation:** one full eval re-run is permitted for infrastructure
  flakes (capacity paused mid-run, HTTP 429 from the LLM API), recorded in the
  report; answer-content failures are not retried away — nondeterminism in answers
  to deterministic questions is itself a defect.

### V8.2 — No tool call outside the allowlist

- **Criterion (master plan):** no tool call outside the allowlist.
- **Query:** over the eval artifact's complete tool-call trace:

  ```powershell
  $allow = 'query_lakehouse_sql','query_log_analytics','get_github_security','get_defender_posture','get_cost_series'
  $r.questions.toolCalls.name | Where-Object { $_ -notin $allow }
  ```

  plus a static grep of `apps/copilot-svc/` confirming no other tool is registered
  with the model.
- **Expected:** empty result from both — every call across every question is one of
  the five named tools; the service registers exactly five.
- **Retry/propagation:** none — deterministic over the recorded trace.

### V8.3 — p95 latency < 20 s

- **Criterion (master plan):** p95 latency < 20 s.
- **Query:**

  ```powershell
  $lat = $r.questions.latencySeconds | Sort-Object
  $p95 = $lat[[math]::Ceiling(0.95 * $lat.Count) - 1]
  ```

  [derived] p95 is computed over the eval suite's per-question end-to-end latencies
  (question in → validated spec out) — the master plan states the threshold but not
  the sample population; the eval run is the only controlled sample available.
- **Expected:** `p95 < 20.0` seconds, measured with the capacity resumed and the
  service warm (one discarded warm-up question precedes the timed set [derived]).
- **Retry/propagation:** if the p95 breach traces to a cold SQL endpoint or paused
  capacity mid-run, the single V8.1 infrastructure re-run covers this criterion
  too; a breach on a clean run is a FAIL.

## Teardown

- **Standard kill/rebuild cycle:** none of its own — `copilot-svc` lives in
  `mls-rg-apps`, deleted by `down.ps1`'s RG delete. **Gate class: gate-free.** The
  Key Vault secret reference disappears with `mls-rg-platform`; the GitHub secret
  `ANTHROPIC_API_KEY` persists (it is repo config, not cloud state) and re-seeds
  Key Vault on replay.
- Nothing G3 in this layer.

## Rollback

- **First validation failure:** Verifier files per-question specifics (which
  question, which of the three checks, observed vs expected). Lead fixes in the
  worktree — prompt/tool changes, SQL templates, schema guard — merges via PR, CI
  redeploys, eval re-runs. Cloud state needs no rollback: deploys are image
  replacements.
- **Never loosen the contract to pass:** editing golden expectations, widening the
  schema, or extending the latency budget to make a failing suite green requires a
  sponsor-approved change to the master plan, not a rollback action.
- Capacity hygiene: every rollback iteration's eval run ends re-paused; resumes are
  G2-stated each time.
- **Second consecutive failure of L8 → G4.**

## Failure modes

1. **LLM API auth/quota failure** (401 or sustained 429 mid-eval). Detection: eval
   artifact error entries; service 5xx on tool loop. Response: human checks the
   Anthropic console/key (G0 item C5); rotate the GitHub secret if invalid —
   credential failure recurring is G4 by definition.
2. **Capacity paused during eval** (SQL tool errors on every data question).
   Detection: tool-call trace shows `query_lakehouse_sql` failures; V8.1 collapse.
   Response: confirm the eval workflow's resume step ran and nothing re-paused
   concurrently (down.ps1 or another layer's close); re-run under the single
   infrastructure-retry allowance.
3. **Schema-invalid specs returned** (V8.1 check b failures). Detection: ajv
   errors in the audit. Response: the service must validate before return — an
   invalid spec escaping means the guard is broken or bypassed; fix the guard, and
   treat any "validate then mutate" code path as the bug.
4. **Eval regression under a model or prompt change** (< 9/10 on content).
   Detection: V8.1. Response: diff the failing SQL/answers against the last green
   artifact; pin the model version in config [derived: the service pins its model
   identifier in committed config so upgrades are deliberate PRs, not drift]; fix
   prompts/tools; re-run.
5. **Latency blowout (V8.3)** with correct answers. Detection: p95 ≥ 20 s on a
   clean run. Causes: oversized tool results (unbounded SELECT), sequential tool
   calls that could batch, cold starts inside the timed window. Response: profile
   per-question latency breakdown in the artifact; cap tool result sizes; keep the
   warm-up question policy honest (one, discarded, documented).

- **Pre-validated locally in Phase P (Track F):** the 5-tool interface with mocked
  tool tests; the schema-validation guard (unit-tested against golden and
  deliberately-broken specs); the eval harness end-to-end in mock mode; live-LLM
  smoke tests the moment the sponsor provides `ANTHROPIC_API_KEY` — all of V8.2's
  static half and the harness mechanics run today.
- **Deferred until tenant (named explicitly):** V8.1's live loop (real lakehouse
  SQL re-execution needs the L5 endpoint; three of the five tools —
  `query_log_analytics`, `get_defender_posture`, `get_cost_series` — have no live
  backend until L6/L9), V8.2's runtime trace against the deployed service, and
  V8.3's latency measurement on real infrastructure. Covered by
  `verification/layer-08-audit.ps1` at L8 deploy time.
