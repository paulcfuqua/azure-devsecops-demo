## Purpose

Ship showpiece #1 as a **custom Microsoft Copilot Studio agent** instead of a
self-hosted LLM service. Four parts, all authored in this repo:

1. **The agent** — a Power Platform solution held unpacked in `infra/copilot-studio/`
   and deployed by pipeline on Microsoft's
   [`copilot-alm-starter`](https://github.com/microsoft/copilot-alm-starter) GitHub
   Actions pattern (export → unpack → PR → import), authenticating with **workload
   identity federation**, so no secret is stored in CI. Agents live inside a Power
   Platform solution by construction, and a *custom* (non-default) solution is what
   makes them exportable between environments
   ([solutions in Copilot Studio](https://learn.microsoft.com/en-us/microsoft-copilot-studio/authoring-solutions-overview)).
2. **Knowledge — a Fabric data agent** over the `mls_operations` lakehouse, attached to
   the Copilot Studio agent as a *connected agent*. Fabric does the natural-language →
   SQL work natively (NL2SQL over Lakehouse/Warehouse), read-only by design
   ([concept](https://learn.microsoft.com/en-us/fabric/data-science/concept-data-agent)).
   **This integration is preview** — see Preconditions and the fallback below.
3. **Tools — an MCP server** on the L6 Container Apps environment carrying the same five
   tool implementations the old service had: `query_lakehouse_sql`,
   `query_log_analytics`, `get_github_security`, `get_defender_posture`,
   `get_cost_series` — plus a sixth added later, `query_compliance` (L12; it answers from
   the committed compliance state artifact baked into the same image, and has no
   cloud/local split), and a **seventh added 2026-09-16**, `query_aws_lakehouse_sql`
   (the cross-cloud Athena link; it is **gated on configuration**, so a server whose six
   AWS settings do not resolve inside the running process advertises six rather than
   seven). Copilot Studio connects over the **Streamable** transport; SSE is
   deprecated upstream and
   [Copilot Studio no longer supports SSE for MCP after August 2025](https://learn.microsoft.com/en-us/microsoft-copilot-studio/mcp-add-existing-server-to-agent).
4. **Surface — a Direct Line embed** in the control tower's **Ask** tab, rendering
   **Adaptive Cards**: declarative JSON UI, never runtime-generated code. The browser
   holds no credential: `apps/directline-token` (a consumption-plan Function) reads the
   Direct Line secret from Key Vault and exchanges it for a short-lived,
   conversation-scoped token with `trustedOrigins` pinned to the control tower's origin.
   The governance story is unchanged, told in Microsoft's idiom; `@mls/spec-renderer`
   still draws the apps' own dashboards.

The golden-question eval suite (≥ 10 questions whose answers derive exactly from the
deterministic seed `20260822`, e.g. "which day of the week has the most launches" →
**Saturday**) remains the layer's functional contract, now driven through Direct Line
against the deployed agent.

### Documented fallback — tools-only, no Fabric knowledge source

If the Fabric data agent is unavailable — preview withdrawn or changed, capacity still
on the trial SKU, region-limited, or the connected-agent path misbehaving over Direct
Line — **the layer still ships**. Remove the connected Fabric data agent from the
solution and let the agent answer lakehouse questions through the MCP server's
`query_lakehouse_sql` tool against the lakehouse SQL analytics endpoint. This is a
solution-level configuration switch committed in the repo, not a rebuild: the same
tools, the same Adaptive Cards, the same golden questions, the same expected answers.
What is lost is Fabric's native NL2SQL — the MCP tool executes SQL that the repo owns
rather than SQL that Fabric generates. Record which path was used in the audit report;
both paths must pass V8.2 identically, and the report names the path so the Verifier's
evidence is unambiguous.

A second, narrower fallback exists for the surface alone: Microsoft states the
connected-Fabric-data-agent combination is
[only validated for Microsoft Teams](https://learn.microsoft.com/en-us/fabric/data-science/data-agent-microsoft-copilot-studio),
with other channels untested. If the knowledge source works but the Direct Line embed
does not, publish the Teams channel for the demo and keep the Ask tab on the tools-only
path.

## Deploy procedure

1. Merge the L8 PR. Two things deploy from it, in this order:

   ```
   .github/workflows/app-mcp-tools-ci.yml       # paths: apps/mcp-tools/**
   .github/workflows/layer-08-copilot-studio.yml
   ```

   [derived] Both workflow names instantiate the master plan's `app-<name>-ci.yml` and
   `layer-<nn>-*.yml` patterns; the plan names the deploy paths, not the files.
2. **MCP server first.** `app-mcp-tools-ci.yml` runs build → unit tests → container
   build → Trivy → OIDC deploy to ACA with `minReplicas: 0`. It must be reachable before
   the agent imports, because the solution's MCP tool connection is validated on import.
   Record the server's HTTPS FQDN — the solution carries it as an environment variable so
   a rebuilt ACA environment can be repointed without editing the agent (see Failure
   mode 5).
3. **Agent solution.** `layer-08-copilot-studio.yml` packs `infra/copilot-studio/` and
   imports it into the Power Platform environment using federated credentials, then
   publishes the agent. Nothing in this step is done in the browser: portal authoring is
   how drift starts, and V8.1 is written to catch it.

   > **The import job prints "L8 — imported, NOT yet live" and exits `success` anyway.**
   > That is by design and it is also the layer's sharpest trap: a green L8 has never meant
   > a live agent. The manual steps it lists are in
   > `infra/copilot-studio/README.md` § 6 and are restated in the run summary. **Work
   > through them; do not read the job's green tick as a deploy.**

3a. **Enable every tool on the MCP connection, then publish.** After the connector is
   created or its server's tool set has changed, open **Tools → the MCP server** and
   confirm that **all seven** tools are toggled **on**. A tool the connector has newly
   *discovered* arrives **disabled** — see **F202** under V8.3 — and a disabled tool
   behaves exactly like an absent one: the agent answers from whatever source remains,
   confidently and with a plausible citation. Saving is not sufficient: **publish**, or the
   change does not reach the published agent Direct Line serves.

   Verify by arithmetic, not by appearance. Ask *"how many rows are in the launches
   table?"* — a correct agent names **both** lakehouses and gives **1,200** for Meridian's
   synthetic operations data and **286,473** for the AWS launch-intelligence data. A single
   unqualified 1,200 means the AWS tool is not reachable, whatever the tool list shows.
4. **Connect the knowledge source** (paid-F2 path only). The Fabric data agent is
   attached as a connected agent inside the solution, with **generative orchestration
   on** — the connected-agent path does not fire without it. On the trial capacity, skip
   to the fallback configuration instead and note it in the run summary.
5. **Light up the Ask tab.** Flip the control tower's `ASK_TAB_ENABLED` configuration on
   (its Direct Line secret reference was provisioned at L6). The tab was shipped dark at
   L7 precisely so this is a config change, not a redeploy.
6. Run the eval suite against the deployed agent:

   ```
   gh workflow run copilot-eval.yml
   ```

   [derived] Dedicated eval workflow — the master plan mandates the suite but not its
   workflow file. It resumes the capacity (G2 per Preconditions), opens one Direct Line
   conversation, asks the ≥ 10 golden questions, uploads `eval-results.json`
   (per question: answer, Adaptive Card payload, tool-call trace, latency, and the path
   used — `fabric-data-agent` or `mcp-tools-only`), and re-pauses the capacity in a
   `finally` step.
7. Post the eval run URL, the results artifact, and the deployed solution version to the
   Verifier.

## Validation cycle

Run by the Verifier as `mls-verifier` via `verification/layer-08-audit.ps1`. Report:
`verification/reports/L08-<date>.md`. The Verifier consumes the eval artifact as
*claims* and re-derives the facts itself.

### `pac` is installed but not on the PATH (F113)

Recorded 2026-09-01 because it cost two runs, and the second was my own fault.

`microsoft/powerplatform-actions/actions-install` drops the CLI in a temporary tool-path
and exports `POWERPLATFORMTOOLS_PACPATH`. **It does not add it to `PATH`.** Every bare
`pac` call — two in this workflow and eighteen more inside
`infra/copilot-studio/import-agent.ps1` — therefore failed with

    line 5: pac: command not found
    ##[error]Process completed with exit code 127

immediately after a step that logged `pac installed to /tmp/...`. It reads like a missing
install and is the opposite.

The workflow now puts the directory on `PATH` once, which fixes every caller, and a laptop
run where `pac` is already on `PATH` is unaffected. Two details are load-bearing:

- **The variable's shape is resolved, not assumed.** It is documented as neither a file nor
  a directory, and the observed value is `/tmp/powerplatform-actions-XXXX/pac` — a path
  whose last segment is literally `pac`, so "executable" and "tool-path directory" are
  genuinely ambiguous. `dirname` is right for one and silently wrong for the other, and the
  wrong one would put the *parent* on `PATH` and reproduce exit 127 through a step that
  logged success. Both shapes are handled.
- **The step proves the capability by using it.** `pac help` runs over the `PATH` just
  built. The first version of this check ran `pac --version`, which is **not a valid pac
  command** — it exits 1 with `Parse failed on: --version` — so the step failed on the very
  run that proved the PATH fix worked. Written from memory instead of checked against the
  tool: the exact defect this repository spends its budget catching, committed inside the
  step whose only purpose is verification.

### V8.1 — Deployed agent matches the committed solution

- **Criterion (master plan):** deployed agent's solution unique name + version +
  component list match the committed solution exactly, and its published state is
  current.
- **Query:** read the deployed solution from Dataverse as `mls-verifier` (read-only) and
  compare against the repo at the audited commit:

  ```powershell
  # deployed: Dataverse Web API, solutions + solutioncomponents
  $dep = Invoke-RestMethod "$envUrl/api/data/v9.2/solutions?`$filter=uniquename eq '$name'" -Headers $verifierAuth
  $cmp = Invoke-RestMethod "$envUrl/api/data/v9.2/msdyn_solutioncomponentsummaries?`$filter=msdyn_solutionid eq $($dep.value[0].solutionid)" -Headers $verifierAuth
  # committed: the unpacked solution in the repo
  Select-Xml -Path infra/copilot-studio/Other/Solution.xml -XPath '//Version','//UniqueName'
  ```

- **Expected:** unique name and version identical; the deployed component set is exactly
  the committed component set (set equality — an extra component is drift, a missing one
  is a failed import). **The committed set is read from THREE files, not one (F145):**
  `Other/Solution.xml`'s RootComponents, every `botcomponents/*/botcomponent.xml` `<name>`,
  and the logical names in `Assets/botcomponent_connectionreferenceset.xml`. Reading only
  the first compares 1 component against the 17 Dataverse reports, which can never be
  equal — the criterion failed for days naming sixteen legitimate topics as drift. If the
  component files cannot be enumerated the criterion reports **UNOBSERVABLE**, because a
  truncated expected set turns every deployed component into an "extra". Also: the agent's
  published-on timestamp is later than the import that
  the L8 run produced. **No unmanaged layer** on the agent component: an unmanaged layer
  means somebody edited the agent in the browser after the pipeline imported it, which
  fails principle 1 and fails this criterion.
- **Retry/propagation:** solution import and publish are synchronous per the workflow;
  allow one re-read at +5 minutes for Dataverse read replication, no longer.

### V8.2 — Eval suite ≥ 9/10 with Verifier-re-derived numbers

- **Criterion (master plan):** eval suite passes ≥ 9/10 against the deployed agent, with
  each answer's number independently re-derived by the Verifier from the lakehouse.
- **Query:** two independent checks per question, over `eval-results.json` and the
  lakehouse:

  ```powershell
  $r = gh run download <runId> -n eval-results | ConvertFrom-Json
  # (a) the agent's answer equals the golden expectation
  # (b) the Verifier re-derives the number itself: run the eval fixture's pinned
  #     reference SQL on the lakehouse SQL analytics endpoint as mls-verifier and
  #     compare to the agent's stated figure
  ```

  For the canonical question the re-derived answer must be: "which day of the week has
  the most launches" → weekday argmax of `launches` = **Saturday** (the generator bias,
  pinned by Track A's distribution test).
- **Expected:** ≥ 9 of the ≥ 10 questions pass both checks. The reference SQL lives in
  the committed eval fixture, not in the agent — this is deliberate: on the Fabric
  data-agent path the SQL is generated inside Fabric and never exposed to us, so the
  audit must re-derive truth from the seed rather than re-execute the agent's own query.
  The criterion is therefore identical on both paths.
- **Retry/propagation:** one full eval re-run is permitted for infrastructure flakes
  (capacity paused mid-run, Direct Line 5xx, MCP cold start), recorded in the report.
  Answer-content failures are not retried away — nondeterminism on deterministic
  questions is itself a defect.
- **The eval can now grade, which it could not for the life of this project (F184).** Run
  `35166952968`, 2026-09-17T00:37:22Z, over Direct Line against the deployed agent:
  **9 / 10 passed, bar 9, `unobservable: 0`**, path `mcp-tools-only`. For a fortnight this
  eval returned 0/10 with zero tool calls and could not tell an unhealthy agent from an eval
  that was not allowed to reach a healthy one. It now returns facts.
  **This is the eval's own artifact, not a V8.2 verdict** — V8.2 was `(not selected)` in
  that run, and V8.2's second half is the Verifier re-deriving each number from the
  lakehouse, which has not happened. The next unfiltered L8 audit is what turns it into a
  verdict.
  Two details from the artifact worth carrying:
  - `toolCalls` is `[]` on every question. Direct Line does not expose the orchestrator's
    tool trace, so **V8.3's runtime half is unobservable through this transport** — the
    numbers in the answers are the evidence that tools ran, not the trace.
  - The single failure was `worst-supplier`, and it failed by **declining**, not by being
    wrong: *"I'm sorry, I'm not sure how to help with that."* That is the
    ungrounded-responses-Off fallback, so the honest reading is "the agent did not reach the
    data", not "the agent stated a false supplier".

### V8.3 — No tool outside the declared allowlist

- **Criterion (master plan):** no tool invoked outside the five-tool allowlist and the
  agent declares exactly those five.
- **The allowlist is seven names now, not five, and the criterion is unchanged.** The master
  plan was written on 2026-08-22, when the MCP server carried five tools. The 2026-08-26
  compliance-platform design added a sixth, `query_compliance`
  (`docs/superpowers/specs/2026-08-26-compliance-platform-design.md` § 5.3, decision D5),
  and the 2026-09-16 cross-cloud link added a seventh, `query_aws_lakehouse_sql`.
  `apps/mcp-tools/tests/allowlist.test.ts` pins the server at **exactly seven**. What the
  criterion asserts — nothing runs outside the *declared* allowlist, and the agent declares
  exactly what is on it — is untouched; only the count moved.
  `verification/layer-08-audit.ps1`'s `-AllowedTool` default carries all seven, and compares
  as a **set**, so a deployed server still advertising the old six fails V8.3 for being
  short just as loudly as one advertising an eighth. A Pester cross-check compares that
  PowerShell default against `apps/mcp-tools/src/tools/index.ts` so the two lists cannot
  drift silently. The verbatim master-plan wording is
  kept above, and in this directory's traceability table, because renumbering a criterion
  to match a later change is how traceability quietly stops meaning anything.
- **Query:** runtime plus static, both required:

  ```powershell
  $allow = 'query_lakehouse_sql','query_aws_lakehouse_sql','query_log_analytics',
           'get_github_security','get_defender_posture','get_cost_series','query_compliance'
  # runtime: every tool call recorded across every eval question
  $r.questions.toolCalls.name | Where-Object { $_ -notin $allow }
  # static: what the MCP server advertises
  #   MCP tools/list against the deployed server → exactly those seven names
  # static: what the solution attaches
  #   grep the unpacked solution for tool/connector components; expect the one MCP
  #   connection and (on the Fabric path) the one connected data agent — nothing else
  ```

- **Expected:** empty result from the runtime filter; `tools/list` returns exactly those
  seven names; the solution declares no additional tool, connector, agent flow, or
  knowledge source beyond the MCP connection and, on the Fabric path, the single
  connected data agent.
- **Adding a tool to the server is NOT enough to make the agent use it — see F202 below.**
  This section used to end with *"the agent itself needs no re-authoring for the sixth
  tool — the Copilot Studio tool list refreshes dynamically from the server."* **That
  sentence was false, and the post-import checklist is where it is now repaired.**
- **Retry/propagation:** none — deterministic over the recorded trace and the deployed
  artifacts.

#### F202 — a newly discovered tool arrives DISABLED, and a disabled tool is indistinguishable from an absent one

**Recorded 2026-09-16 because a rebuild walks straight back into it.** The old claim above
was written when `query_compliance` became the sixth tool — but that happened **before the
MCP connector was ever built**, so "the list refreshes dynamically" had never once been
tested by adding a tool to an *existing* connection. 2026-09-16 was its first real test and
it failed in a way neither half of the claim describes.

Seven tools were listed. The seventh was **present and switched OFF**. The agent therefore
answered a launch-provider question from **Fabric's 1,200 rows** while citing a table that
does not exist in the AWS Glue catalog — correct-looking, confidently sourced, and from the
wrong lakehouse. Nothing about the tool list's *length*, and nothing about the generative
orchestration setting, distinguishes that state from a working one. A human found it by
adding up the numbers. Fixing it took a toggle **and a publish**: a save alone did not reach
the published agent.

Three consequences, all of which belong to anyone re-importing this solution:

1. **This is F119's class in another system.** A thing that exists but is not enabled
   produces behaviour identical to a thing that is absent.
2. **The tool description had already done its discrimination job.** It says in terms that
   the AWS source is real provider data, that Fabric is synthetic and belongs to a different
   organisation, and that the two must never be mixed. An orchestrator that had seen that
   text could not reasonably have answered 1,200. It never saw it.
3. **Only arithmetic discriminates the two lakehouses.** Both have a `launches` table and
   both return plausible vehicle names, because the synthetic data deliberately uses real
   public vehicle names. Any future check of this link asserts a **number** — 1,200 versus
   286,473 — never a plausible-looking answer. That is what V8.6 is for.

**Bounded by measurement, 2026-09-17.** A subsequent solution re-import (run `35166952968`,
00:32Z) did **not** disable the tool again: the golden-question eval run 5 minutes later
returned live AWS figures (286,473 launches; 57,622 for the modal weekday) that appear
nowhere in the agent's prompt. So the hazard observed is a **newly discovered** tool
arriving disabled, not every import resetting every tool. Treat the post-import step as
required after any change to the MCP server's tool set, and cheap to perform otherwise.

### V8.4 — Every visual answer is a schema-valid Adaptive Card

- **Criterion (master plan):** every visual answer is an Adaptive Card payload that
  validates against the pinned Adaptive Cards schema; zero HTML/JS/JSX in any response.
- **Query:**

  ```powershell
  # (a) each recorded card payload validates against the Adaptive Cards 1.5 schema
  npx ajv validate -s verification/schemas/adaptive-card-1.5.json -d card.json
  # (b) no response body contains generated UI code
  $r.questions.responses | Where-Object { $_ -match '<script|<div|=>\s*\(|React\.' }
  ```

- **Expected:** every card validates; `"type": "AdaptiveCard"` with `"version": "1.5"`
  on each; no `Action.Execute` anywhere (the Bot Framework Web Chat component behind the
  Direct Line embed
  [supports schema 1.6 but not `Action.Execute`](https://learn.microsoft.com/en-us/microsoft-copilot-studio/adaptive-cards-overview),
  and Teams — the fallback channel — is limited to 1.5, so [derived] the repo pins 1.5
  and `Action.Submit` so one payload renders in both); the code-grep returns empty. A
  single generated-UI response fails the criterion outright — that is the governance
  claim the demo makes on stage.
- **Retry/propagation:** none — deterministic over the recorded payloads.

### V8.5 — p95 latency < 20 s

- **Criterion (master plan):** p95 latency < 20 s.
- **Query:**

  ```powershell
  $lat = $r.questions.latencySeconds | Sort-Object
  $p95 = $lat[[math]::Ceiling(0.95 * $lat.Count) - 1]
  ```

  [derived] p95 is computed over the eval suite's per-question end-to-end latencies
  (Direct Line activity posted → final agent activity received) — the master plan states
  the threshold but not the sample population, and the eval run is the only controlled
  sample available.
- **Expected:** `p95 < 20.0` seconds, measured with the capacity resumed, the MCP
  container warm, and the Direct Line conversation already open (one discarded warm-up
  question precedes the timed set [derived]). Note for the record: the Fabric
  data-agent path adds an agent-to-agent hop the tools-only path does not, so the two
  paths are timed separately and the report states which one the number describes.
- **Retry/propagation:** if the breach traces to a cold MCP replica or a paused capacity
  mid-run, the single V8.2 infrastructure re-run covers this criterion too; a breach on a
  clean run is a FAIL.
- **Observed 2026-09-17T00:37:22Z, and it is over budget: p95 = 34.18 s.** From the eval
  artifact of run `35166952968` (`agent-eval-results.json`, `p95LatencySeconds: 34.177`).
  **This is not a V8.5 verdict** — V8.5 was `(not selected)` in that run's audit — it is the
  eval's own number, and the eval harness prints it against the 20 s budget itself.
  Two things about it are worth knowing before anyone re-runs:
  - The p95 **is** the maximum here: 10 questions, and the slowest was the **first**
    (34.18 s against 3.3–11 s for the other nine). That is the cold-start signature this
    section's *"one discarded warm-up question precedes the timed set"* note exists to
    remove, and that warm-up did not happen. Cold start on `minReplicas: 0` was measured at
    26.9 s, and the AWS path adds an Athena submit/poll/retrieve on top.
  - The disambiguation behaviour shipped on 2026-09-16 makes an ambiguous question query
    **both** lakehouses, so the honest answer costs roughly twice the work of the wrong one.
    That is a deliberate trade and it eats into this budget; measure it warm before
    concluding anything about the agent.

### V8.6 — The AWS Athena lakehouse answers with ROWS, not with a status code

- **Criterion [derived, 2026-09-16 aws-lakehouse-link]:** V7.6's rule, one cloud over.
  L7 signed off 5/5 for two days over an estate whose every `/api/tables` route answered
  503, because no criterion read a row. The AWS link began answering on 2026-09-16 —
  286,473 rows in 4,431 ms through the live MCP endpoint — and the evidence was a scratch
  script that no longer exists. An estate that answers from AWS with no criterion
  asserting it is one teardown from `docs/DEMO-READINESS.md` § D's position.
- **Query:**

  ```
  GET  <mcpServerUrl>/healthz                      # is query_aws_lakehouse_sql DECLARED?
  POST <mcpServerUrl> tools/call query_aws_lakehouse_sql {"sql":"SELECT COUNT(*) AS n FROM launches"}
  POST <mcpServerUrl> tools/call query_aws_lakehouse_sql {"sql":"SELECT COUNT(*) AS n FROM launches_latest"}
  ```

- **Expected:** the deployed server declares the tool, the base table counts at or above
  its floor, and the **view** does too. The view is queried on purpose: a Glue view needs
  `glue:GetTable` on its *own* ARN, so a role built from the base-table names answers
  every base-table question perfectly and `AccessDenied`s this one — the partial failure
  that reads like a data problem in front of an audience.
- **Floors, not equalities.** This lakehouse belongs to the sponsor and refreshes from an
  upstream launch feed, so a pinned count is guaranteed to go stale and a stale equality
  **fails on correct data**. V5.3 owns exact counts, over a dataset this repo seeds.
- **The `/healthz` half needs no credential, and is never a pass on its own.** The tool
  registers only when all six AWS settings resolve *inside the running process*, so a
  rebuild whose settings never reached the container advertises six tools rather than
  seven and fails here. But an empty lakehouse and a broken link both declare exactly the
  same thing, which is why declaring it is necessary and nowhere near sufficient.
- **Credential:** the MCP endpoint is behind `mcp-auth-token`. The audit takes it as an
  explicit input only (`-McpAuthToken` / `$env:MLS_MCP_AUTH_TOKEN`), never from a vault;
  without it the criterion reports **SKIP** naming what is missing.
- **Wired 2026-09-17, and the wiring is half reproducible.** The L8 verify job now reads
  that one secret as `mls-verifier` and passes it in, so V8.6/V8.7 no longer skip.
  `mls-verifier` holds **Key Vault Secrets User scoped to the single secret**
  `.../vaults/mls-sec-demo-kv/secrets/mcp-auth-token` — not to the vault, which also holds
  the Direct Line secret and data-api's PAT. **That grant is expressed in
  `infra/bicep/apps/modules/key-vault-secret-role.bicep` and has never been deployed**: the
  live assignment is the hand-applied one from 2026-09-16, and the last `layer-07-apps` run
  predates the template. Until an L7 deploy applies it, a teardown erases the grant and
  V8.6/V8.7 return silently to SKIP — F159's class, with a criterion as the casualty.

- **First verdict, 2026-09-17T00:38:07Z** — `layer-08-copilot-studio` run `35166952968`,
  branch `tmp/l8-credentialed-verify`, verify job running as `mls-verifier`:
  **V8.6 PASS · V8.7 PASS.** The job renders as a red X: the audit exits **3** on a filtered
  `-OnlyCriterion` run, deliberately, so nothing downstream can mistake a diagnostic for a
  sign-off, and GitHub only knows zero from non-zero. V8.1–V8.5 reported `(not selected)`
  in that run and **have no verdict from it**.
- **Passing once is an observation, not a property.** Both criteria have run against exactly
  one estate, which has not been torn down since they existed. A rebuild is what converts
  them.
- **Retry/propagation: 4 minutes, poll 30 s, and the number is chosen rather than
  inherited.** It waits on a Container Apps scale-from-zero cold start (900 s cooldown)
  and on Athena being asynchronous — submit, poll, retrieve. Nothing here waits on Entra
  or policy propagation.

### V8.7 — A denial is never reported as an empty dataset

- **Criterion [derived, 2026-09-16 aws-lakehouse-link]:** F105's exact shape, one cloud
  over. Fabric answered `/tables` with `[]` to a caller without OneLake read, and the
  audit called the lakehouse empty while its SQL endpoint held 1,200 rows. Athena against
  a Glue database the role cannot read can answer **emptily** rather than 403.
- **Query:**

  ```
  POST <mcpServerUrl> tools/call query_aws_lakehouse_sql
       {"sql":"SELECT table_name, table_type FROM information_schema.tables WHERE table_schema = '<glueDatabase>'"}
  ```

  The database name is resolved from the **running container's** own `MLS_GLUE_DATABASE`
  when not supplied, because a value the estate derives cannot disagree with the estate
  (F129). Unresolvable → UNOBSERVABLE, never "the catalog is empty".
- **Expected:** a non-empty listing carrying the table and the view V8.6 queries — that
  expected set is *derived from V8.6's own parameters*, not a second list (F145).
- **The verdict table, which is the criterion:**

  | what came back | verdict |
  |---|---|
  | transport failure, auth gate, HTTP 429, 5xx, no JSON-RPC envelope | **UNOBSERVABLE** |
  | a refusal from the tool | **FAIL — DENIED**, never "the lakehouse has no tables" |
  | **zero rows** | **UNOBSERVABLE** — an empty listing is what Athena returns *both* for a database with no tables *and* for one this role may not read |
  | a readable listing missing a name | **FAIL**, observed missing |
  | a readable listing with the names | **PASS** |

  It is structurally incapable of reporting the link absent when it could not look, and
  equally incapable of reporting it present — an auditor that cannot see a control must
  not be able to claim it either way.
- **A throttle is not an answer.** `az containerapp exec` returns HTTP 429 with
  `retry-after: 600` after roughly three calls, and a throttled response looks exactly
  like an empty value; two present environment variables were nearly recorded as absent
  on that basis. Athena and STS refuse under load the same way, so a throttled tool error
  classifies as UNOBSERVABLE rather than as a result.
- **Retry/propagation: 2 minutes**, shorter than V8.6 deliberately — catalog metadata with
  no S3 scan behind it, on a container V8.6 has already woken. Propagation is shared wall
  clock; the second criterion does not start it again.

## Teardown

- **Standard kill/rebuild cycle:** the MCP server lives in `mls-rg-apps` and dies with
  `down.ps1`'s RG delete. **Gate class: gate-free.** Nothing else in this layer is
  touched by the standard cycle.
- **The agent and its solution persist**, deliberately, in the same spirit as Entra
  objects and the Fabric workspace shell: they are not RG-scoped, re-import + re-publish
  + channel reconfiguration does not fit inside the 60-minute rebuild claim, and the
  Direct Line secret would have to be re-issued and re-vaulted by a human every cycle.
- **Two things inside the agent do not persist**, and the rebuild's L8 leg repairs both
  before the eval runs:
  1. the **MCP server** and therefore its FQDN (Failure mode 5), and
  2. on the paid-F2 path, the **Fabric data agent** — it is a workspace item, so
     `infra/fabric/teardown-items.ps1` deletes it with the lakehouse (L05 § Teardown).
     The leg recreates and republishes it, then repoints the agent's connected
     reference. On the tools-only fallback path there is nothing here to repair.
- **Deleting the agent, its solution, the Power Platform environment, or the
  pay-as-you-go billing link is G3** — tenant-level, per-occurrence human approval,
  exactly like deleting the Fabric workspace. `down.ps1` contains no code path that can
  reach any of them; that separation is structural, not a runtime flag.
- The Key Vault secret reference disappears with `mls-rg-platform` and is re-seeded from
  the value the human vaulted at G0 on replay.

## Rollback

- **First validation failure:** Verifier files per-criterion specifics (which question,
  which check, observed vs expected, and which path the run used). The lead fixes in the
  worktree — solution content, agent instructions, MCP tool implementation, card
  templates — merges via PR, the pipeline re-imports and re-publishes, the eval re-runs.
- **Never fix it in the browser.** A portal edit will make the eval pass and V8.1 fail,
  and it breaks the demo's central claim. If an emergency portal change is ever made, the
  only valid follow-up is to export it back into the repo through
  `copilot-studio-export.yml` [derived name, per the ALM starter's `export-solution.yml`]
  and remove the unmanaged layer.
- **Never loosen the contract to pass:** editing golden expectations, widening the card
  schema, or extending the latency budget to make a failing suite green requires a
  sponsor-approved change to the master plan, not a rollback action.
- Falling back to the tools-only path is a legitimate rollback action **only** when
  Preconditions justify it (preview/capacity/region), and it is recorded in the report
  with the reason — not used to sidestep a genuine quality failure on the Fabric path.
- Capacity hygiene: every rollback iteration's eval run ends re-paused; resumes are
  G2-stated each time.
- **Second consecutive failure of L8 → G4.**

## Failure modes

1. **Fabric data agent not offered in Copilot Studio's picker.** Detection: the connected
   agent step in the solution import fails, or the data agent is simply absent from the
   list. Causes, in the order worth checking: capacity is trial rather than paid F2 (the
   commonest, and permanent until G2); data agent not published; different tenant or a
   different signed-in account; missing read access to the data agent or its underlying
   sources; cross-geo AI tenant settings off. Response: run the documented tools-only
   fallback and record the cause. This is the preview risk (register item 6) materialising
   and it is expected, not exceptional.
2. **MCP connection fails on import or at runtime.** Detection: solution import error on
   the connector component, or `tools/list` empty at runtime. Causes: the server URL in
   the solution points at a dead FQDN (see mode 5); the server offers SSE rather than
   Streamable HTTP — Copilot Studio dropped SSE for MCP after August 2025 and will not
   negotiate it; OAuth 2.0 configuration mismatch (callback URL not registered on the
   Entra app). Response: fix the transport or the app registration; both are repo/portal
   configuration, and the OAuth callback URL is the one value that must be copied back
   into the Entra app after the connector is created.
3. **Agent answers but the Ask tab shows nothing.** Detection: eval green over Direct
   Line while the browser tab is silent. Causes: the agent was not (re)published after
   import — Direct Line serves the *published* agent, not the authoring copy; the Direct
   Line secret in Key Vault is stale; secured-access settings on the web channel reject
   the token. Response: republish, re-vault, re-check `configure-web-security` settings.
4. **Cards render as plain text or not at all.** Detection: V8.4 passes on payload
   validity but the stage picture is wrong. Cause: a card using `Action.Execute` or a
   1.6-only element in the Web Chat host, or a 1.6 card that only renders in Copilot
   Studio's own test chat. Response: hold the 1.5 + `Action.Submit` pin; test in the Ask
   tab, never only in the Copilot Studio test chat, which is more permissive than the
   real surface.
5. **Rebuilt ACA environment gives the MCP server a new FQDN.** Detection: after a
   kill/rebuild, the agent's tool calls fail while the agent itself is healthy. Cause:
   the Container Apps environment's generated domain suffix changes when the RG is
   recreated, so the solution's stored server URL no longer resolves. Response: the L8
   rebuild leg repoints the connection from the environment variable recorded in deploy
   step 2 rather than by hand [derived — the master plan does not address this; it is a
   direct consequence of the agent outliving the RGs]. This is the one genuinely new
   moving part the amendment introduced into the rebuild path; the kill/rebuild runbook
   carries it as leg 6.
6. **Copilot Credit enforcement disables the agent mid-demo.** Detection: users see
   "This agent is currently unavailable. It has reached its usage limit." Cause: the
   environment is not actually on the pay-as-you-go meter (billing plan missing, or the
   environment is a Developer-Plan environment that cannot carry one), so it is drawing
   on prepaid capacity and hit
   [the 125 % overage enforcement threshold](https://learn.microsoft.com/en-us/microsoft-copilot-studio/requirements-messages-management).
   Response: confirm the environment is listed under the billing plan in the Power
   Platform admin center — with pay-as-you-go, overage bills to Azure instead of blocking.
   Set a per-agent monthly consumption cap there as a cost backstop.
7. **Eval regression after a solution change.** Detection: V8.2 below 9/10 on content.
   Response: diff the failing answers against the last green artifact; the agent's model
   is Microsoft-managed and not pinnable — treat instructions, example
   question/query pairs on the data agent, and tool descriptions as the tunable surface,
   and change one at a time so the eval attributes the regression.

## What it took to make this layer answer (2026-09-02)

The Ask tab went from *"not configured"* to answering a real question from the lakehouse.
Ten findings stood in the way, and they are recorded in full in `docs/DEMO-READINESS.md`.
What belongs **here** is the shape of them, because a future L8 change will meet the same
shapes:

| | What was wrong | Why it was invisible |
|---|---|---|
| **F122** | the Key Vault reference resolved to nothing | `appsettings list` prints the reference back whether or not it resolves |
| **F124** | the bundle carried no token URL | the image was built *after* the variable was set, and still lacked it — the build job declared no environment |
| **F128** | agent used integrated auth | Direct Line cannot do it; the error named a mode, not a fix |
| **F129** | the connector pointed at a **dead Container Apps environment** | that domain segment is random per environment, so the literal could not survive a rebuild |
| **F130** | a green import that deployed nothing | `import-agent.ps1` is idempotent on the solution **version**, and the fix changed content |
| **F131** | the repo carried the settings that break Direct Line | every import silently reverted the hand-applied fix |
| **F133** | the tool server read `data/generated` | it shipped in `local` mode; the directory is not in the image |
| **F134** | mcp-tools had **no Fabric role at all** | dormant while it was in local mode and never asked Fabric for anything |
| **F135** | Easy Auth token store off | `/.auth/me` returns claims and no raw token |
| **F136** | the Functions host owns the `OPTIONS` preflight | CORS worked for every request except the one the browser asks permission for first |

**Three rules fall out of that list, and they are cheap to follow:**

1. **Change one thing, then look.** Every wrong diagnosis in that sequence came from
   inferring a cause instead of reading the state that decides it. The connector host was
   found only by opening the tool's own error detail; the auth mode by querying Dataverse;
   the CORS failure by reading a preflight response.
2. **A manual fix in Copilot Studio is temporary.** The solution is the source of truth and
   an import restores it — `agent-definition.md` §7.1 said imports leave auth *blank*, and
   it was wrong. Change the solution, then import; do not change the portal and hope.
3. **Bump the solution version whenever content changes**, or the import will report success
   and do nothing.
