## Purpose

Render, for NIST SP 800-171 Rev 2 and the frameworks that map onto it, which requirements
this estate meets, which it does not, what the evidence is in each case, and — the part
that makes it worth building — **which of those answers a machine checked and which a
human merely asserted**. A compliance tool that blurs those two launders a gap into a
green box, so the whole layer is built around not doing that.

Four things ship here:

1. **`compliance/`** — the 110-requirement catalog with its 800-53 Rev 5 / CMMC 2.0 /
   FAR 52.204-21 mappings, the assessment register, the pure derivation function
   (`lib/MlsCompliance.psm1`), five collectors, and the state emitter
   (`Invoke-MlsCompliance.ps1`).
2. **`.github/workflows/compliance.yml`** — collects the state on every push to `main`,
   nightly at 02:17 UTC, and on dispatch, and **commits** the dated artifact, so
   `git log compliance/state/` is the record of when the estate became compliant and when
   it regressed.
3. **`apps/compliance`** — a static Fluent UI board (`mls-compliance-demo-ca`) behind
   Container Apps Easy Auth, rendering the committed artifact that was baked into its
   image at build time.
4. **`query_compliance`** — the sixth tool on the L8 MCP server, answering from the same
   artifact, returning authored recommendations verbatim and never extrapolating.

**What the board says today, and why that is the deliverable.** Nothing in this estate
has ever been deployed. So the board reports **0 COMPLIANT · 15 PARTIAL · 1 GAP ·
0 INCONCLUSIVE · 0 NOT_APPLICABLE · 94 NOT_ASSESSED** of 110, plus 4 out-of-catalog
800-53-keyed rows, and it says on its own face that the `verification-suite` collector
found no reports because nothing has been deployed. **A green board at this stage would
be a defect, not a milestone** — it would mean the platform had invented a claim. The
pre-deployment board is precisely what makes a post-deployment board mean anything.

(This line read "12 PARTIAL · 3 GAP · 95 NOT_ASSESSED" until 2026-08-29 and was stale
twice over: F19 had already moved 3.1.1, 3.1.2 and 3.1.5 from GAP to PARTIAL, and the
enforced-MFA work then added `3.5.3` as an assessed **GAP**. `compliance/README.md`
carries the same counts; both are derived from `compliance/state/state-latest.json`,
which is the only place they are computed.)

## Preconditions

- **None for the collection half.** `Invoke-MlsCompliance.ps1` is read-only, offline, and
  needs no credential and no tenant. `compliance.yml` therefore carries no pre-G0 guard
  and is green from the first push. A collector that collected nothing is recorded as
  having collected nothing (`collectors[].recordCount = 0`), which is a different and more
  useful statement than its absence.
- **For the board's container app:** G0 complete + G1b granted; L6 Verifier PASS (the
  Container Apps environment must exist); L7 in flight or complete — the compliance app is
  deployed by the *same* template and the *same* workflow as the other four
  (`infra/bicep/apps/main.bicep` § `complianceApp`, `.github/workflows/layer-07-apps.yml`),
  so it has no deploy path of its own.
- **An Entra app registration.** Easy Auth validates sign-ins against
  `complianceEntraClientId`, fed from the `MLS_COMPLIANCE_CLIENT_ID` environment variable
  on the `demo` GitHub environment. `mls-compliance-demo-app` is declared in
  `infra/entra/manifest.json` and created by the **Identity workstream** (L3), not this
  layer; it is listed in `docs/runbooks/g0-bootstrap.md` § C9. **F26 correction:** an unset
  variable does NOT make ARM reject the deployment — an undefined GitHub variable expands
  to the empty string, so `readEnvironmentVariable` returns `''` and never reaches its
  `'unset'` default. What actually happens (F36) is that `layer-07-apps.yml` **resolves
  the client ID itself** — by the display name `infra/entra/manifest.json` declares for
  this app, honouring `MLS_COMPLIANCE_CLIENT_ID` first if you set one — and, when it
  cannot, the template gives the app INTERNAL ingress and no `authConfig` rather than
  shipping an Easy Auth block nobody can pass, or a board sitting anonymously on the
  public internet. The same workflow adds this app's Easy Auth reply URL
  (`https://<fqdn>/.auth/login/aad/callback`) to the registration once the app has an
  FQDN, so the variable is an override rather than a prerequisite.
- **`COMPLIANCE_PORT`** — open item P-1. The image serves on 8080 (nginx); the parameter
  still defaults to the placeholder `80`. Set `COMPLIANCE_PORT=8080` on the `demo`
  environment when the first real image publishes, alongside the other four ports.
- Credentials: `mls-github-deployer` for the container-app deploy. The collection job
  needs none — `compliance.yml`'s `collect` job holds only `contents: read`, and its
  `commit` job holds `contents: write` and installs nothing at all.

## Deploy procedure

1. **Collect and commit the state** (runs today, pre-tenant, needs nothing):

   ```
   pwsh compliance/Invoke-MlsCompliance.ps1
   ```

   Writes `compliance/state/state-<ISO-date>.json` and a real-file copy
   `state-latest.json` (never a symlink — authored on Windows, collected on Linux). In CI
   this is `.github/workflows/compliance.yml`, whose `collect` job additionally asserts,
   on the emitted bytes, that there are exactly 110 requirements, that no JSON key is named
   like a percentage/ratio/score, and that `state-latest.json` is not a link. Only then may
   the separate `commit` job move the file into place.

2. **Build the image.** `.github/workflows/app-compliance-ci.yml`:
   build → test → container build → Trivy (fail on CRITICAL) → **smoke test**
   (`docker run` + `/healthz`, the F22 pattern) → GHCR push. The Docker build context is
   the **repo root**, not `apps/compliance` (open item P-7): the Dockerfile copies the root
   lockfile plus `compliance/catalog/` and `compliance/state/`, because the catalog and
   every snapshot are baked into the JS bundle at image build time. There is no runtime
   fetch and no data plane.

3. **Deploy the container app.** Either `app-compliance-ci.yml`'s own deploy job or the
   layer-ordered `layer-07-apps.yml`; both resolve the name through
   `.github/actions/naming` (`mls-compliance-demo-ca`). Only **`layer-07-apps.yml`**
   passes `MLS_COMPLIANCE_CLIENT_ID` — it is a Bicep parameter, and the app CI job is an
   `az containerapp update` that swaps the image and leaves `authConfig` alone; an earlier
   revision of this step claimed both passed it, which was never true. That workflow
   **resolves** `MLS_COMPLIANCE_CLIENT_ID` (and the two dashboard IDs) from the Entra app
   registrations L3 created when the variable is unset, and registers each app's redirect
   URI afterwards (F36); an ID it cannot resolve leaves that app internal-only rather than
   failing the deploy or publishing it open. An OAuth client ID is a public
   identifier — it is visible in the browser's own redirect URL during login — and **no
   client secret is configured for the provider anywhere**, because the app asks exactly
   one question ("is this caller signed in to our tenant") and calls no downstream API on
   the user's behalf.

4. **Deploy `query_compliance`** — no separate step. It ships inside the L8 MCP server
   image (`apps/mcp-tools`), reading the same committed artifact baked into *that* image.
   It has no cloud/local backend split: there is no tenant to switch to.

5. Post the run URL, the board FQDN (`complianceFqdn`) and the collected state's commit
   sha to the Verifier.

> gates in CI, not by an independent read-only identity against deployed state, and the
> sixth cannot be checked at all until the Entra app registration exists."* All three

**`verification/layer-12-audit.ps1` runs as `mls-verifier` and reports 4 PASS + 2 SKIP.**
The distinction the old text drew is still the right one and is now settled explicitly per
criterion rather than for the layer as a whole:

| Criterion | Who checks it | Why there |
|---|---|---|
| **V12.1** artifact complete, no score | **the audit**, independently | reads the committed artifact against the catalog as a SET, so a duplicate or an out-of-catalog row fails too. The expected count is DERIVED from `compliance/catalog/nist-800-171r2.json`, never pinned at 110 |
| **V12.2** honesty invariant | **the audit**, independently | `compliance/tests` property-tests the *derivation*; the audit tests the *artifact that shipped*. Only the second survives a hand-edit, a bad merge, or a collector run from a branch whose derivation differed |
| **V12.3** board renders the artifact | CI gate (`apps/compliance` vitest + bundle grep) | **SKIP by design.** It needs the rendered board, and V12.4 exists to prove the board is unreachable without authenticating. Fetching it to inspect it would mean defeating the control beside it |
| **V12.4** Easy Auth refuses anonymous | **the audit**, independently | two reads: the platform configuration, and a real anonymous GET |
| **V12.5** `query_compliance` grounding | **L8's V8.3** against the deployed server | **SKIP by design.** Re-running `apps/mcp-tools`' own vitest here would not be an independent read of deployed state - it would be this script marking its own homework in a second process |
| **V12.6** collection history | **the audit**, independently | judges the commit that *introduced* each snapshot, not every commit touching the directory |

A SKIP that names its owner is worth more than a PASS that inherited one, so both are
recorded in the report with all six ids present rather than omitted.

Where a criterion is checked today, the command is given verbatim and the number beside it
was **observed on 2026-08-28 at commit `42cebc2`**, not estimated.

### V12.1 — The artifact is complete, and carries no score

- **Criterion (design spec § 3.3):** one entry for every one of the 110 requirements; a
  requirement nothing was said about is `NOT_ASSESSED` / `none`, never an omission. No
  percentage, ratio or score field anywhere.
- **Query:**

  ```
  pwsh compliance/Invoke-MlsCompliance.ps1
  jq '.controls | length' compliance/state/state-latest.json
  grep -Eic '"[A-Za-z]*(percent|ratio|score|pct)[A-Za-z]*"[[:space:]]*:' compliance/state/state-latest.json
  ```

- **Expected:** `110`, and `0`. Both are asserted inside `compliance.yml`'s unprivileged
  `collect` job, before the privileged `commit` job is allowed to touch the file — a short
  or scored artifact must fail there rather than be committed and rendered as a board with
  holes in it.
- **Observed 2026-08-28:** 110 requirements, 4 out-of-catalog rows, 23 evidence records
  from 5 of 5 collectors; zero score-shaped keys.
- **Retry/propagation:** none — the emitter reads files, no clock and no network.

### V12.2 — The honesty invariant holds

- **Criterion (design spec § 3.4):** `COMPLIANT` is reachable from the criteria branch
  alone; an authored assertion can never produce it, whatever its status. `Provenance` is
  set by which branch fired and is never read from an input field, so no record can ask to
  be called machine-verified.
- **Query:**

  ```
  pwsh -c "Invoke-Pester -Path compliance -Output Minimal"
  ```

- **Expected:** all green, including `tests/derivation.Tests.ps1`, which property-tests
  both halves of the invariant over a generated space of assertion shapes — so neither can
  be broken without a test going red.
- **Observed 2026-08-28:** **269 tests passed, 0 failed** across the ten `compliance/tests`
  suites (derivation 94, state-emitter 51, collector-contract 34, repo-static 22,
  catalog 17, verification-suite 13, azure-policy 11, manual 11, github 10, register 6).
- **Retry/propagation:** none.

### V12.3 — The board renders the emitted artifact, unaltered

- **Criterion (design spec § 5.1):** the app is a read-only renderer of the committed
  state. What a reader sees must be what the emitter wrote — including the collector
  limitations and the "nothing has been deployed" statement, which are surfaced *verbatim*
  from `collectors[].limitation` and never re-worded in JSX.
- **Query:**

  ```
  npm run typecheck --workspace apps/compliance      # main.tsx imports the real artifact
  npm test --workspace apps/compliance
  npm run build --workspace apps/compliance
  grep -c "Nothing in this estate has been deployed" apps/compliance/dist/assets/*.js
  ```

- **Expected:** typecheck and tests green; the built bundle contains the artifact's own
  counts and its deployment statement. The board tallies statuses from `controls[]` rather
  than trusting `summary.byStatus`, so a fixture that mutated one without the other could
  not plot a number the rows do not support.
- **Observed 2026-08-28:** typecheck exit 0; **50 vitest tests passed**; the production
  bundle carries `totalRequirements:110`, `NOT_ASSESSED:95`, `PARTIAL:12`, `GAP:3` and one
  copy of the deployment banner — identical to `compliance/state/state-latest.json`.
- **Retry/propagation:** none.

### V12.4 — Easy Auth refuses an unauthenticated request

- **Criterion (design spec § 5.2, decision D8):** the board is human-facing but not public. An
  unauthenticated request must never reach nginx; the platform, not the app, enforces it
  (a static SPA has nowhere to keep a secret or enforce a policy).
- **Query:**

  ```
  curl -s -o /dev/null -w '%{http_code} %{redirect_url}\n' "https://<complianceFqdn>/"
  az containerapp auth show --name mls-compliance-demo-ca --resource-group mls-rg-apps \
    --query "{action:globalValidation.unauthenticatedClientAction, aad:identityProviders.azureActiveDirectory.enabled}"
  ```

- **Expected:** a 302 to the Entra login endpoint — **not** a 200 —
  `unauthenticatedClientAction == "RedirectToLoginPage"`, the Entra provider enabled, and
  no client secret configured on it.
- **Observed 2026-09-01:** **CHECKED, and it PASSES.** `unauthenticatedClientAction ==
  RedirectToLoginPage`, the Entra provider enabled, no client secret. One correction to the
  expectation above: the endpoint answers **302 to PowerShell and 401 to curl** — the same
  refusal, a different shape per client. The audit therefore asserts *any non-2xx*, because
  pinning 302 would fail a working control on the User-Agent of whoever ran it. The
  original note read: *"NOT CHECKED - cannot be. There is no tenant, no deployed app and no
  Entra app registration to point it at."* This criterion is the reason the compliance app is
  deliberately excluded from `main.bicep`'s `containerAppNames` output: V7.1's
  `Test-PublicEndpoint` issues an unauthenticated GET expecting 200, which is the exact
  request Easy Auth exists to intercept. What *is* checked today is the template, by
  `verification/tests/compliance-app.Tests.ps1`.
- **Retry/propagation:** Easy Auth config is applied with the container app revision;
  single check once deployed.

### V12.5 — `query_compliance` answers from the same artifact, and only from it

- **Criterion (design spec § 5.3, D5):** the tool returns authored recommendations
  verbatim and must not extrapolate; it returns no percentage; a missing or malformed
  artifact is an error, never an empty-but-confident answer.
- **Query:**

  ```
  npm test --workspace apps/mcp-tools
  ```

- **Expected:** green, including `tests/compliance-tool.test.ts` (**27 cases**) and
  `tests/allowlist.test.ts`, which pins the server at **exactly six** advertised tools.
- **Observed 2026-08-28:** **321 tests passed** in `apps/mcp-tools`, six tools advertised.
- **Retry/propagation:** none locally. Against the deployed server this is L8's V8.3, whose
  allowlist is now six names — see the note in `L08.md` § V8.3.

### V12.6 — The collection history is a git history

- **Criterion (design spec § 3.3):** state is committed on every run, so
  `git log compliance/state/` answers *when* the estate became compliant and when it
  regressed. Snapshots are never hand-edited.
- **Query:**

  ```
  git log --oneline -- compliance/state/
  ls compliance/state/
  ```

- **Expected:** one dated artifact per collection that changed anything, each authored by
  `github-actions[bot]` with the message `verify(compliance): state at <sha>`.
- **Observed 2026-08-28:** **one** snapshot, `state-2026-08-28.json` — because
  `compliance.yml` has never run on `main`. The Trend view says so in those words ("One
  collection so far… A trend needs at least two dated collections to compare against each
  other — this is one collection, no trend yet, not an empty chart and not an error"), which
  is the honest rendering of a one-row history and is what a stranger will see on day one.
- **Retry/propagation:** the second point appears on the next nightly run; nothing to
  retry.

## Teardown

- **The collection half has nothing to tear down and must not be torn down.**
  `compliance/`, its committed state snapshots and the workflows are repo content. Deleting
  the snapshots would destroy the only record of the estate's posture over time, which is
  the layer's whole product.
- **The board's container app is removed by the standard cycle**, with everything else in
  `mls-rg-apps`: `az group delete --name mls-rg-apps --yes`, via `scripts/down.ps1`.
  **Gate class: gate-free** (RG-scoped demo resources).
- **There is no `L12` teardown script, and this playbook is not describing one.**
  CLAUDE.md requires every layer to ship a triplet — deploy path, teardown script,
  `verification/` audit script — and says a layer without all three is not done. L12's
  honest position, stated rather than papered over (this is finding **F23**'s lesson: three
  runbooks once named teardown scripts that did not exist):

  | Leg | Status |
  |---|---|
  | Deploy path | **Present.** `compliance.yml`, `app-compliance-ci.yml`, and the `complianceApp` module reached by `layer-07-apps.yml`. |
  | Teardown script | **Deliberately none.** The layer's only cloud resource is one container app inside `mls-rg-apps`, which `scripts/down.ps1` already deletes with its four RGs. A dedicated script would duplicate that and add a second path to keep correct. This is the same position L9 takes for the DevSecOps chain. |
  | `verification/` audit script | **ABSENT, and this is a real gap.** No `verification/layer-12-audit.ps1` exists. V12.1–V12.3, V12.5 and V12.6 are enforced by CI gates (`compliance.yml`'s own assertions, `compliance/tests/`, `apps/compliance/tests/`, `apps/mcp-tools/tests/`, `verification/tests/compliance-app.Tests.ps1`) rather than by the Verifier under `mls-verifier`; V12.4 is unenforceable today. **By CLAUDE.md's own rule, L12 is therefore not done.** See § Deferred validation. |

- The Entra app registration Easy Auth depends on is a **tenant object**: its deletion is
  **G3**, and it belongs to L3, not here. `down.ps1` has no code path that can reach it.

## Rollback

- **A bad state artifact** (wrong counts, a score field, a missing requirement) never
  reaches `main`: `compliance.yml`'s unprivileged `collect` job fails first and the
  privileged `commit` job never runs. Fix the emitter or the register and re-dispatch; do
  **not** hand-edit a snapshot — a hand-edited artifact is exactly the laundering this layer
  exists to prevent, and it would silently poison the trend.
- **A regression the board correctly reports** is not an L12 failure. If a control moves
  `PARTIAL → GAP`, the platform is working; the fix belongs to the layer that owns the
  control, and the transition stays in the trend as evidence.
- **A failed container-app deploy** rolls back like any other app: previous revision stays
  active (`app-compliance-ci.yml` deploys by digest), fix forward via PR.
- **L7 warns "Some dashboards are not publicly reachable"** — this is the fail-closed
  path working, not a defect: L7 could not resolve an Easy Auth client ID, so that app
  deployed with internal ingress instead of open to the internet. Run the Identity layer
  (`gh workflow run layer-03-entra.yml`) to create the app registrations, then re-run L7;
  or set `MLS_COMPLIANCE_CLIENT_ID` / `MLS_LAUNCH_OPS_CLIENT_ID` /
  `MLS_CONTROL_TOWER_CLIENT_ID` to bring your own. Never work around it by disabling
  `authConfig`: the two dashboards proxy `/api/` to `data-api`'s subscription-scoped
  Security Reader grant (F25). An **error** naming an ambiguous app registration is a
  different thing — two registrations share a display name, and L7 refuses to guess.
- **Second consecutive failure of L12 → G4**, as everywhere.

## Failure modes

1. **The board shows more green than the estate earned.** Detection: any `COMPLIANT` row
   whose provenance is not `machine-verified`, or a bare `byProvenance` total quoted as if
   it meant "passing". Response: this is the highest-severity failure this layer has —
   `derivation.Tests.ps1`'s property tests and the emitter's `byProvenanceAndStatus`
   cross-tab exist to make it impossible, so a sighting means one of them was weakened.
   Treat as a G4-class event, not a bug ticket. Remember a skipped criterion renders
   `INCONCLUSIVE` / `machine-verified`: **`COMPLIANT` is the only status that means verified
   and passing.**
2. **`CLOSED` leaks onto the board.** Detection: the string `CLOSED` in a rendered status
   badge. Response: `CLOSED` is *register* vocabulary meaning "no known open finding" — it
   is weaker than "the control is met" and belongs to no rendered enum.
   `Get-MlsControlStatus` maps it to `PARTIAL` / `asserted` precisely so the weaker claim
   cannot be laundered into the stronger one; a leak means the derivation was bypassed.
3. **A collector dies quietly and the board looks healthier for it.** Detection: the
   board's collector panel names any collector whose `status != "ok"`; a run where several
   collectors died must never render identically to a healthy one. Response: read
   `collectors[].error`, fix, re-collect. Note that *zero records* is not a failure —
   `github-security` and `azure-policy` legitimately return nothing pre-tenant.
4. **The image ships a stale artifact.** Detection: the board's "Collected … from commit
   `<short>`" line disagrees with `git log compliance/state/`. Cause: the snapshot changed
   after the image was built. Response: `app-compliance-ci.yml` is path-filtered on
   `compliance/state/**` for exactly this reason — if it did not rebuild, check that filter
   before anything else.
5. **The Easy Auth block is deployed with a placeholder client ID.** Detection: ARM rejects
   the deployment (the intended outcome), or — worse — someone "fixes" it by removing
   `authConfig` and the board becomes anonymously reachable. Response: the second case is a
   security regression, not a workaround;
   `verification/tests/compliance-app.Tests.ps1` asserts the auth block exists in code
   rather than merely in a comment, and will go red.
6. **The trend is read as a score.** Detection: any slide, README line or answer quoting a
   single blended number for this estate. Response: there is deliberately no such number —
   counts by status and by provenance only, and the cross-tab of the two. A figure that
   blends machine-verified and asserted controls is exactly the number an adopter would
   quote to an auditor and exactly the number that would be wrong.

## Deferred validation

- **Pre-validated locally and in CI today:** the emitter, the derivation, all five
  collectors, the register and the catalog (**269 Pester tests**); the board (**50 vitest
  tests**); `query_compliance` and the six-tool allowlist (**321 vitest tests** in
  `apps/mcp-tools`); the L7 template and CI wiring for the compliance app
  (`verification/tests/compliance-app.Tests.ps1` + `control-mapping.Tests.ps1`,
  **41 Pester tests** together); and `compliance.yml`'s own byte-level assertions on the
  emitted artifact. All of it runs with no tenant, which is the point.
- **Deferred until tenant, named explicitly:** V12.4 in full (needs the Entra app
  registration, then a deployed revision); the deployed-server half of V12.5 (which is
  L8's V8.3); and every `machine-verified` status on the board — today **zero** controls
  carry one, because every register record declares `criteria: []` and no Verifier report
  exists to collect. The `-Control` annotations are already on all 11 layer audits
  (enforced by `verification/tests/control-mapping.Tests.ps1`), so the first real
  `verification/reports/L*.json` will start populating that column without further code.
- **Deferred work this playbook is naming rather than hiding:** writing
  `verification/layer-12-audit.ps1` so the Verifier, as `mls-verifier`, executes V12.1–V12.6
  against deployed state and commits `verification/reports/L12-<date>.md` like every other
  layer. Until that exists, L12 has two legs of its triplet, not three.
