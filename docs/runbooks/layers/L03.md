## Purpose

Instantiate the manifest-driven identity layer from `infra/entra/manifest.json`:
5 fictional users (flight ops, security analyst, SRE, finance, exec), 5 groups (four
audience groups plus `mls-break-glass`, below), app
registrations for four apps (`launch-ops`, `control-tower`, the compliance board added
by F25, and — since the 2026-08-24 amendment — `mcp-tools` in place of the retired
`copilot-svc`; that one is what Copilot Studio's MCP tool connection authenticates
against with OAuth 2.0), and
**three** Conditional Access policies, plus EMS E5 licenses
assigned via group licensing. All users are fictional (brief rule 4: no real person's
PII).

**Two of the three CA policies are report-only; one is enforced, and the difference is
the whole point.** Added 2026-08-28 on sponsor instruction ("I am ok with entra login.
We should make it 2fa"):

| Policy | State | Scope |
|---|---|---|
| `mls-ca-require-mfa-admins` | `enabledForReportingButNotEnforced` | admin directory roles, **All** applications |
| `mls-ca-block-legacy-auth` | `enabledForReportingButNotEnforced` | **All** users, **All** applications, legacy client app types |
| `mls-ca-require-mfa-dashboards` | **`enabled`** | **All** users, exactly the three dashboard app registrations, break-glass group excluded |

F25 put Easy Auth in front of the three dashboards, so reaching one requires an Entra
sign-in — but Easy Auth asks for whatever the tenant's sign-in policy asks for, and
nothing here asked for a second factor. `mls-ca-require-mfa-dashboards` is what asks.
It is enforced because that is what makes it real; the other two stay report-only
because they target *All applications*, and an enforced All/All grant in a tenant this
repo does not own is a lockout rather than a demo.

## Deploy procedure

1. Dispatch:

   ```
   gh workflow run layer-03-entra.yml
   ```

   [derived] Workflow name per the `layer-<nn>-*.yml` pattern. The workflow runs
   `infra/entra/apply-entra.ps1` (Graph PowerShell, app-only as
   `mls-github-deployer`), which for each manifest entry is **create-if-absent /
   converge-if-drifted**:
   - users (5) with UPNs on the tenant's onmicrosoft.com domain, usage location set
     (required for license assignment);
   - groups (5) with memberships per manifest — except `mls-break-glass`, which is
     created empty on purpose (below);
   - app registrations (4) for `launch-ops`, `control-tower`, `mcp-tools` and the
     compliance board — see the box below;
   - CA policies created in **exactly the state the manifest declares**. The apply
     script does not hard-code a state and never has a reason to: the manifest is the
     decision. What it *does* refuse is an **unsafe** enforced policy — see the
     break-glass box below.

   Order inside that list is load-bearing, not cosmetic. `mls-ca-require-mfa-dashboards`
   scopes itself to three named applications, and Conditional Access addresses an
   application by its client id, which does not exist until the registration does. So
   `apply-entra.ps1` creates groups and app registrations first, collects their ids, and
   substitutes them for the manifest's `includeApplicationsByDisplayName` /
   `excludeGroupsByDisplayName` keys (neither is a Graph field) before the policy is
   posted. A reference it cannot resolve is never posted as an empty — i.e. tenant-wide —
   scope; the policy is skipped and the run says which reference was missing.
2. A dry-run job (`apply-entra.ps1 -WhatIf`) executes first in the same workflow and
   uploads its plan as an artifact; the apply job runs only if the dry-run parses
   clean.
3. Post the run URL + manifest commit SHA to the Verifier.

> **BREAK GLASS: why the first run does not create the enforced policy, and why that is
> correct (2026-08-28).** Microsoft's own guidance is that every enforced Conditional
> Access policy excludes at least one emergency-access account. Without one, a wrong
> policy — a typo'd scope, a grant nobody can satisfy, an MFA service outage — locks the
> tenant's owner out of their own tenant with no way back in. So the manifest declares
> `mls-break-glass`, flagged `"breakGlass": true`, and the enforced policy excludes it.
>
> **An adopter cannot enable this policy without one, and that is enforced in three
> places, not asserted in prose:**
>
> 1. **Authoring.** `Assert-ManifestSchema` refuses any manifest whose `enabled` policy
>    excludes no break-glass-flagged group, targets `All` applications, or names no
>    application at all. The failure is before the first Graph call.
> 2. **Applying.** `Test-BreakGlassReady` reads the group before an enforced policy is
>    created or re-enabled, and refuses unless it holds a member that is **neither** one
>    of the manifest's fictional personas **nor** an on-premises-synced account. The
>    refusal is *per policy* — everything else in the layer still applies — and prints
>    `REFUSING to create ENFORCED CA policy …` in red.
> 3. **Verifying.** V3.3 fails if the group is excluded but empty, or holds only personas
>    or synced accounts. An exclusion pointing at an empty group only looks like a
>    recovery path.
>
> **So L3 is a two-pass layer the first time.** Pass one creates the group empty and
> refuses the enforced policy. You then create the emergency-access account and add it
> (`g0-bootstrap.md` item 13). Pass two — the same `gh workflow run layer-03-entra.yml`,
> idempotent as always — creates the policy. Nothing else waits on this, and every replay
> after that is a no-op.
>
> **The account's membership is deliberately NOT in the manifest.** An emergency-access
> credential is held by a real human; every user in `manifest.json` is fictional, and that
> file is public (CLAUDE.md rule 4). That is also why V3.2 exempts this one group from
> set equality — an adopter doing the right thing must not fail an audit for it — and why
> V3.3 asserts the stronger property in its place.

> **This layer owns FOUR app registrations, and L7 consumes three of them
> (F25/F36, 2026-08-28).** `infra/entra/manifest.json` gained `mls-compliance-demo-app`
> alongside `mls-launch-ops-demo-app`, `mls-control-tower-demo-app` and
> `mls-mcp-tools-demo-app`. Three of the four supply an Entra application (client) ID to
> Container Apps Easy Auth, because both dashboards proxy `/api/` to `data-api`, whose
> identity holds Security Reader at subscription scope. Never route around that by
> disabling `authConfig`.
>
> **Nothing has to be copied out of the portal.** Each entry carries an `appKey` matching
> `infra/bicep/naming.bicep`'s app keys, and `layer-07-apps.yml` resolves each client ID
> itself: it reads the display name for an `appKey` from this manifest and asks Entra for
> that registration's `appId`. `MLS_LAUNCH_OPS_CLIENT_ID`,
> `MLS_CONTROL_TOWER_CLIENT_ID` and `MLS_COMPLIANCE_CLIENT_ID` remain as *overrides* for
> an adopter bringing their own registrations. A registration L7 cannot resolve is not a
> failure: that app deploys **internal to the Container Apps environment**, never
> anonymously reachable, and the L7 run names it and says to run this layer.
>
> **The redirect URIs are no longer a manual step (F36).** Each app's Easy Auth reply URL
> is `https://<that app's ingress FQDN>/.auth/login/aad/callback`, and that FQDN only
> exists after L7 — so L7 adds it, *merged* into whatever the registration already lists,
> right after the apps deploy. Run this layer, then L7; there is no third step.
>
> The manifest change moves V3.1's expected count from 3 to 4 (and the group count from 4
> to 5, with `mls-break-glass`); the audit derives every count from the manifest, so the
> two cannot drift.
> See `L12.md` § Preconditions and `docs/runbooks/g0-bootstrap.md` § C9.

## Validation cycle

Run by the Verifier as `mls-verifier` via `verification/layer-03-audit.ps1` using
Graph **read-only** (`Directory.Read.All`; CA read additionally needs
`Policy.Read.All` — see note under V3.3). Report:
`verification/reports/L03-<date>.md`. All expected values come from
`infra/entra/manifest.json` at the audited commit — the audit reads the manifest, not
the plan text.

### V3.1 — Object counts

- **Criterion (master plan):** Graph queries confirm object counts.
- **Query:**

  ```powershell
  $m = Get-Content infra/entra/manifest.json | ConvertFrom-Json
  ($m.users  | ForEach-Object { Get-MgUser  -UserId $_.userPrincipalName }).Count
  ($m.groups | ForEach-Object { Get-MgGroup -Filter "displayName eq '$($_.displayName)'" }).Count
  ($m.appRegistrations | ForEach-Object { Get-MgApplication -Filter "displayName eq '$($_.displayName)'" }).Count
  ```

- **Expected:** 5 users, 5 groups, 4 app registrations — every manifest entry
  resolves to exactly one directory object; zero extras matching the `mls` naming
  prefix that are absent from the manifest (drift check). The counts come from the
  manifest at the audited commit, so this line is documentation, not the assertion.
- **Retry/propagation:** Entra object propagation can lag 15–45 min (spec F6), so V3.1
  declares `-RetryWindowMinutes 45` and absorbs that wait. V3.2–V3.4 declare 10: they
  read a directory V3.1 has already waited out, and propagation is shared wall clock,
  not a cost each criterion pays again. Polled every 20 s (F59).

### V3.2 — Group memberships

- **Criterion (master plan):** Graph queries confirm group memberships.
- **Query:**

  ```powershell
  foreach ($g in $m.groups) {
    $id = (Get-MgGroup -Filter "displayName eq '$($g.displayName)'").Id
    (Get-MgGroupMember -GroupId $id).AdditionalProperties.userPrincipalName
  }
  ```

- **Expected:** each group's member set equals the manifest's member list exactly
  (set equality — missing or extra members both fail).
- **One exemption, and only one:** a group flagged `"breakGlass": true`. Its membership
  is deliberately not in the manifest — the emergency-access account is a real human
  credential and every persona in that file is fictional — so set equality there would
  fail an adopter for doing exactly what the runbook told them to. Its membership is not
  unchecked: **V3.3 asserts the stronger property**, that the group actually holds a
  usable emergency-access account, because that is what makes the enforced MFA policy
  safe to have turned on.
- **Retry/propagation:** membership writes propagate with the same 15–45 min worst
  case; 30-minute bounded retry.

### V3.3 — every CA policy is in the state the manifest declares, and the enforced one enforces

> **Rewritten 2026-08-28.** This criterion used to assert that *every* CA policy was
> report-only, which meant a green V3.3 was positive evidence that MFA was **not**
> enforced. With `mls-ca-require-mfa-dashboards` that assertion would have been not just
> weak but wrong, so it now checks each policy against **its own** declared state and
> then checks that the enforced one does what it claims.

- **Criterion:** each manifest CA policy is live in the state the manifest declares —
  the two broad policies `enabledForReportingButNotEnforced`, the dashboard policy
  `enabled` — and the enforced policy grants `mfa`, covers exactly the dashboard
  applications the manifest names (never `All`), and excludes a break-glass group that
  actually holds a cloud-only emergency-access account.
- **Query:**

  ```powershell
  Get-MgIdentityConditionalAccessPolicy |
    Where-Object DisplayName -in $m.conditionalAccessPolicies.displayName |
    Select-Object DisplayName, State, Conditions, GrantControls
  # then, for the enforced policy only:
  #   GET /applications?$filter=displayName eq '<dashboard app>'   -> appId
  #   GET /groups/<break-glass group id>/members?$select=id,userPrincipalName,onPremisesSyncEnabled
  ```

  [derived] Reading CA policies requires Graph `Policy.Read.All` (read-only), which
  is not in spec F8's minimal `mls-verifier` grant; `01-root-oidc.ps1` consents it on
  `mls-verifier` at G0 so this audit can run. Read-only scope only — the Verifier
  credential must still be unable to write (a writable Verifier credential is itself
  a finding). The application and group reads need only `Directory.Read.All`, which
  `mls-verifier` already holds for V3.1/V3.2.
- **Expected, policy by policy:**
  - `mls-ca-require-mfa-admins`, `mls-ca-block-legacy-auth` — `State ==
    enabledForReportingButNotEnforced`. Either of them found `enabled` is an immediate
    **SAFETY FLAG** to the lead (failure mode 3): they target All applications, so
    enforcing them is a tenant-lockout risk.
  - `mls-ca-require-mfa-dashboards` — `State == enabled`; `grantControls.builtInControls`
    contains `mfa`; `conditions.applications.includeApplications` equals exactly the three
    dashboard applications' client ids and does **not** contain `All`;
    `conditions.users.excludeGroups` contains the break-glass group, **and** that group
    holds at least one member that is neither a manifest persona nor an on-premises-synced
    account. Report-only here is a FAIL, not a safety flag — it is the regression this
    criterion exists to catch.
- **How an adopter checks the same thing by hand, after L3 runs:**

  ```powershell
  # 1. the policy exists and is enforced
  Get-MgIdentityConditionalAccessPolicy |
    Where-Object DisplayName -eq 'mls-ca-require-mfa-dashboards' |
    Select-Object DisplayName, State,
      @{n='Grants';    e={ $_.GrantControls.BuiltInControls }},
      @{n='Apps';      e={ $_.Conditions.Applications.IncludeApplications }},
      @{n='Excluded';  e={ $_.Conditions.Users.ExcludeGroups }}

  # 2. and, the part a policy read cannot tell you: that a second factor was actually
  #    presented. Sign in to a dashboard, then read the sign-in back.
  Get-MgAuditLogSignIn -Filter "appDisplayName eq 'mls-launch-ops-demo-app'" -Top 5 |
    Select-Object userDisplayName, createdDateTime,
      @{n='MfaRequired'; e={ $_.AuthenticationRequirement }},
      @{n='Methods';     e={ $_.AuthenticationDetails.authenticationMethod }}
  ```

  `AuthenticationRequirement` reads `multiFactorAuthentication` on a sign-in the policy
  actually gated. A policy in state `enabled` with no sign-in behind it proves the
  configuration, not the behaviour — which is why V3.3 asserts the first and this
  paragraph tells you how to see the second. (Sign-in logs need
  `AuditLog.Read.All`; they are not part of the audit's scope.)
- **Retry/propagation:** CA propagation up to 45 min worst case (spec F6); audit
  retries within the standard 30-minute window, and on state-visible-but-wrong fails
  immediately (wrong state is not a propagation artifact). A policy that is **absent**
  is retried — but note the most likely cause is not propagation at all: the apply
  script refused to create it because no break-glass account exists yet
  (`g0-bootstrap.md` item 13). The audit's Detail says so.

### V3.4 — License assignment success for every user flagged `licensed`

> **Amended 2026-08-26.** The criterion used to read "for all 5", which was wrong in two
> directions at once. Nothing in the deploy path assigns a licence — `apply-entra.ps1`
> sets `usageLocation` (a *prerequisite* for licensing) and stops there — so L3 deployed
> and then failed its own audit, and the manual assignment step existed in no checklist.
> It is now **g0-bootstrap.md item C10**. Separately, the criterion assumed all five
> personas stay licensed forever; the EMS E5 trial's free seats expire at day 90, and
> paying for five seats to demo as one is not a cost anyone chose. `manifest.json` now
> carries a per-user `"licensed"` flag and this criterion follows it.
>
> Note the sponsor's 2026-08-26 constraint: the project runs inside a **30-day** window
> bounded by the Azure free credit, which expires 60 days *before* the EMS E5 seats do. So
> in practice all five stay flagged `true` for the life of this demo and the flag is
> insurance rather than a lever you will pull. Keep it correct anyway — the next rebuild
> may not be inside a trial.

- **Criterion:** license assignment state == success for every manifest user with
  `"licensed": true`. A user with the property absent counts as licensed, so a manifest
  predating the flag audits exactly as before.
- **Query:**

  ```powershell
  foreach ($u in $m.users | Where-Object { $null -eq $_.licensed -or $_.licensed }) {
    Get-MgUser -UserId $u.userPrincipalName -Property licenseAssignmentStates |
      Select-Object -ExpandProperty LicenseAssignmentStates |
      Select-Object SkuId, State, Error
  }
  ```

- **Expected:** for each flagged user, the EMS E5 SKU assignment shows `State == Active`
  and `Error` empty — the Graph representation of "success". `Error ==
  MutuallyExclusiveViolation` or `CountViolation` (seats exhausted) is a FAIL.
- **Deliberately not a finding:** a user flagged `"licensed": false`. It still has to
  exist (V3.1) and still has to hold its group memberships (V3.2); what it gives up is
  the sign-in-risk feed and enforceable CA. That is a licensing fact, not drift.
- **If every user is unflagged:** V3.4 passes with `no manifest user is flagged licensed`
  in Observed. That is the honest reading — there is no assignment to verify — but it
  means the demo has no sign-in-risk story at all, so read the Observed text rather than
  the PASS.
- **Retry/propagation:** licensing is asynchronous — allow the full 30-minute bounded
  retry before failing. If you assign per-user rather than through a licensing group, the
  state still lands as `Active`; the group route is a convenience, not a requirement, and
  no manifest group is a licensing group today.

## Teardown

- **Standard kill/rebuild cycle:** **no-op by design.** Entra objects persist;
  `up.ps1` replays `apply-entra.ps1`, whose create-if-absent logic no-ops in seconds
  (spec F6). `down.ps1` never touches Entra.
- **Full teardown:** `infra/entra/teardown.ps1` deletes manifest-listed users,
  groups, app registrations, and CA policies, **in that reverse-dependency order — CA
  policies first**. That order matters more than it used to: deleting `mls-break-glass`
  while the enforced policy still referenced it would leave a live MFA policy whose only
  exclusion points at nothing. Policies go first, so it cannot happen. (The emergency
  account itself is not manifest-listed and survives teardown — only its group
  membership goes with the group.) **Gate class: G3**, per-occurrence
  approval. Deleting these invalidates recorded object IDs and restarts license
  propagation clocks — rebuild after G3 teardown carries the honest 2–3 hour SLA
  (`docs/runbooks/kill-rebuild.md` § G3 variant).

## Rollback

- **First validation failure:** Verifier files specifics. Lead fixes the manifest or
  apply script in its worktree, merges via PR, re-dispatches
  `layer-03-entra.yml` — the converge-if-drifted apply corrects state in place.
  **Never delete-and-recreate Entra objects as a rollback tactic:** deletion is G3,
  and recreation resets propagation clocks, making things slower and noisier.
- **Exception — a *report-only* CA policy found enforced (`enabled`):** the lead may
  immediately re-apply to force the state back to
  `enabledForReportingButNotEnforced` before any
  other analysis; a wrongly-enforced CA policy is a live risk to tenant access, and
  the converge path is a modification, not a deletion (no gate). **This exception does
  not apply to `mls-ca-require-mfa-dashboards`**, which is enforced by design: converging
  *that* one to report-only is a silent removal of MFA and needs the same sponsor
  decision that turned it on. The audit's SAFETY FLAG text names which case it saw.
- **Second consecutive failure of L3 → G4.** Note the risk-register expectation:
  propagation lag is the most common false failure here; the audit's built-in
  30-minute retry exists precisely so G4 means something real.

## Failure modes

1. **Graph consent missing/revoked** (`Authorization_RequestDenied` from
   `apply-entra.ps1`). Detection: workflow fails on first write with 403. Response:
   credential failure — human re-runs the consent step of `01-root-oidc.ps1`;
   recurrence is G4 by definition.
2. **Trial licenses not activated or seats exhausted** (V3.4 shows `Error =
   CountViolation` or the SKU absent from the tenant). Detection: audit V3.4, or
   apply-script warning when the licensing group's assignedLicenses call fails.
   Response: human action in M365 admin center (activate trial / check the 25-seat
   pool — 5 demo users + admin fit comfortably; exhaustion implies test users leaked
   from earlier runs → clean up via manifest, not portal).
3. **A broad CA policy created enforced instead of report-only.** Detection: V3.3
   observes `State == enabled` on `mls-ca-require-mfa-admins` or
   `mls-ca-block-legacy-auth` and raises a SAFETY FLAG naming it; also guarded pre-merge
   by Pester tests asserting each policy is posted in the state its manifest entry
   declares. Response: immediate converge re-apply (see
   Rollback exception); then root-cause the apply script — this class of bug is a
   mandatory retro item because the blast radius is tenant lockout.
   (`mls-ca-require-mfa-dashboards` being enforced is *not* this failure mode.)
4. **UPN domain mismatch** (manifest UPNs use a vanity domain not verified on the
   tenant). Detection: user creation fails `Request_BadRequest` naming the domain.
   Response: manifest fix to the tenant's onmicrosoft.com default domain via PR;
   re-apply.
5. **Propagation lag mistaken for missing objects.** Detection: V3.1/V3.2 partial
   counts that increase between polls. Response: nothing — the audit's 30-minute
   bounded retry is the response; leads must not re-run apply mid-audit (double
   writes churn the directory and can create the very drift the audit flags).
6. **The enforced MFA policy was refused, or is missing.** Detection: the apply log
   says `REFUSING to create ENFORCED CA policy …` and the summary line reports
   `CaBlocked=1`; V3.3 then fails with "2 of 3 manifest CA policies visible". Response:
   this is the guard working, not a bug — create the emergency-access account
   (`g0-bootstrap.md` item 13), add it to `mls-break-glass`, re-dispatch the layer. If
   the account *does* exist, check it is cloud-only and is not one of the demo personas:
   both are disqualified deliberately, and the refusal message says which test failed.
7. **The enforced MFA policy exists but its exclusion is hollow.** Detection: V3.3 fails
   with "excludes […] but no such group holds a cloud-only emergency-access account".
   The policy is live and enforcing while nothing can recover from it being wrong.
   Response: treat as urgent — restore the emergency-access account first, investigate
   who removed it second.

### Failure mode: `Request_ResourceNotFound` on a group membership

`POST groups/{id}/members/$ref` returns 404 `Request_ResourceNotFound` moments after the
user and group were both confirmed visible. This is **directory replication, not a missing
object**: visibility is a GET, and the membership write needs a replica that can resolve
both objects and link them - a strictly stronger condition (F67). Handled automatically at the Graph choke point (`Invoke-GraphApi`), so it covers every
call and not just the one observed to fail -
the call retries for `-PropagationTimeoutSeconds` (default 180) and only then fails, with
an error that says replication rather than "does not exist". Any other Graph failure is
raised immediately and is a real defect: a 403 does not become a 200 by waiting.


### Failure mode: the enforced CA policy is refused

Two causes, both deliberate refusals rather than errors, and both leaving the layer's other
work intact.

1. **No usable break-glass account.** `Test-BreakGlassReady` requires a member of the
   break-glass group that is cloud-only, is not one of the manifest's demo personas, **and
   holds an active Global Administrator role**. That last condition was added 2026-08-30
   after an account satisfying the first two — and holding no role whatsoever — passed the
   check (F77). A PIM-*eligible* assignment does not count and is reported with the reason:
   activating it needs a sign-in, a healthy PIM service and usually MFA, which are the
   controls the account exists to bypass. See `docs/runbooks/g0-bootstrap.md` item 13.

2. **Security Defaults are enabled on the tenant.** Graph will not accept an *enabled*
   Conditional Access policy alongside them; report-only policies are fine, which is why
   this layer deploys two of three and declines the third. **This is a supported
   configuration, not a defect.** V3.3 passes: control 3.5.3 asks whether MFA is enforced,
   and Security Defaults enforce it (F78). Do not disable them to make the policy land —
   this manifest enforces only the dashboard policy, so the tenant would lose baseline MFA
   for every user in exchange for one policy (F75). The supported route to Conditional
   Access is: raise the two broad policies to `enabled` in the manifest, register MFA for
   the accounts they scope, then disable Security Defaults, in that order.
