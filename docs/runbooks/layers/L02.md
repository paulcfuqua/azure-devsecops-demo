# L2 Playbook — Landing Zone: Management Groups, Policies, NIST

| | |
|---|---|
| **Layer** | L2 |
| **Lead** | Identity & Governance |
| **Master plan** | `docs/superpowers/plans/2026-08-22-g1-master-plan.md` § L2 |
| **Teardown gate class** | **G3** (tenant-level: MG + policy assignments); standard cycle leaves them |
| **Cost delta** | $0 |

## Purpose

Stand up the mini landing zone: management group `mls` under the tenant root with the
demo subscription moved beneath it, and the governance policy set — tag **deny** on
resource groups missing the six required tags (`env`, `app`, `costCenter`, `owner`,
`dataClassification`, `managedBy=iac`), tag-inherit **modify** on resources,
allowed-locations guardrail, and the NIST 800-53 R5 initiative assigned at
subscription scope in **audit mode**. Every later layer's RG creation is subject to
these policies, so L2 must be verified before any resource-bearing layer runs.

## Preconditions

- G0 complete + G1b granted; L1 has Verifier PASS (`verification/reports/L01-*.md`) —
  the deploy runs through the OIDC path proven there.
- Orchestrator unblock for L2.
- `mls-github-deployer` holds Owner on the subscription (G0) — Owner at subscription
  scope covers policy assignment there; creating the MG under tenant root and moving
  the subscription additionally require the tenant-root MG permissions the human
  granted at G0 (`01-root-oidc.ps1` output lists them; if absent, this layer fails
  fast — see failure mode 1).
- Track E artifacts merged: `infra/bicep/` landing-zone templates compile clean;
  Track C's `infra/policy/` scripts Pester-green with mocked Az calls.

## Deploy procedure

1. Dispatch the layer workflow (called by `infra-up.yml` in full runs):

   ```
   gh workflow run layer-02-landing-zone.yml
   ```

   [derived] Workflow file name instantiates the master plan's `layer-<nn>-*.yml`
   pattern. The workflow, as `mls-github-deployer` via OIDC:
   - `az account management-group create --name mls` (idempotent — succeeds or
     no-ops if present);
   - `az account management-group subscription add --name mls --subscription
     $AZURE_SUBSCRIPTION_ID`;
   - deploys `infra/policy/` assignments via Bicep at MG/subscription scope: tag deny
     (RGs), tag-inherit modify (resources), allowed-locations, NIST 800-53 R5
     initiative (built-in initiative, `enforcementMode: DoNotEnforce` = audit mode);
   - runs the **negative canary test**: attempts
     `az group create --name mls-rg-canary-untagged --location $AZURE_LOCATION`
     with no tags, asserts the failure is `RequestDisallowedByPolicy`, and deletes
     the canary if it was (wrongly) created. [derived] Canary RG name and the
     placement of the negative test in the deploy workflow: the Verifier is
     Reader-only and must not perform writes, so the write-attempt lives with the
     deployer and the Verifier confirms it independently from the Activity Log
     (V2.2).
2. Wait for run success, then hand the run URL + assignment IDs (deployment outputs)
   to the Verifier.

## Validation cycle

Run by the Verifier as `mls-verifier` (Reader) via `verification/layer-02-audit.ps1`;
report committed to `verification/reports/L02-<date>.md`.

### V2.1 — Subscription sits under MG `mls`

- **Criterion (master plan):** `az account management-group show mls` shows the sub.
- **Query:**

  ```
  az account management-group show --name mls --expand --recurse \
    --query "children[?contains(id, '$env:AZURE_SUBSCRIPTION_ID')].displayName"
  ```

- **Expected:** exactly one child returned — the demo subscription. (Reader on the
  subscription grants MG read via the subscription's ancestry; if the MG read is
  denied, that is a finding on `mls-verifier` scope, not a pass.)
- **Retry/propagation:** MG moves propagate in minutes; standard 30-minute bounded
  retry, poll every 5 minutes.

### V2.2 — Untagged canary RG creation fails with policy denial

- **Criterion (master plan):** creating an untagged canary RG **fails** with policy
  denial (then cleaned up).
- **Query (read-only — the Verifier audits the deployer's canary attempt from the
  Activity Log rather than attempting a write itself):**

  ```
  az monitor activity-log list --offset 2h --status Failed \
    --query "[?contains(resourceGroupName,'mls-rg-canary-untagged')].{op:operationName.value, sub:subStatus.localizedValue, code:properties.statusMessage}"
  az group exists --name mls-rg-canary-untagged
  ```

- **Expected:** at least one `Microsoft.Resources/subscriptions/resourceGroups/write`
  event with failure code `RequestDisallowedByPolicy` naming the tag-deny assignment;
  `az group exists` returns `false` (canary cleaned up).
- **Retry/propagation:** policy assignments can take up to 30 minutes to become
  effective; if the Activity Log shows the canary **succeeding**, the deploy workflow
  retries the canary after a delay — the Verifier polls the log within the standard
  30-minute window before declaring failure.

### V2.3 — NIST compliance data present

- **Criterion (master plan):** `az policy state summarize` returns NIST compliance
  data within 30 min of assignment.
- **Query:**

  ```
  az policy state summarize --subscription $env:AZURE_SUBSCRIPTION_ID \
    --query "policyAssignments[?contains(policyAssignmentId,'nist')].{id:policyAssignmentId, nonCompliant:results.nonCompliantResources}"
  ```

- **Expected:** the NIST 800-53 R5 initiative assignment appears with a populated
  `results` block (non-zero total evaluated resources once any resources exist;
  immediately post-L2 the evaluated set may be small — presence of the assignment
  summary with results is the pass condition, per the plan's wording "returns NIST
  compliance data").
- **Retry/propagation:** **explicitly 30 minutes** per the master plan — poll every
  5 minutes from assignment timestamp; a first evaluation cycle beyond 30 minutes is
  a criterion failure.

## Teardown

- **Standard kill/rebuild cycle:** **leaves L2 intact.** MG + policy assignments are
  tenant-level objects that persist (spec F6); `down.ps1` never touches them, and
  `up.ps1` replays L2 as an idempotent no-op in seconds.
- **Full teardown:** `infra/policy/teardown.ps1` removes the policy assignments, the
  NIST initiative assignment, moves the subscription back to tenant root, and deletes
  MG `mls`. **Gate class: G3** — per-occurrence human approval, stated scope, no
  exceptions. See `docs/runbooks/kill-rebuild.md` § G3 variant.

## Rollback

- **First validation failure:** Verifier files the FAIL report. Identity & Governance
  lead corrects in-place — all L2 operations are idempotent (MG create, subscription
  add, policy assignment deploy re-applies) — and re-dispatches
  `layer-02-landing-zone.yml`. Fix-forward only: do **not** delete the MG or
  assignments to "reset" (that is G3 territory and unnecessary — re-assignment
  overwrites).
- **Distinguish propagation from defect** before touching anything: V2.2/V2.3
  failures inside the 30-minute window are retried by the audit itself, not rolled
  back.
- **Second consecutive failure of L2 leads to G4.** Particularly likely trigger
  here: management-group creation refused at the root (see failure mode 1),
  which is a credential failure and independently a G4 condition.

## Failure modes

1. **Management-group creation refused at the tenant root** (`AuthorizationFailed`
   on `az account management-group create`). Detection: the *Ensure management group*
   step fails at `/providers/Microsoft.Management`. Note what this is NOT: by default
   any directory principal may create an MG beneath the root and becomes its Owner,
   so this step normally succeeds with no tenant-root RBAC whatsoever, and the
   deployment that follows targets MG `mls` -- which the deployer now owns -- rather
   than the root. The failure means the tenant has enabled the hierarchy setting
   *Require write permissions for creating new management groups*. Response: a human
   either turns that setting off or grants the deployer
   `Microsoft.Management/managementGroups/write` at the root. Do **not** answer this
   by granting Owner at `/` and pointing the deployment there: a standing root-scope
   Owner is a worse finding than the outage (F47). Recurrence escalates G4.
2. **Policy propagation lag causes a false-negative canary** (canary RG creates
   successfully minutes after assignment). Detection: deploy workflow's canary
   assertion fails; Activity Log shows a *succeeded* write. Response: delete the
   canary immediately (it was created untagged — it must not survive), wait, re-run
   canary; only after the 30-minute window counts as a validation failure.
3. **NIST built-in initiative definition ID drift** (Azure republishes the
   initiative; hardcoded definition ID no longer resolves). Detection: assignment
   deploy fails with `PolicyDefinitionNotFound`. Response: `infra/policy/` resolves
   the initiative by display name lookup at deploy time; pin the new ID in the layer
   manifest via PR — never hand-edit in the portal.
4. **Canary RG left behind** (assertion passed but cleanup step failed). Detection:
   V2.2's `az group exists` returns `true`. Response: the deploy workflow re-run
   deletes it (`az group delete --name mls-rg-canary-untagged --yes`); RG-scoped
   delete is gate-free. Verifier re-audits.
5. **Tag-inherit modify policy misfires on later layers** (resources created before
   the modify assignment finished propagating carry no inherited tags). Detection:
   later layer audits find untagged resources despite tagged RGs. Response: trigger a
   policy remediation task from code
   (`az policy remediation create`) in the deploy path — never hand-tag in the
   portal.

## Deferred validation

- **Pre-validated locally in Phase P:** Track E — every `infra/bicep/` landing-zone
  template passes `bicep build` and `bicep lint` with no errors; Track C — the
  `infra/policy/teardown.ps1` is Pester-tested with mocked `az` calls (L2 has no
  apply script -- it deploys straight from `layer-02-landing-zone.yml`)
  (idempotency branches, error paths) and PSScriptAnalyzer-clean; `actionlint` clean
  on `layer-02-landing-zone.yml` (Track G).
- **Deferred until tenant (named explicitly):** MG creation and subscription
  placement (V2.1), live policy-denial behavior (V2.2), NIST policy-state evaluation
  (V2.3), and real `az deployment what-if` on the landing-zone templates. All are
  covered by `verification/layer-02-audit.ps1` at L2 deploy time — nothing about live
  policy state can be simulated locally.
